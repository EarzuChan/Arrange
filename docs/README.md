# Arrange 文档工作总约束

本文档描述 `Arrange` 项目 `docs/` 目录下文档的撰写、维护与归档标准。本规范仅约束文档工作，不约束项目代码的具体技术实现。

这篇“文档工作总约束”被被视为文档工作的“元文档”。

## 核心目标

`docs/` 目录的内容必须保持清晰、克制、可维护，以确保项目维护者能够以最低成本确认以下三项事实：

1. **项目全貌**：项目的总体方向与最终形态。
2. **当前状态**：当前里程碑的进度与待办事项。
3. **技术事实源**：任意一项核心技术设定的唯一依据所在位置。

## 目录职权划分

### `docs/proj/`：项目管理与工作区

用于承载项目推进过程中的管理状态与阶段性约束。

**包含内容：**
- 项目总纲。
- 里程碑（总表）。
- 术语速查表。
- 远期想法暂存器。
- 具体开发的额外约束（仅限一篇：用来记录一些事关开发的杂项事宜，比如代码风格）。
- 各个里程碑的临时工作目录（例如 `docs/proj/m1/`），用于存放当前里程碑的待办、退出审计、杂项文件。

**不负责内容：**
- 深入解释项目架构细节。
- 冻结或定义 API 细节规范。
- 重复阐述 `docs/arch/` 中已存在的长期技术设定细节。

**生命周期要求：**
在一个里程碑结束后，视情况将 `proj/m<N>/` 中被验证为长期有效的技术设定迁移至 `arch/` 或建立新 ADR，避免将阶段性的临时状态遗失在里程碑工作目录中。

### `docs/adr/`：架构决策记录

用于记录在时间线推进中产生的重大技术决策及其背景。每篇 ADR 应记录多项内容，以提高信息密度，杜绝文档量爆炸，

**定位与职责：**
- 记录某阶段做出的技术选择及其带来的影响。
- 为后续维护者提供“为什么系统会设计成这样”的历史上下文。

**管理规则：**
- 按时间顺序编号（编号越大，篇目越新）。
- 当新 ADR 与旧 ADR 有的同一事物有不同阐释时，以新 ADR 的设定为准。
- **只编辑最新篇目**：一旦产生更新的 ADR 篇目，就只能编辑新篇目，全部旧 ADR 篇目都不能再编辑。
- 允许在旧 ADR 顶部追加简短的元信息（例如声明“本篇部分内容已被新 ADR 替代”），但严禁篡改旧 ADR。
- 历史 ADR 仅代表历史决策，不应混淆设定；关于项目总体设定的唯一事实源应沉淀在 `arch/` 目录中。旧 ADR 与当前 `arch/` 母文档冲突时，当然是以 `arch/` 中的描述为准。

### `docs/arch/` (长期架构与核心设定)

用于记录里程碑无关的，直抵项目目标的细节技术设定。

**包含内容：**
- 架构边界与核心设计（运行时、渲染、输入、native boundary、诊断等）。
- API 形态与行为语义。
- 测试与验证策略。

**不负责内容：**
- 当前开发进度：应在里程碑工作目录下管理。
- 特定里程碑的人工验收进度。
- 已过期、被更改的历史设定：旧记录可自然留存于 ADR 中（意思是如果当时有写 ADR，那就有留存，没写，那没了就是没了），不可找补“缅怀”旧设定。

**撰写要求：**
`arch/` 中的文档必须以“系统最终应达成的目标”为基准进行编写，而非记录“当前阶段如何粗糙实现”。若当前代码实现确为过渡状态，必须在文档中明确指出其为“暂无能力/暂无必要进行深入设计”而产生的总体妥协。

## 唯一事实源规则

系统中的一个具体设定，只能在唯一一篇母文档中进行深入解释：即某一文档中若包含某一设定的具体阐述，则不可再在其它文档中重复具体阐述。

其他关联文档在涉及该概念时，仅允许：
- 进行简短的上下文引用（提一嘴名字）。
- 编写相关的验收要求或历史背景。
- **提供指向母文档的相对路径链接**。

严禁在多个文档中重复阐述同一事物的具体设定，啰嗦且不论，最可怕的是：无法确定单一信源，如果有不统一的叙述，那该取信哪里？！

**母文档分配示例：**

| 主题 | 唯一事实源 (母文档) |
| :--- | :--- |
| App 入口、`useLive`、`useDist` | `docs/arch/02-App入口.md` |
| 热更新与 Reload 链路 | `docs/arch/06-热更新.md` |

若发现多个文档同时详细解释同一概念，维护者必须立即确立母文档，并将其他位置的解释内容删减，视情况添加引用链接。

## 冲突处理优先级

当不同文档对同一概念或规则的描述发生冲突时，按以下优先级进行事实判定（1 为最高）：

1. **`arch/` 中的当前母文档**：最高长期事实源。
2. **编号最新的 `adr/`**：代表最新的技术决策走向。
3. **`proj/m<N>/` 下的文档**：仅代表里程碑下的当前（临时）工作状态，无权覆盖长期架构设定。
4. **看板、待办列表与审计文档**：仅代表管理状态，不作为 API 或架构事实源。

若冲突无法通过上述优先级明确判定，维护者应立即更新对应的 `arch/` 母文档以确立标准，并在冲突的旧文档位置留下指向母文档的链接。

## 行文与用词约束

文档须以中文为主，允许保留必要的英文专业术语。禁止使用纯英文编写完整文档。

**行文要求：**
- 表述需言简意赅、客观清晰。
- 首次引入非通用专业术语或自定义概念时，必须给出明确定义。
- 不可啰嗦，不可写“黑话”（好：整体流程已经跑通，实现效果很稳定，接口也定下来了。到此为止，我们算是做了一套完整的声明式 UI 框架”，不好：“这个链路已闭环，功能很稳，语义已冻结；我们不是在构建传统意义的兼容层，而是基于声明式范式重塑了一套新一代 UI 基础设施”）

## 文档变更路径与依赖维护

**修改前的归属判定：**
在新建或修改文档前，按以下逻辑判断内容归属：
1. 属于长期生效的系统设定：写入 `arch/`。
2. 属于特定历史背景下的决策论证：写入 `adr/` 的最新篇目（不可编辑历史篇目！）。
3. 属于当前里程碑的局部或临时状态：写入 `proj/m<N>/`。
4. 属于项目管理规则或基础环境配置：写入 `proj/`。
5. 若该概念已存在母文档：直接修改母文档，其余文档仅维护链接。

**修改后的级联检查：**
修改完成后，必须检查以下事项：
- 文档间是否产生了重复的事实源。
- 新内容是否与现有的 ADR 发生未声明的冲突。
- 是否将临时性设定错误地写进了长期架构文档中。
- 是否将长期有效的架构规则错误地留在了里程碑工作目录：而没“沉淀”到相关 `arch/` 文档或 `adr\` 篇目。

**命名与链接约束：**
- 文件名必须直观反映文档内容，保持命名稳定。
- 文档间的引用必须使用实际存在的文件相对路径。
- 若必须重命名文档，应全局搜索并同步修正所有指向该文件的路径链接。

## 里程碑施工期间的要求

在每个里程碑（M<N>）工作周期中，视情况执行以下文档归档动作：
1. 梳理实践中产生的重要技术决策，补充撰写并归档为新的 ADR。
2. 在里程碑工作收尾期，提取该里程碑中已完成验证且长期有效的架构设定，修订至 `arch/`。
3. 在 `proj/m<N>/待办.md` 中对已完成的临时事项进行“打标”，并简单阐述完成情况。
4. 在该里程碑的退出审计报告中，明确记录验收结论并提供验证证据的存储位置。
5. 同步整体里程碑进度状态。

## 绝对禁止事项

- 禁止在多个文档中对同一核心概念进行分散且深入的重复阐述。
- 禁止修改、增删或篡改历史的 ADR 篇目。
- 禁止将过渡性的临时过程堆砌在 `arch/` 目录的长期文档中。
- 禁止在不同文档间重复阐述单一具体规则设定。
