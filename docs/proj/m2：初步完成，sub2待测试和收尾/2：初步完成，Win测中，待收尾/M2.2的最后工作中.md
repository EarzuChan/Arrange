- 默认构建目录在 FetchContent 布局下可容纳约 33 个字符的用户名；使用外部 JUCE 源码时约 13 个字符，超出由预检报告并提示 `native.buildRoot`。

- 本轮复验中 `pnpm install` 因公网 npm 的 `ECONNRESET` 重试，耗时 9 分半，与 CLI 无关。

## 主人试玩暴露的问题与修复（2026-10-10）

现象：create 后立即 sync，SETUP 失败；再次 `arrange sync` 报 `Fatal arrange.project.yaml: framework-incompatible — fetch failed`。

原因：

- 首次 SETUP：UI 依赖装了 15 分钟（公网 npm 的 `ECONNRESET`，本机网络环境所致）；随后 native configure 克隆 GitHub 上的 Arrange 仓库失败。另外远端没有 `v0.0.0-m.3.0` tag（只有 `m.2.0`、`m.2.1`），网络正常也会失败。
- 再次 sync：工程配置的本地 registry 当时没有在运行。CONFIG 总是在线查询 registry，连接被拒后被归类为“不兼容”，信息只剩 `fetch failed`（真实原因 `ECONNREFUSED` 在 `error.cause` 里被丢掉）。已装入本地的 Framework 本可离线判定，却没有用。

修复（规则写在 [CLI 与工程模式](../../../arch/31-ArrangeCLI与工程模式.md#版本与工具链) 与[托管模型](../../../arch/32-ArrangeCLI托管与同步模型.md)）：

1. 区分“连不上”与“不兼容”：新增 `RegistryUnreachableError`，信息带 registry 地址和真实原因；sync 把它报告为 `framework-unverifiable`，registry 明确给出的否定答案仍是 `framework-incompatible`。用户取消仍以 AbortError 传出。
2. sync 的 CONFIG 与 SETUP 改为已安装优先：本机 UI 目录里的 Framework 版本与契约匹配就不联网。
3. SETUP 预检 Arrange 原生源码：需要配置构建树时，在安装 UI 依赖之前用 `git ls-remote --tags` 确认 git 可用、仓库可达、tag 存在。预检在测试中暴露过一个会让它静默失效的错误（托管项 id 写成了区域 id `cmake.framework-version`，应为 `framework.version`），已修。

真机验证（全新打包的 CLI，registry 与 git 按下述情形）：

| 情形 | 结果 |
|---|---|
| 默认 GitHub 地址，远端没有该 tag | 12 秒内 `Fatal native-source`，说明仓库、缺失的 tag、Framework 版本与本地源码出路；SETUP 在装 UI 之前停下（此前是 15 分钟后一大段 CMake 栈） |
| registry 不可达，本机没装 Framework | `framework-unverifiable — 无法连接 registry http://127.0.0.1:4873：connect ECONNREFUSED 127.0.0.1:4873；本机 UI 目录里没有可用于离线验证的 @arrange/framework@0.0.0-m.3.0` |
| registry 不可达，Framework 已装 | 完整 `sync` 通过（CONFIG Fatal 0，SETUP 完成），不联网 |
| `create --fetch-content <本地 git 仓库路径>`，本地有 tag `v0.0.0-m.3.0` | 预检通过；FetchContent 从本地仓库克隆成功，native SETUP 80 秒完成。克隆体量实测每棵构建树 14 MB（`.git` 8 MB） |

测试：CLI 271 项（265 通过、0 失败、6 跳过），新增 `framework-resilience.test.ts` 13 项，并在 `setup-build-dev.test.ts` 补 2 项；预检用真实的本地 git 仓库验证，不依赖外部网络。

本地发布了 git tag `v0.0.0-m.3.0`（指向 `794b899`，未推送远端），供 `--fetch-content` 指向本地仓库时使用。

仍存在但未改的：CONFIG 报告里同一个 `.npmrc / node.registry` 出现两行（Cluster 与 Region 的 id 都是 `node.registry`），仅显示重复。（2026-10-11 随终端输出重构解决：报告默认只列需要处理的条目；区块组按托管标记写作 `cluster:node.registry`。）

## 终端输出重构（2026-10-11）

主人试玩后提出：去掉 `[ArrangeCLI]` 前缀，交互输出统一为 clack 风格；pnpm、cmake、Vite、Standalone 的原始输出不再直通终端，而是收进固定高度、可滚动回看的框；进度与用时可见；可并行的大任务并行执行，失败按 gradle 语义（其余跑完再一起报告）。规则写入[CLI 与工程模式](../../../arch/31-ArrangeCLI与工程模式.md#终端输出与交互)，SETUP 执行顺序的变更写入[托管模型](../../../arch/32-ArrangeCLI托管与同步模型.md)，验证方式写入[测试策略](../../../arch/22-测试策略.md)。

完成内容：

1. 输出通道：新增 `cli/src/ui/`（Screen 实时区域、Reporter 消息、TaskBoard 任务面板、LogView 缓冲与视口、LineDecoder 解码、Input 解析、ConsoleInput 输入持有者、TaskLog 日志文件）。`[ArrangeCLI]` 前缀全部移除；各命令以标题行开头、以完成/失败/取消行结束；CONFIG/SETUP 报告折叠为计数加需要处理的条目，本机工具改为表格。
2. 任务框：安装、configure、构建都作为任务呈现；ninja 的 `[n/N]` 驱动真实进度条；日志框支持滚轮（按位置命中并聚焦）、方向键、翻页、Home/End、Tab、点击；失败时写入原因、日志末尾与完整日志路径；日志写入 `.arrange/logs`，保留最近 20 次运行。扫描、加载、读取 Framework 版本等无日志等待显示临时状态行。
3. 并行：SETUP（UI 安装 ∥ debug configure ∥ release configure）、build（UI ∥ native）、release dev（UI ∥ Standalone）。Windows 构建根认领在进程内只做一次，避免两个 flavor 并发写 `owner.json`；SETUP 结束后再次核对配置快照。
4. dev：Vite 与 Standalone 各一个常驻窗格，状态为启动中、就绪、运行中；结束时给出各自的摘要与日志路径。
5. 编码与颜色：子进程输出逐行先按严格 UTF-8、失败按控制台代码页解码（实测 cl 经管道时随控制台代码页输出：936 为 GBK，65001 为 UTF-8，437 下中文已是问号）；子进程强制颜色，CMake 打开彩色诊断，MSVC 的错误、警告行由 CLI 着色。
6. 新依赖：运行时 `fast-string-width`（clack 已在用的宽度计算库）；开发依赖 `@xterm/headless`（渲染测试用的真实终端模拟器）。

真机验证中发现并修复的问题：

- 帧里用 `\n` 换行依赖终端驱动转换 CRLF：xterm 回放测试中行首错位。TTY 下改写 `\r\n`。
- 缩放窗口时 xterm.js（VS Code 终端）不重排光标所在行，按“每行占几行”计算的擦除行数与实际不符，擦掉了上方内容。改为每帧以换行结束、光标停在区域下方的空行，光标行恒为空。
- 命令结束后进程不退出：clack 提问结束时在 stdin 仍在读取的情况下切回行模式，Windows 上由此产生的行模式读取阻塞在 ReadConsole、等回车才返回；之后任务会话的输入（滚轮、光标位置应答）全被它截住，退出时也一直等它。曾尝试调整停止顺序、在切模式前暂停读取，均无效。最终改为 ConsoleInput 独占 stdin：首次需要时进入原始模式并保持到命令结束，clack 读取代理流，任务会话与提问不再争用、不再切换模式。修复后提问之后的滚轮有效，诊断入口在不显式退出的情况下也能自然退出；入口另在恢复终端、写完输出后显式结束进程，作为保险。
- 滚轮滚动某个框后按 End 作用到了另一个框：滚轮改为同时把焦点移到该框。
- 窄终端里操作提示被截断，“Ctrl+C 取消”看不到：提示按宽度在完整、紧凑、最简三档中选择。
- 每 80ms 整帧重绘（实测一次两分钟的 configure 写出约 4MB）：改为行数、列数不变时只重写变化的行。
- 只有临时状态行时也开启了鼠标上报，期间无法用滚轮翻看终端历史：改为存在任务框时才接管按键与鼠标。

Windows 真机结果（ConPTY 运行正式入口，xterm.js 回放屏幕）：sync（三个 SETUP 任务并行、确认工具提问后接任务框）、build --clean（UI 18s 与 native 1m24s 并行、进度 34/149→101/149、框内滚动后 3 秒内容不动、End 恢复跟随）、build 中按 Ctrl+C（35 个编译进程 3.3 秒内全部结束，退出码 130，光标与鼠标上报恢复）、dev（两个窗格分别显示 Vite 与 Standalone 日志，Ctrl+C 后 Vite 与 Standalone 无残留）、create 提问中的方向键与 Ctrl+C 取消。CMake 输出经管道是逐步到达的（采样所见框内 16→20→21→25 行），框内日志是实时的。

测试：CLI 共 327 项（318 通过、0 失败、9 跳过，跳过的均为既有的 macOS 专属测试）；新增 `ui-ansi`、`ui-line-decoder`、`ui-input`、`ui-log-view`、`ui-task-board`、`ui-screen`、`ui-tasks`，其中屏幕与会话测试用 xterm.js 无头终端回放，断言实际屏幕与滚动历史，滚轮命中依赖模拟终端对光标位置查询的真实应答。

已知边界：缩窄窗口后，若终端重排出的实时区域高于整个屏幕，溢出部分已被推进滚动历史，无法擦除，会留下一段旧帧（主缓冲区流式呈现的固有限制，测试中有专门用例记录）【日后谈：是否这个可以变成，进入CLI运行后，整个屏幕都被CLI接管？整个滚动最新的界面，抽象为CLI内的，滚动是CLI内的滚动，而不是原生外部控制台Shell】。
