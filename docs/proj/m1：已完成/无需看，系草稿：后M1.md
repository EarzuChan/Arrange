# 已知问题

以下问题来自后 M1 调度、动画与代码结构复盘。当前只记录问题与初步判断，不代表已经确定最终修复方案；后续需要结合 profiler 与具体讨论逐项收束。

## 1. 动画每帧穿越 JS / Vue / native 全链路

当前动画大致会经过：

```txt
native frame tick
-> QuickJS RAF
-> JS 动画计算
-> Vue reactive update
-> renderer patch
-> native mutation
-> apply
-> invalidation
-> layout / paint plan
-> DrawOps
-> repaint
```

这会把整条 composition 链路每帧点燃。Debug 下 QuickJS、Vue flush 与 C++ debug build 成本叠加，容易造成肉眼可见卡顿；Release 虽好一些，但仍可能存在帧间距波动。

初步方向：

- 保持现有 `animate*AsState` / `updateTransition` API。
- 评估将常见可静态表达的动画 timeline 下沉到 native。
- JS 只声明 target / duration / easing，native FrameClock 负责逐帧计算 current value。
- 对无法 native lowering 的复杂 JS target 保留 JS RAF fallback，并通过 diagnostics 标注 backend。

## 2. prop dirty 粒度过粗，paint-only 更新可能触发布局

当前普通 `SetPropMutation` 基本会同时标记 layout 与 paint dirty。这样会导致一些本应 paint-only 的变化触发 measure / layout，例如：

- `textStyle.color`
- `Icon.tint`
- background color
- alpha
- border color

动画场景中这类问题会被每帧放大，尤其颜色动画和视觉状态动画。

初步方向：

- `PropSchema` 不只负责 validate，也应提供 dirty classification。
- dirty 需要细到字段级：
  - `fontSize` / `lineHeight` / `text`：layout + paint。
  - `color` / `tint` / `background` / `alpha`：paint only。
  - `source`：resource + paint。
  - event callback：event only。
- prop dirty 精度应向当前 Modifier diff 的水平靠拢。

## 3. 一帧内存在重复 pump / 补 pump 路径

当前 `FramePumpDriver::pumpFrame()` 中可能先调用一次 `runtime.pumpFrame(...)`，当 diagnostics 变化后又补一次 `runtime.pumpFrame(...)`。同时 `EditorSceneHost::pumpFrame()` 外层也存在 diagnostics prepare / publish / enqueue intent 逻辑。

这说明 frame 阶段仍不够统一，存在 pipeline 后又反向 enqueue intent、下一轮或本轮再 pump 的风险。

初步方向：

- 一个 host tick 内应有明确阶段：

```txt
drain external/native events
-> JS composition
-> reduce runtime / diagnostics / resource state
-> produce one FramePlan
-> run one SceneFramePipeline
-> publish
-> request repaint
```

- diagnostics / resource 不应在 pipeline 后随手 enqueue 反向触发新 pipeline，除非明确进入下一帧。
- 补 pump 可以作为显式 fallback，但需要可观测、可计数、可解释，不能成为常态。

## 4. 每帧更新窗口标题 / 宿主 chrome

当前 timer tick 中会调用 `updateWindowTitle()`，动画期间可能每帧执行：

```txt
setName
peer->setTitle
topLevel->setName
topLevel peer->setTitle
```

这类宿主 chrome 操作不属于 frame rendering 主链路，Debug 下可能带来明显额外开销或帧间距抖动。

初步方向：

- window title 只在状态变化时更新，例如 live/dist 切换、loaded/error 切换、diagnostics badge/source 状态变化。
- 建立 chrome state diff，避免每帧盲 set。

## 5. partial repaint 还不彻底，paint 仍遍历全 DrawOps

当前 repaint adapter 会计算 repaint bounds，但实际 paint 时仍可能对完整 DrawOps 列表进行遍历。小 demo 问题不明显，但大树、Canvas、Lazy 与动画场景下会成为瓶颈。

初步方向：

- painter 读取当前 clip / repaint bounds，跳过不相交 DrawOps。
- `PublishedFrame` 明确区分 full repaint 与 partial repaint。
- 大树后考虑 display list 分块或 spatial index。

## 6. diagnostics / resource 准备混入主帧路径

Debug 下 badge、toast、错误屏均启用。当前 diagnostics 既维护状态，又构建 DrawOps，又可能 enqueue diagnostics intent。resource prepare 也可能在 frame pump 后继续产生 intent。

风险链路类似：

```txt
diagnostics tick
-> emit
-> enqueue intent
-> prepare diagnostics frame
-> publish diagnostics drawops
-> enqueue diagnostics intent again
```

这会让 Debug 帧耗时更不稳定。

初步方向：

- `DiagnosticsScene` 保持独立，但生命周期纳入统一 FramePlan。
- diagnostics state change 应一次性进入 invalidation。
- build diagnostics 应是 pipeline 阶段，不应在外部重复 prepare / publish。
- resource prepare 的状态变化也应进入统一 state / invalidation / FramePlan。

## 7. 调度频率策略过于硬编码

当前存在明显的 `60 / 20` 调度频率策略。问题包括：

- 60Hz 不等于真实显示刷新率。
- 20Hz 维护 tick 与动画 / diagnostics 切换可能造成节奏跳变。
- vblank 与 timer fallback 的状态机较粗，可能出现 start / stop 或 demand 切换抖动。

初步方向：

- FrameClock 记录真实 tick delta。
- 使用 vblank 时跟随 vblank。
- fallback timer 可配置，并避免频繁 start / stop。
- timer demand 增加 hysteresis，避免状态抖动。

## 8. 文本 / Input / diagnostics magic number 与重复 metrics

当前输入文本 padding、默认尺寸、diagnostics 布局数值等存在多处硬编码，例如 input 文本区域相关 `16.0f`。这不是首要性能问题，但会导致：

- 布局、绘制、IME bounds、caret / selection overlay 不完全同源。
- 后续优化难以统一。
- 维护成本变高。

初步方向：

- 收束为 `InputMetrics` / `TextFieldMetrics` 等共享模型。
- Layout、Paint、TextInputLayoutModel 共用同一套 metrics。

## 当前性能贡献度初步排序

1. 动画每帧穿越 JS / Vue / native 全链路。
2. prop dirty 粒度过粗，paint-only 更新可能触发布局。
3. 一帧内重复 pump / pipeline 后反向 enqueue。
4. 每帧更新窗口标题 / 宿主 chrome。
5. partial repaint 不彻底，paint 仍遍历全 DrawOps。
6. diagnostics / resource 准备混入主帧路径。
7. 调度频率策略硬编码。
8. 文本 / Input / diagnostics magic number 与重复 metrics。

# 新思想

## Arrange Vue：面向阶段化 UI runtime 的响应式改造

后 M1 的核心路线应从“修补当前 custom renderer 链路”升级为“建设 Arrange Vue”。Arrange Vue 不是单纯把 Vue 渲染到 native，也不是在现有 Vue renderer 外侧追加更多适配层；它是面向 Arrange host target 的 authoring、composition 与 scheduling 前端。

长期定位：

```txt
Arrange = Vue-like authoring experience
        + Compose-like phase-aware UI runtime
        + JUCE-native execution layer
```

Arrange 选择 Vue，是因为它提供了很好的 UI 语言资产：SFC、template、`<script setup>`、`ref` / `computed` / `watch`、组件组织、Vite HMR 与开发期体验。后续动刀 Vue compiler / runtime 的目标，不是抛弃这些资产，而是让它们服务 Arrange 自己的阶段化 UI runtime。

核心判断：

```txt
Ref 本身不是问题。
问题是把所有 Ref 变化都统一解释为 Composition 变化。
```

当前普通 render 链路容易把 UI 值变化导向：

```txt
ref changed
-> component render effect
-> VNode create / diff
-> generic prop patch
-> native mutation
-> dirty 推断
-> layout / draw
```

这会让动画、颜色、尺寸、透明度等 UI 值的高频变化点燃过多无关阶段。Arrange Vue 的目标是让状态变化按它实际参与的 UI 阶段精确失效。

## 阶段化响应式

Arrange Vue 需要建立 phase-aware reactivity。状态变化不应只有“触发组件重 render”这一种结果，而应依据其读取、绑定和消费位置进入不同失效域：

```txt
业务 / 结构状态      -> Composition dirty
尺寸 / 约束 / 度量    -> Layout dirty
颜色 / alpha / tint  -> Draw / Paint dirty
事件回调             -> Event slot update
资源状态             -> Resource / Draw dirty
```

一句话：

```txt
Ref 的绑定位置决定它的失效阶段。
```

例如，同样是 `Ref`：

```txt
v-if / v-for / dynamic component 中读取 -> 结构 composition
width / padding / fontSize 中绑定       -> layout slot
background / color / alpha 中绑定       -> draw slot
clickable / input callback 中绑定       -> event slot
```

这使 `Ref` 继续保持统一的 authoring 心智，但 runtime 不再把所有变化都粗暴导向同一条 composition / VNode diff 链路。

## Reactive Slot Runtime

Arrange Vue 的关键运行时形态可以暂命名为：

```txt
Arrange Reactive Slot Runtime
```

核心链路：

```txt
Ref / computed / animatedXAsRef
-> typed UI slot binding
-> JS value phase flush
-> dirty slot batch
-> native FramePlan
-> LayoutTree / JUCE repaint
```

模板中的 UI 值绑定应逐步从普通动态 prop 变成 typed slot binding。例如：

```vue
<Box :background="bg" :width="w" />
```

长期目标不是每次 `bg` / `w` 变化都重新 render component、创建 VNode、diff props、调用 generic `patchProp`，而是建立明确绑定：

```txt
bg -> node.background -> Draw/Paint slot
w  -> node.width      -> Layout slot
```

于是动画帧可以走：

```txt
animatedColorAsRef tick
-> bg.value 更新
-> background paint slot dirty
-> typed paint update batch
-> native draw dirty / repaint
```

而不是：

```txt
animatedColorAsRef tick
-> component render
-> VNode diff
-> generic prop patch
-> native mutation
-> 粗 dirty
```

因此，动画值、transition 状态和 easing / spring 计算不必天然迁出 JS。真正重要的是：高频 UI 值变化必须进入精确 slot 与阶段化调度，而不是穿越通用 composition 链路。

## Arrange compiler / runtime 的演进方向

### 1. Arrange host target lowering

Arrange compiler 应以 Arrange host target 为目标，认识 Arrange host components、Modifier、typed prop、theme 与 reactive slot。

目标：

```txt
template
-> Arrange host component lowering
-> typed prop / modifier / event / text / slot op
-> runtime 可建立阶段化 dependency
```

这意味着 `Box` / `Row` / `Column` / `Text` / `Input` / `Canvas` 等组件不应长期只作为普通 component / VNode 处理，而应逐步获得专门 lowering 与 prop schema。

### 2. 特化 runtime / renderer

当前 custom renderer 的 host op 是必要的 M1 基础，但后续应减少 generic `patchProp` 与普通 object prop diff 的中心地位。

目标：

```txt
typed prop op
modifier op
event slot op
text op
resource op
reactive slot op
```

UI 值变化可直接进入对应 slot update，普通 component render 只负责真正的结构和语义变化。

### 3. 阶段化 scheduler

调度应明确拆分并统一进 FramePlan：

```txt
Composition Phase
JS Value Phase
Native Render Phase
```

其中：

- Composition Phase 处理组件结构、条件分支、列表、slots、普通业务状态造成的界面结构变化。
- JS Value Phase 处理动画、transition、computed UI value 与 dirty slot batch。
- Native Render Phase 消费 typed mutations / slot updates，执行 apply、dirty resolution、measure / layout / draw preparation / publish。

### 4. 阶段化 reactivity

在保留 `Ref` / `computed` / `watch` authoring 心智的前提下，runtime 需要区分：

```txt
composition dependency
layout slot dependency
draw slot dependency
event slot dependency
resource dependency
```

业务层 `watch` / `computed` / Pinia 等语义继续服务 semantic state；UI slot dependency 服务 Arrange 的 layout / draw / event / resource 阶段。

### 5. 远期 Arrange Composition Runtime

若 Vue runtime-core 的通用模型最终成为束缚，Arrange 可以继续演进为自研 composition runtime。`.vue`、`<script setup>`、template 与类似 Composition API 的 authoring 体验可以保留，但底层不必永久依赖标准 Vue runtime。

## JS / native 分工

长期分工应改写为：

```txt
JS / Arrange Vue layer:
  - SFC / template / script setup
  - ref / computed / watch / component lifecycle
  - 业务状态与结构 composition
  - 动画与 transition 语义
  - typed UI slot 调度
  - HMR 与开发期 authoring runtime

Native / C++ / JUCE layer:
  - LayoutTree / LayoutNode
  - LayoutEngine / measurement / placement
  - Text shaping / measurement / editing integration
  - DrawOps / repaint bounds
  - HitTest / input dispatch / focus
  - resource decode / platform integration
  - JUCE Component / plugin host lifecycle
  - FramePlan 中真正的 layout / draw / publish
```

JS 与 native 之间不应是互相防备的割裂边界，而应在统一 FramePlan 下分工协作。JS 可以承担更适合语言层和开发体验的 runtime 智能；native 专注真正贴近 JUCE、平台和 UI 执行层的重工作。

## 铁律

为避免退回旧链路，必须确立以下原则：

```txt
动画过程值变化不得默认触发 component render。
UI prop ref 的高频变化不得默认走 VNode diff。
paint-only 值变化不得触发布局。
layout 值变化必须只进入必要 layout dirty。
typed slot update 与 native apply / layout / draw 必须由统一 FramePlan 消费。
Arrange host target 是 compiler / runtime 的正向目标；其它宿主目标的语义没有默认 lowering。
```

## 对里程碑的影响

M1 已经打通：

```txt
Vue SFC -> QuickJS -> custom renderer -> native transaction -> LayoutTree -> JUCE paint
```

这是必要的历史阶段，证明 Arrange 可以跑通从 authoring 到 native paint 的完整链路。但后 M1 的主轴应升级为：

```txt
Arrange Vue
-> Phase-aware Arrange Reactivity
-> Reactive Slot Runtime
-> Unified FramePlan
```

这可能要求重写后续里程碑。新的最高原则是：**让 Ref、template、scheduler、typed slot 与 native FramePlan 有机统一，让 UI 值变化按实际参与阶段精确失效。**
