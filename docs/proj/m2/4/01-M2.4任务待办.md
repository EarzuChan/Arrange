# M2.4：确立 Arrangable、模板与原生节点的明确边界

更新日期：2026-09-19。状态：本轮公开行为与能力取舍已拍板，待实施；本文不代表任何实现已完成。

本期从小到大收紧模板、参数、内容与节点执行的关系：Arrange 就是 Arrange，不保留含糊的 Vue/Web 兼容状态。Arrangable 就是此前所谓的“组件”，不再存在与它并列或分离的组件概念；单文件形式正式称为 SFA（Single-File Arrangable，取代 SFC 的概念称谓），文件扩展名正式使用 `.sfa`，替换 `.vue`。Arrangable 接收明确声明的参数与内容，参与组合和重排（Rearrange）；实际布局、绘制和交互由明确的原生 LayoutNode 承担。此前讨论中的“重组”在 Arrange 语义下统一称为“重排”。

本文是本期施工目标与验收清单，不是另一份长期 API 规范。下文记录主人的最终口径，内部类型名、节点构造函数等实现设计不另冒充待拍板的产品选择。实施时须同步对应母文档（本M2.4是最新设计，实现后应更新母文档），不能把旧母文档中的透传、emits、v-model 等现状当作继续保留它们的理由，也不能仅凭本文就宣称源码已经迁移。

以下目标示例表示施工要求，不代表当前已可用；内部职责示意不冻结具体函数签名。

## 施工原则与已有基础

- 允许 breaking change 和施工过程中的编译失败（途中编译不过不是很正常的事情吗？不刮骨疗丢怎么肃清？）；最终交付必须完成生产链路、Demo、类型、测试和文档的迁移，代码必须干净，不得搞什么兼容层或者双轨制偷偷维护被废除的语义
- 测试验证新契约；删除或改写仅保护旧语义的断言，不为旧测试倒退实现
- 没有 Web 能力的解释与执行基础即自然无法处理 Web，无需建立一套 Web 黑名单门禁；检查的是 Arrange 自身正向契约
- 延续代码规范：自然语言文案、报错、日志和注释使用中文，注释行末不带句号；本来单行能放下的表达式不任意折行，逻辑组间留空行；TS 默认无分号，TS/CPP 缩进 4 空格

当前已有的美好物质基础必须被准确识别，而非一律推倒后重新发明。但的确，我们要清算很多：

| 已有机制 | 本期应如何对待 |
| --- | --- |
| VNode、JS 宿主节点账本、C++ ArrangeNode 已分离 | 明确职责与正式命名，将有效职责迁入正式类型，不混用 Arrangable、RearrangeNode、ArrangableInstance 与 LayoutNode |
| 模板动态输入延后求值，结构 effect 与 ValueBinding 按实际读取订阅 | 保住结构和值更新的分离，不退回值一变就整层重排 |
| JS Modifier 描述、原生 ModifierInstance、协调与退休 | 保住实例身份、独立状态、顺序语义和精确更新 |
| 结构操作与 SlotUpdate 有序提交，候选 scene/帧成功后发布 | 新节点应用入口继续接入统一提交和发布边界 |
| VBlank 帧泵、分阶段失效、布局及绘制结果复用 | 不因上层正规化而另开帧源或直接驱动绘制 |

# 第一趴

## 1．从模板字面量开始，停止自动造内容和自动转换

### 1.1 裸文本、插值与源码空白

现有反例：

```vue
<Row>恩情</Row>
<Text>恩情</Text>
<Row>{{ { a: 1 } }}</Row>
<Row><Spacer/> <Spacer/></Row>
```

已观察到的后果：裸文本变成原生 Text；Text 子内容被写入文本；对象插值被格式化为 JSON 后显示；最后一例的空格生成第三个子节点，而换行版本只有两个。

- [ ] 模板内容位置不支持裸字符串与 `{{插值}}`，有意义的文本内容直接报错
- [ ] 标签之间的纯排版空白统一忽略，空格、换行和缩进不得改变节点数与布局间隔
- [ ] 显示文本必须经过显式 Text 的 `text` 参数；`<Text :text="title" />` 合法，`<Text :text="({ a: 1 })" />` 应因类型不合而失败
- [ ] 彻底删除对象到显示字符串、任意值到文本节点等旧垃圾路径，不能只禁止一种模板写法而保留另一条等价旁路
- [ ] 内部结构锚点与可见 Text 分开，不再借文本创建入口表达锚点

### 1.2 参数写法只表达确定的值

**已定：**拒绝 Boolean casting、根据目标类型猜值、未声明默认值却补值，以及类型错误仅警告后继续执行。

**已拍板：**三种写法全部允许，且只具有以下含义。带冒号的绑定必须显式给定表达式，不支持同名自动补全。

| 写法 | 唯一含义 |
| --- | --- |
| `title="abcd"` | 固定字符串表达式，值为 `"abcd"`，不解释为 JS |
| `enabled` | 固定布尔表达式，值为 `true` |
| `:amount="expression"` | JS 表达式的反应式求值结果，常量表达式同样允许 |
| `:xx` | 非法，即使当前作用域存在同名 Ref xx，也不得补成 `:xx="xx"` |

绑定语法保留明确的同族写法，不因允许别名而恢复其他 Vue 协议：

| 写法 | 含义与边界 |
| --- | --- |
| `:amount="value"`、`v-bind:amount="value"` | 等价的显式表达式绑定，两种写法都必须提供表达式 |
| `:[propName]="value"`、`v-bind:[propName]="value"` | 动态求出参数名，归一后仍须匹配目标声明；不允许借动态名字传入未声明参数 |
| `v-bind="params"` | 将对象字段作为本次调用的参数，逐项遵守名称、类型和重复检查，不表示向内部透传 |
| `:some-value.camel="value"`、`:[propName].camel="value"` | 显式 camelize 参数名，不转换参数值；长写 v-bind 同样适用 |

**参数名称规则：**保留 Vue 的 camelize 规则，声明名和传入名均归一后匹配。因此声明 `someValue` 或 `some-value` 都归一为 `someValue`，调用方的两种拼写也匹配同一参数。沿用 Vue camelize 的确定转换算法，不扩大为大小写忽略、全小写猜测、下划线兼容或模糊匹配。此规则只适用于 prop 名称，不扩展到 Arrangable 标签或槽位名。

反例及目标结果：假设 Xxx 明确声明 `flag: boolean`、`amount: number`。

| 调用 | 旧现象或问题 | 本期要求 |
| --- | --- | --- |
| `<Xxx flag="" />` | 空字符串被转成 true | 固定空字符串因 string 不符合 boolean 而失败 |
| `<Xxx flag="flag" />` | 同名字符串被转成 true | 同上，不允许同名特例 |
| `<Xxx flag="false" />` | 警告后传入 truthy 字符串 | 报错，不执行布尔转换 |
| `<Xxx amount="12" />` | 字符串与数字边界易混淆 | 保持 string；要求 number 时失败 |
| `<Xxx />` | Boolean prop 没有 default 仍补 false | 只应用显式默认值，否则保持未传或报告必需参数缺失 |

- [ ] 实现三种确定的参数写法，删除 `:xx` 同名绑定简写；检查引号、转义和重复参数处理，移除沿袭上游但没有 Arrange 定义的转换
- [ ] 普通模板绑定继续支持 Ref 解包并反应式求值；显式原样绑定允许传递 Ref 本体，语法、声明与依赖语义见 1.3，不依据目标类型偷偷切换解包方式
- [ ] 标签统一 PascalCase，按定义的准确名称解析，不兼容 `keep-alive` → `KeepAlive`；prop 声明与传入统一 camelize，Foundation、用户 Arrangable、静态属性、绑定及参数对象采用同一规则
- [ ] 保留 v-bind／冒号、动态参数名、对象参数绑定和 `.camel`；不继承 `.prop`、`.attr`、`.sync` 等其他修饰符，不保留无表达式绑定或无效动态名字自动补空字符串等宽松处理
- [ ] 同一声明中两个名称归一后冲突，在定义阶段报错；同一次调用中第二次传入同一归一参数立即报错，不覆盖、不合并回调、不按源码先后选胜者
- [ ] 静态可确定的重复在编译时报告；动态参数名和对象绑定在参数组装边界一旦确定重复即拒绝，不先执行目标逻辑再报错；参数对象内部已经完成的普通 JS 求值遵守 JS 语义，不追溯对象构造前的覆盖过程
- [ ] 动态表达式值变化后同样遵守类型契约，不能仅检查初始值

例如 `<Xxx :someValue="a" :some-value="b" />`、`<Xxx :count="a" v-bind:count="b" />` 均报重复参数；`<Xxx v-bind="params" :count="count" />` 在 params 含归一后同名字段时同样报错。DynamicArrangable 的 props 参数对象进入目标调用边界时也采用同一名称及冲突规则。

### 1.3 显式原样传递 Ref 本体

**已拍板：**允许通过已声明的 prop 显式传递 Ref 本体，用于共享可写状态、交付只读响应式状态，或将状态容器交给下层逻辑。这里的“原样传递”只表示保留参数值及 Ref 身份，不是什么 attrs fallthrough 的复活（更不是什么自动把参数传给接收方内部的其他 Arrangable）。

调用方在绑定表达式外层使用尖括号标记（这是主人发明的新写法）：

```vue
<Editor :oriRef="<documentRef>" />
```

等价的长写为 `v-bind:oriRef="<documentRef>"`。尖括号是 SFA 模板编译语法，不是 JS 运算符、字符串值或类型断言；SFA 编译器识别完整外层标记，再按 TS 表达式处理内部内容，生成保留 Ref 本体的取值入口，不注入通常的 `.value`／unref 解包。绑定仍须显式给定表达式，不恢复同名简写。

接收方使用类型式 prop 声明，Something 为业务类型：

```ts
import type { Ref } from '@arrange/framework'

const props = defineProps<{
    oriRef: Ref<Something>
}>()
```

`Ref<Something>` 是 TS 类型。普通 TS 中读取 `props.oriRef` 得到原 Ref，读取 `props.oriRef.value` 才消费其中的值；可写 Ref 允许通过 `props.oriRef.value = nextValue` 写入，但不允许给 `props.oriRef` 重新赋值。只读状态须采用只读 Ref 契约，不因传参获得写权限。

- [ ] 原样标记只作用于完整绑定表达式的外层；明确其与比较运算、泛型调用和 TS 类型语法的解析边界，保留源码位置，不以简单替换尖括号处理所有表达式
- [ ] 原样模式禁止编译器自动解包，仍遵守内部表达式的正常 JS 求值；显式 `.value`、运算、函数调用或代理本身的取值语义不被撤销，不自动重建已经丢失的 Ref
- [ ] 原样绑定仍是反应式求值，不等于首次取值后永久冻结；若选择表达式的依赖改变并返回另一个 Ref，按新身份更新参数
- [ ] 仅传递 Ref 本体不读取其 `.value`，同一 Ref 的 value 变化不会仅因这次传参而触发参数替换或结构重排；接收方实际读取 `.value` 的消费者正常订阅，结构读取可触发重排，值绑定读取只唤醒对应值消费者
- [ ] 编译产物、prop 存储与传递链完整保留 Ref 身份，不使用普通模板实例代理的解包结果代替本体；继续向内部传递时也必须显式声明和调用，不自动透传
- [ ] 冒号与 v-bind 长写、动态参数名及 `.camel` 使用一致的原样值语义；名称转换不影响参数值，参数对象和 DynamicArrangable 目标参数入口不得再次悄悄解包其中显式保留的 Ref
- [ ] SFA 编译器识别类型式 Ref 声明，形成与运行时入口一致的 Ref 契约；最终表达式结果不符合声明时拒绝，不能仅靠 TS 类型就宣称运行时已支持，也不假装完整验证任意泛型业务类型
- [ ] 明确只读 Ref 与可写 Ref 的类型及运行时可识别约束，不能仅凭 isRef 就视为可写；不克隆状态容器，不建立隐式双向绑定协议或恢复 v-model

### 1.4 唯一的 SFA 文件与脚本模式

**已拍板：**单文件 Arrangable 只使用 `.sfa` 扩展名。文件中的 `<script>` 唯一表示 TS setup，不再要求或接受 setup、lang 属性，不保留普通模块 script 与 setup script 两套模式（默认/开箱即用即是setup体，不再有options体（应移除全部Options API相关）），不保留独立 JS 脚本模式（script体内直接/只能写ts）。Arrange IDE 插件暂不建设，也不作为 M2.4 的交付前提。

正式文件形态，例如 Counter.sfa：

```html
<template>
    <Text :text="String(count)" />
</template>

<script>
import { ref } from '@arrange/framework'

const count = ref(0)
</script>
```

主人注：先写template块再写script块，是不言而喻的约定俗成/默契；在模板内，同级模板节点之间留出空行，也是香香软软的美好实践。

- [ ] SFA 最多一个 script 块，无逻辑时可省略；存在时统一按 TS setup 编译，顶层绑定供模板使用，局部状态及初始化逻辑按 Arrangable 实例执行，重排不重新执行初始化
- [ ] import 保持模块语义；模块级共享状态、导出及工具逻辑放入独立 `.ts` 模块，不在 SFA 中恢复第二个模块脚本或手写 default export Arrangable 配置入口
- [ ] 删除 `<script setup>`、`lang="ts"`、`lang="js"` 及普通 script/setup 双块路径，不保留冗余属性兼容别名或按属性切换行为的分支；JSX/TSX 等其他脚本模式同样不开放
- [ ] 未写类型标注的常规代码仍按 TS 解析与推断，不强迫每个局部变量加类型；类型式 defineProps 等宏及模板表达式统一按 TS 处理，脚本转译成功不等于类型检查通过
- [ ] 正式源文件、Demo、测试 fixture、脚手架、导入语句及示例迁移为 `.sfa`；Arrange 构建入口停止把 `.vue` 当作 Arrangable 源文件，不保留双扩展名加载或自动回退
- [ ] 同步文件发现、模块解析、Vite/构建转换、依赖追踪、HMR、源码映射、诊断文件名及类型检查入口，保证真实 `.sfa` 文件可从源码编译到原生运行；类型支持须保留定义与 prop 契约，不用通配 any 声明冒充完成
- [ ] 不依赖 Vue 官方 IDE 插件识别或正确解释 Arrange 专属语法，不把 `.sfa` 自动关联回 Vue 来声称兼容；本期保证编译与命令行诊断链路，不承诺专用补全、跳转或其他 IDE 插件功能

## 2．Arrangable 是参数边界，Modifier 和回调也必须声明

### 2.1 **严肃彻底**删除模板节点透传机制，而非默认关闭透传

当前反例：Xxx 未声明 props，内部仅返回带 `text="内部"` 和 `M.padding(8)` 的 Text，外部调用：

```vue
<Xxx text="abcd" :modifier="M.width(99)" />
```

实测内部文本被覆盖为 `abcd`，Modifier 只剩 width，且没有警告。

- [ ] 正式统一 Arrangable 与 SFA 术语，定义、类型、诊断、工具链和公开文档不再设立另一套“组件”概念；具体 API 与工具内部符号重命名清单在实施前列明，文件扩展名和脚本模式按 1.4 正式迁移
- [ ] 只能传入目标 Arrangable 明确声明的 prop（且不透传到目标Arrangable内的任何模板节点，而是在目标Arrangable定义脚本内从Props取用（另：目标Arrangable模板直接拿Prop名取用不变）），未声明即报错，不忽略、不收集后转交内部
- [ ] 删除 attrs fallthrough、inheritAttrs 开关及等价旁路；内部零根、单根、多根都不改变参数边界
- [ ] Modifier 是普通的、需要精确声明的 prop，不因名称为 modifier 就获得系统待遇
- [ ] prop 的默认值、必需性与校验来自声明，不能按命名或内外部标签形状推断
- [ ] 正式声明直接参与编译优化：已知 Arrangable 定义时预先确定参数位置、默认值处理及内容调用入口，减少运行时名称解析与临时参数对象组装；动态定义仍在真实边界校验，静态与动态调用遵守同一契约，不改变默认值求值时机

对 `<Mamba :modifier="externalModifier" />` 的验收要求：

| Mamba 的实现 | 结果 |
| --- | --- |
| 未声明 modifier | 报错 |
| 声明但未使用 | 不产生视觉效果，框架不替它应用 |
| 显式传给内部一个受体 | 仅作用于该受体 |
| 显式传给多个受体 | 各受体分别物化实例与状态 |
| 没有产生 Node | 不凭空生成承挂 Modifier 的盒子 |

### 2.2 坚决删除模板节点上的 Dom Element ref 与事件、双向绑定协议

以下为退出公共写法的例子：

```vue
<Box ref="box" />

<Xxx @submit="submit" />

<Input v-model="name" />
```

第一个不能再用来取得宿主元素或 Arrangable 实例；第二个不再经过 emit、监听器识别、命名变换与合并；第三个不再隐式展开为 modelValue 与 update 事件。

- [ ] 移除模板特殊 prop `ref` 及获取 Dom Element 实例引用的相关公共能力；注意：这里不是指删除响应式系统 `ref()`
- [ ] 删除 emits、emit、`v-on`／`@xxx` 事件语法与命名约定驱动的特殊分派
- [ ] 删除 v-model、defineModel、系统 modelValue、update:modelValue、modelModifiers 及其 trim/number 等转换
- [ ] 交互通知改为明确声明的函数 prop；`onXxx` 若作为普通参数名使用，不产生自动合并、冒泡或多播
- [ ] 保留原生交互回调所必需的 typed event slot 与生命周期管理；删除的是用户层隐式协议，不是所有事件输送能力

目标形态示例，具体参数名随正式定义落定：

```vue
<Input :value="name" :onValueChange="value => name = value" />

<Mamba :onConfirm="confirm" />
```

旧清单中一次 submit 导致 count 从 0 变为 2 的反例，须迁移为单一明确调用路径。需要两个回调时由实现显式调用，不按参数名称暗中合并。

`modelValue`、`style` 等单词不建立黑名单；去除系统特权后，用户自行声明的同名普通 prop 不自动拥有任何 Vue/Web 能力。

## 3．保留控制流，明确内容入口与 Slot

### 3.1 控制流属于组合语言

- [ ] 保留 v-if、v-else-if、v-else、v-for，用于声明结构分支与列表
- [ ] 正式保留显式组合 key，用于重排中的身份判定与复用；它是组合控制信息，不进入 Arrangable 的业务 props，也不自动转发
- [ ] 组合 key 与 Modifier key 分开：前者协调 Arrangable 调用或内容身份，后者协调同一受体的 Modifier 层，二者均不等于原生运行时 handle
- [ ] 删除 v-html、v-show、v-pre、v-once、v-memo 及其专有解释、转换、运行时依赖，不保留空实现或兼容别名；删除 v-pre 的解析旁路，不让它绕开模板契约
- [ ] 删除用户手动冻结描述或填写 memo 依赖表的协议，不删除编译器对确定静态部分的自动缓存，也不影响组合 key 的身份语义
- [ ] 模板语法采用封闭集合：保留本节控制流、1.2 的参数绑定家族、3.2 的内容语法及明确组合 key；未列入的指令、修饰符和扩展机制没有解释与执行入口，不默认继承 Vue 能力
- [ ] 审计并删除其余上游指令和编译语法残留，审计待办不表示此前默认允许；名称别名仅保留本文明确的范围

### 3.2 接受内容必须有声明

现有反例：

```vue
<Input>
    <Text text="子节点" />
</Input>
```

旧链路允许提交 Input → Text 父子关系，却没有相应内容契约；这不等于它拥有正确布局行为。

- [ ] Arrangable 未声明 Slot 时，外部不得强塞子内容
- [ ] 用户 Arrangable 在实现模板中通过 `<Slot />` 显式声明并调用默认内容，通过 `<Slot name="header" />` 显式声明并调用具名内容，不额外要求 defineSlots 声明
- [ ] `<Slot />` 只是模板中的槽位代称与内容入口，不是运行时 Arrangable；被提供的内容相当于无参数的 `@Composable () -> Unit`，由接收者明确决定是否调用、在哪里调用，不在外层提前生成一包节点再隐式搬运
- [ ] 运行时执行的是填入的 Arrangable 内容，不创建 Slot 包装实例或原生节点；内部可保留内容调用、依赖与生命周期管理机制，但不能将这些机制实体化为 Slot Arrangable，槽位语法不接受业务 prop 或 Modifier
- [ ] 内容内部可以有零个、一个或多个 Arrangable，Slot 使用方无需也不能依赖其数量或窥探内部结构；不保留 scoped slot 的出口传参和外部解构协议
- [ ] `name="header"` 是静态槽位选择语法，由编译器解析，不是 Slot 的运行时 prop；不接受 `:name="expression"`、`:modifier` 或其他业务参数
- [ ] 提供具名内容允许等价的 `<Template v-slot:header>...</Template>` 与 `<Template #header>...</Template>`，其他静态槽位名同理；默认内容可用 default 名显式选择，保留同族写法不恢复动态槽位名、scoped slot 参数或修饰符
- [ ] Template 不产生布局节点，不为这个分组凭空增加运行时包装实例；槽位名按声明准确匹配，不随 prop 一起 camelize
- [ ] 已声明的默认或具名 Slot 未被提供时，使用默认空 Arrangable（default empty Arrangable）的空内容语义；合法调用且不产生实际 Arrangable 实例或原生节点，不报必需内容缺失
- [ ] Foundation Arrangable 与用户 Arrangable 使用一致的内容契约，不能拥有暗中接受任意 children 的特权
- [ ] 明确同一内容多次调用时的实例独立性、词法变量来源、响应式订阅及生命周期归属
- [ ] 内容调用建立独立的 RearrangeScope，明确提供方词法环境与调用方生命周期归属；内容内部依赖变化只唤醒实际消费者，不无故唤醒提供方或无关外层结构
- [ ] 复用可证明安全的内容描述与调用入口，减少重复分配；同一份内容多次调用的状态和订阅仍独立，词法输入变化时刷新，不能冻结提供方变量或通过窥探孩子数量优化，不产生 Slot ArrangableInstance

提供方的正式形态：

```vue
<Containable>
    <Template v-slot:header>
        <Text text="标题" />
    </Template>
    
    <Something :xx="x" />
    
    <Something2 />
</Containable>
```

Containable 的实现模板在自己的布局中显式使用：

```vue
<Column>
    <Slot name="header" />
    
    <Slot />
</Column>
```

默认内容整体作为无参数内容提供给默认槽位。`xx` 是 Something 的 prop，`x` 来自提供方词法作用域，均不是槽位参数。上例运行时执行 Column、Text、Something 和 Something2 等实际 Arrangable，不存在额外的 Slot 实例；内容产生的实际 LayoutNode 接入调用位置的原生父节点。同一份内容在不同位置调用时，其内部 Arrangable 分别具有独立实例和身份。未声明的槽位仍不能强塞，不能将“已声明但未提供时为空”误解为接受任意内容。

## 4．Foundation Arrangable 必须有自己的明确实现

当前 `components.ts` 里的字符串加类型断言、宿主 schema 特判和 Icon 读取 attrs 的方式全部退出。M2.4 正式规定：**所有内建 Foundation Arrangable 均由 Arrange 内部 TS 代码定义，不在内部包使用 `.sfa` 定义 FA。** 用户 SFA 与内建 FA 都遵守相同的 prop、Slot、getter、Modifier 和生命周期契约；代码定义只拥有实现 Layout、资源和原生能力所必需的正式内部入口，不拥有隐式参数或节点特权。

### 4.1 内建 FA 的代码定义与完整契约

- [ ] 为 Box、Row、Column、Spacer、Text、Input、Image、Icon、Layout，以及 KeepAlive、DynamicArrangable 建立各自可定位的代码定义；不建立“内部 FA 用 `.sfa`、用户 FA 用代码”的第二条定义路线
- [ ] 每个 FA 明确声明 prop、类型、默认值、必需性、默认/具名 Slot、是否创建 LayoutNode、使用的 Layout/MeasurePolicy、Modifier 受体、内部能力、生命周期与错误边界；定义、TS 类型、编译检查和运行时检查共享同一契约来源
- [ ] FA 的第一方行为在自身实现中显式写出：接收 props 和内容，调用明确的 Layout 或其他已定义 FA，选择策略，组合并物化 Modifier，提交结构和值操作；禁止 renderer、原生引擎或标签名暗中替 FA 完成这些行为
- [ ] FA 不因名称自动获得 children、modifier、style、事件、资源或布局盒子；没有声明和实现就没有对应能力，内部零根、单根、多根不改变边界
- [ ] 代码定义使用正式的 `defineFoundationArrangable` 内部协议；该协议不是用户公共 API，但其声明和调用结果必须可被编译器、运行时、诊断和测试追踪
- [ ] 空 Modifier 起点正式命名为大写 `M`，例如 `M.padding(8)`；`m` 及其导出、类型声明、编译器识别和文档示例全部退出，Modifier 类型名仍为 `Modifier`

用户看到的目标形态：

```sfa
<Box :modifier="panelModifier">
    <Text text="野兽先辈" :style="titleStyle" />
</Box>
```

### 4.2 Layout 是公开 FA，也是 LayoutNode 的明确入口

Layout 正式作为可在 SFA 中使用的 Foundation Arrangable，声明 `measurePolicy`、`modifier` 和默认内容入口。它不是原生引擎看到某个名称后自动套用的黑箱，也不是只能由 FA 内部调用的隐藏能力。

```sfa
<Layout :measurePolicy="policy" :modifier="M.padding(8)">
    <Something />
</Layout>
```

其固定物化链路为：

```text
Layout 调用
-> 产生对应 RearrangeNode
-> Rearrange 按调用身份创建、复用或退休 LayoutNode
-> 将 measurePolicy、Modifier 和内容关系写入正式结构操作
-> 在原生事务中物化 Modifier 受体与 LayoutNode 状态
-> 在测量、放置、绘制、命中阶段消费 LayoutNode
```

- [ ] Layout 明确声明并校验 `measurePolicy`、`modifier`、默认内容；调用方不取得 Layout 或 LayoutNode 实例
- [ ] Layout 的一个调用对应可追踪的 RearrangeNode 和 LayoutNode 关联；RearrangeScope 管理结构执行，LayoutNode 管理原生布局实体，三者不合并
- [ ] Layout 将 Modifier 交给明确的 LayoutNode 受体，外部 Modifier 与内部能力的顺序在 FA 实现中写明；不凭空创建盒子承接未声明 Modifier
- [ ] LayoutNode 的创建、更新、插入、移动、移除、退休和代际校验使用正式内部接口；不通过 `switch (Arrangable 名称)` 选择布局或绘制行为

### 4.3 MeasurePolicy 独立于 FA

MeasurePolicy 是独立的布局算法值，表达“如何测量和放置”，不表达“属于哪个 FA”。一个 FA 可以选择一个或多个 Policy；同一 Policy 也可以服务多个 FA 或用户直接调用的 Layout。Policy 不按 FA 名称自动选择。

本期正式预制以下策略：

| Policy | 使用职责 |
| --- | --- |
| `BoxMeasurePolicy` | 叠放、内容对齐和最小约束传播 |
| `RowMeasurePolicy` | 水平排列、间距、交叉轴对齐和 weight |
| `ColumnMeasurePolicy` | 垂直排列、间距、交叉轴对齐和 weight |
| `MinSizeMeasurePolicy` | 以约束最小尺寸完成布局；无内容或内容不参与自身尺寸时使用 |
| `TextMeasurePolicy` | 在文本约束、baseline、行数和 overflow 规则下取得文本测量结果并完成放置 |

`MinSizeMeasurePolicy` 的语义固定为：接收约束，返回 `layout(constraints.minWidth, constraints.minHeight, placementBlock)`；没有需要放置的子项时 `placementBlock` 为空。它是可复用的普通策略值，不因被 Spacer 或 Image 使用就获得 FA 特权。

- [ ] Policy 是独立、可校验、可追踪的输入，参数变化只使实际消费者失效；缓存是实现优化，不成为 FA 与 Policy 的隐式绑定
- [ ] Box、Row、Column 分别在代码定义中显式选择对应 Policy；Spacer 使用 `MinSizeMeasurePolicy`
- [ ] Text 使用 `Layout` 与明确的 `TextMeasurePolicy` 及文本绘制能力组合；文本测量、baseline、绘制缓存和文本输入更新有正式归属，不通过 Text 标签特判绕过 Layout 与 Modifier
- [ ] Image 使用 `Layout`、`MinSizeMeasurePolicy` 和显式 paint 能力；其尺寸和绘制受 Painter 固有尺寸、约束及 Modifier 共同影响，不为 Image 另造无语义的专属 Policy
- [ ] Icon 不提供 Icon 专属 MeasurePolicy；其代码定义显式调用 Box，并向 Box 交付 paint Modifier，着色使用显式 tint 生成 colorFilter
- [ ] 允许未来公开 JS MeasurePolicy，但必须使用同一 Layout 参数契约：在 Owner 的受控测量阶段接收约束和子项测量能力，返回 typed MeasureResult；禁止异步等待、结构修改、任意事件重入和跨线程访问
- [ ] JS MeasurePolicy 与原生 Policy 共用 Policy 语义，不提前伪造一个无法运行的 API；新增 JS 策略时只扩展 Layout/Policy 层，不重写各个 FA

### 4.4 内建 FA 正式确立必须 styleless

内建 FA 有行为但没有特征样式。禁止 FA 自带背景、边框、圆角、阴影、装饰性 padding、主题色、默认设计系统字体或输入框皮肤。字体 fallback、文本测量、光标、选区、焦点和 IME 是行为或基础呈现，不等于装饰样式。

- [ ] Text、Input、Image、Icon、Box、Row、Column、Spacer 均不偷偷注入主题装饰；Input 删除平台/设计系统默认皮肤，保留编辑、光标、选区、焦点和 IME 行为
- [ ] FA 不使用 provide/inject 取得颜色、字体风格或其他样式；不恢复 LocalContentColor、LocalTextStyle 或其他 Local 样式系统
- [ ] FA 若需要根本行为或宿主服务（例如字体解析器、资源服务），可使用正式 provide/inject；注入值不得暗中改变 FA 的视觉样式，必须在 prop 或正式行为契约中可追踪
- [ ] 未提供样式时使用明确的无样式状态，不以 FA 名称、原生节点类型或上下文偷偷补视觉默认值

### 4.5 Painter 作为 Image/Icon 的资源与绘制边界

Image 和 Icon 不再直接接收 path、URL 或资源字符串并在实现内魔法加载；二者明确声明 `painter: Painter`。资源获取、解码、异步完成、失败、取消及释放属于 Painter 获取层，Image/Icon 只消费 Painter。

```text
资源来源与加载层
-> Painter
-> paint Modifier
-> LayoutNode 的测量与绘制能力
```

Painter 是正式的绘制能力对象，至少提供固有尺寸（可无）、可绘制内容及内容版本、失效通知、资源归属和释放语义。第一版资源加载管理可以简单，但必须输出 Painter，并处理完成、失败、取消和迟到结果；以后正规化资源系统只替换 Painter 获取与实现层，不改 Image/Icon 契约。

Painter 的公开形态只表达绘制能力和生命周期，不开放任意绘制回调：

```ts
interface Painter {
    readonly intrinsicSize: Size | undefined
    readonly contentVersion: number
}
```

实际绘制操作由 paint Modifier 和 LayoutNode 的正式受体消费；Painter 可以由资源获取层创建，资源路径、解码器和缓存实现不进入 Image/Icon 的 prop 语义。

- [ ] Painter 进入正式 UI 能力入口；不把任意 `onDraw` JS 函数冒充 Painter，不在绘制深处任意回调 JS
- [ ] Image 声明 painter、contentScale、alignment 等正式 prop，代码定义调用 Layout、使用 `MinSizeMeasurePolicy` 并显式组合 paint Modifier
- [ ] Icon 声明 painter、tint 等正式 prop，代码定义调用 Box 并显式组合 paint Modifier；tint 转换为 colorFilter，不读取主题色，不暗加默认尺寸
- [ ] 删除 Image/Icon 的 path、source 字符串魔法加载和按标签名分派的资源路径；资源路径若保留，只能由独立资源获取 API 先转换为 Painter，再传给 FA
- [ ] Painter 的固有尺寸、内容版本和失效归属接入统一 getter、Rearrange、LayoutNode 及帧阶段；资源迟到结果不能写入退休的 Painter 或 LayoutNode

# 第二趴

## 5．确立五类对象、Rearrange 过程与 Modifier 受体

### 5.1 五类对象的正式命名与边界

**已拍板：**TemplateNode、Arrangable、RearrangeNode、ArrangableInstance、LayoutNode 是不同职责的正式命名，不是可以互换的别称。源码、内部类型、编译产物协议、统计、诊断和公开文档都须按实际职责迁移；不是只修改文案或给旧万能对象增加类型别名。

| 正式名称 | 职责                                        | 用户接触边界 |
| --- |-------------------------------------------| --- |
| TemplateNode／模板节点 | 模板中的 `<Xxx />` 等语法节点及其编译期表示，表达调用或模板结构     | 用户书写模板，不手工创建编译器 AST；Xxx 指向 Arrangable，`<Xxx />` 本身是 TemplateNode |
| Arrangable | 参数、内容入口及模板或 Foundation 实现的定义，正式取代“组件”概念   | 可导入 SFA/FA 定义并用于标签或动态选择 |
| RearrangeNode／重排节点 | 模板程序执行后产生、参与结构协调的运行时结构记录；即原 VNode，现伟大转型升级 | 仅由正式内部入口生成，不向用户开放手工视图构造 |
| ArrangableInstance／Arrangable 实例 | 一次调用存续期间的局部状态、作用域、依赖与生命周期                 | 用户可使用正式生命周期能力，但不取得内部实例对象 |
| LayoutNode／布局节点 | 实现显式创建的原生布局、绘制及交互实体，提供明确的 Modifier 受体     | 由 Foundation 与原生执行系统管理，不向用户提供宿主引用 |

这些对象没有一对一关系：一个带 v-for 的 TemplateNode 可产生多次调用及各自的 RearrangeNode、ArrangableInstance；同一个 Arrangable 可有多个实例，一个实例可产生零个、一个或多个 LayoutNode。更新前后的 RearrangeNode 可关联复用同一 ArrangableInstance 或 LayoutNode，描述更新不等于实例重建。

`<Slot />`、`<Template>` 是模板语法中的 TemplateNode，但不因此产生同名 ArrangableInstance 或 LayoutNode。内部若需要内容调用范围或结构分组记录，可使用明确种类的 RearrangeNode；它不冒充额外 Arrangable 或布局盒子。

- [ ] SFA 编译产物与 FA 提供正式、可识别的不可变定义值，具有定义身份；普通函数或拼出几个同名字段的对象不能冒充定义，显示名称和文件名不充当唯一运行身份
- [ ] 删除 getCurrentInstance、defineExpose/expose 及公开实例代理等用户入口，不提供 `$el`、`$refs`、`$parent` 或手动 update/unmount 实例接口作为旁路
- [ ] 内部保留实现作用域、provide/inject、生命周期注册所需的实例归属；公开生命周期能力和用户自行创建的业务状态对象不等于公开运行实例
- [ ] 正式文档和诊断中的“组件实例”统一为 ArrangableInstance；旧名称仅用于明确指认待迁移代码或历史来源
- [ ] RearrangeNode 按真实结构种类区分所需字段，明确定义、组合 key、参数求值入口、内容及实例关联的职责；清除 Teleport、Suspense、特殊 ref、memo 等已废除协议字段，不原封不动复制 VNode 的所有分支
- [ ] 区分 TemplateNode 的源码位置与编译期身份、RearrangeNode 的协调身份、ArrangableInstance 的逻辑生命以及 LayoutNode 的原生身份与代际；JS 宿主账本、结构锚点及 Modifier.Node 等辅助实体按自身职责命名，不把所有带 Node 的类型机械改为 LayoutNode

### 5.2 LayoutNode、Modifier 受体与 Rearrange 过程

- [ ] Arrangable 定义参数、内容与实现，ArrangableInstance 承担调用期间的状态和生命周期；二者均不天然等于布局盒子
- [ ] RearrangeNode 及其协调身份，与 LayoutNode 的身份、父子关系和原生生命周期分开
- [ ] LayoutNode 是布局、绘制和交互的实在对象；明确创建、更新、插入、移动、移除及退休入口
- [ ] 缩小原生阶段的实际工作范围：定位测量、放置、绘制与命中缓存中扩大失效和无关遍历的路径，依据 LayoutNode/Modifier 能力减少兄弟节点扫描及结果重建；保留布局必要的父子传播，不以错误截断依赖换取低计数
- [ ] Modifier 描述可以被多个受体复用；每个受体的实例、缓存、动画及交互状态独立物化，不共享有状态实例
- [ ] 保留 Modifier 顺序、重复层、key 协调、精确实例更新与失效归属；不能退回平铺样式表
- [ ] 梳理目前 Vue renderer、JS 宿主账本与原生事务应用之间的正式职责，收窄为 Arrange 专用链路
- [ ] 清理 createText、setElementText、insertStaticContent、innerHTML/textContent 等残留契约中无 Arrange 用途的路径；结构锚点等有用职责转为自己的机制

不以“有没有 Renderer 接口”或“是否直接调 C++”判定改造完成。可保留有必要的应用边界，但不能留下通用 DOM 契约再由 Arrange 勉强适配。是否采用 Composer 类实体由真实职责决定，不为对照 Compose 生造对应物。

**正式过程：Rearrange／重排。** 原 VNode diff 及此前称为重组的过程统一使用这一名称，对标 Compose 的 Recompose。重排执行必要的模板结构程序、产生 RearrangeNode 并协调新旧结构，决定 ArrangableInstance 的创建、复用与退休，以及所需 LayoutNode 结构操作；它涵盖身份判定、参数与内容更新及增删移动，不仅指列表位置变化。

首次建立结构也走这套机制；后续只有实际结构消费者失效或调用结构需要更新时才执行必要重排。独立值绑定可以直接更新对应输入而跳过 Rearrange，原生测量、放置和绘制是其后的独立阶段，不并入重排计数。

- [ ] 运行时入口、类型与字段、统计指标、测试、诊断和公开文档统一使用 Rearrange 及上述五类名称，不继续把整个过程称为 VNode diff 或重组
- [ ] 原 VNode 的有效结构职责迁入 RearrangeNode，不改叫 Arrangable、TemplateNode 或 LayoutNode；内部仍可使用身份比较、列表协调等算法，但算法名不替代正式过程名

### 5.4 RearrangeScope：可独立重启的重排作用域

**已拍板：**RearrangeScope／重排作用域是可独立失效、调度和重新执行的结构单位，纳入 M2.4 正式实现与验收。RearrangeNode 是结构记录，RearrangeScope 是产生并协调一段结构的执行单位，二者不混用；作用域本身不增加 ArrangableInstance 或 LayoutNode，不向用户公开手动执行入口。

```text
ArrangableInstance
└─ 根 RearrangeScope
   ├─ 条件 RearrangeScope
   │  └─ 当前分支的 RearrangeNode 及内部作用域
   └─ 列表 RearrangeScope
      ├─ 条目 RearrangeScope（key=A）
      └─ 条目 RearrangeScope（key=B）
```

- [ ] 编译器为根模板、v-if／v-else-if／v-else 分支链、v-for 列表及其条目生成明确的结构执行边界；内容调用按 3.2 建立调用作用域，不要求用户拆成大量小 SFA 来获得细粒度
- [ ] 每个作用域保存所属 ArrangableInstance、父作用域、执行函数、当前结构记录、依赖、脏状态及退休状态，并保留源码归属；作用域身份在所属调用和编译位置内确定，列表条目结合明确组合 key 或既定无 key 协调规则，不建立全局 key 身份
- [ ] 结构读取在当前作用域内追踪，嵌套作用域建立自己的依赖；条件变化只唤醒对应条件作用域，条目内部条件变化只唤醒必要的条目或条件作用域，不重新执行根结构和无关兄弟
- [ ] 列表作用域负责集合、条目身份与顺序，条目作用域负责条目内部结构；插入、移动、删除使用正式 Rearrange 协调，同 key 移动保留作用域，item/index 等词法输入改变时刷新闭包和实际消费者，不把无响应式读取的闭包永久当作常量
- [ ] 分支切换退休退出分支内的作用域，保留分支选择作用域；条目删除清理依赖与待执行任务，迟到工作不得命中复用后的新身份；KeepAlive 停用暂停所属作用域，恢复按最新输入执行必要工作
- [ ] 作用域只加入统一帧调度器的结构阶段；父子同时失效时先处理父层，已删除子作用域不再执行，保留的子作用域按最新输入处理，已经处理的脏版本不重复执行，新失效仍按依赖顺序有界处理
- [ ] 普通 prop 求值和 Modifier 参数继续独立追踪，不回流到结构作用域；纯值更新可以不执行任何相关 RearrangeScope，不把 block 协调优化冒充独立作用域重启

本期落实上述明确边界，不建设完整 Snapshot 隔离、多线程重排或照搬 Compose 的全部 Group／dirty 位体系。依赖版本不冒充状态快照；统一 VSync 决定何时执行，RearrangeScope 决定执行哪里，两者共同参与正式调度。

- [ ] 模板继续将动态输入延后求值，由实际消费者建立依赖；同一个 Ref 可同时参与结构和值输入

### 7.1 DynamicArrangable：动态调用定义

DynamicArrangable 自己明确声明 `is` 和 `props`：`is` 接收 Arrangable 定义，`props` 接收目标调用的参数对象。两层参数边界分别成立，不接受未声明的顶层参数后再整体转交目标。

```vue
<DynamicArrangable :is="currentPage" :props="{ document }" />
```

这里 currentPage 是 SFA 或 FA 的定义值，例如导入的 Overview；也可以是保存该定义的 Ref，经模板解包后传入。用户只是在选择定义，实例创建仍由模板调用和运行时完成。

| 写法或输入 | 结果 |
| --- | --- |
| `<DynamicArrangable :is="Overview" :props="{ document }" />` | Overview 定义合法且声明兼容的 document 时成立 |
| `<DynamicArrangable :is="Overview" :document="document" />` | DynamicArrangable 自己没有声明 document，报错 |
| `is="Overview"` | 固定字符串不是 Arrangable 定义，报错，不按名称查找 |
| `:is="null"` | 报错；无内容时用 v-if 明确表达 |
| is 收到 ArrangableInstance、LayoutNode、RearrangeNode、普通函数/对象或 Promise | 报错；异步加载须完成并取得定义后再显式选择 |

- [ ] 按 is 的定义身份验证目标；编译/类型工具尽早检查目标与 props 的兼容性，动态选择在运行时按目标声明检查
- [ ] 定义、参数与内容作为一次完整调用输入校验和应用，不先切换目标再以旧目标的参数执行新实例
- [ ] 定义与调用身份均不变时保留实例并更新参数；定义变化或组合 key 变化时退休旧实例并建立新实例，需要缓存退出内容时使用 KeepAlive
- [ ] 动态内容交付属于该 FA 的明确调用职责，目标 Slot 名称按定义校验；不窥探 Slot 内部结构，也不恢复 scoped slot 参数协议
- [ ] `is`、`props` 不成为所有 Arrangable 的系统参数，不恢复 attrs 透传；非法目标或参数不回退成空注释、空视图或宿主字符串

### 7.2 KeepAlive：保存整份内容实例的逻辑生命

KeepAlive 缓存的是默认 Slot 一次调用对应的内容实例作用域，包含其创建的全部 Arrangable 实例、局部状态、后代与上下文关系。内容可以有零个、一个或多个 Arrangable，不要求默认 Slot 恰好一个孩子，不窥探第一个孩子来猜缓存对象。

```vue
<KeepAlive :cacheKey="pageId">
    <PageToolbar />
    
    <DynamicArrangable :is="currentPage" :props="{ document }" />
</KeepAlive>
```

KeepAlive 明确声明 cacheKey，用于选择其内部的内容缓存记录。普通组合 key 标识 KeepAlive 自身，二者不可混用：`<KeepAlive :key="pageId">` 会改变 KeepAlive 调用身份，不表达在同一缓存所有者内切换页面。

```text
KeepAlive 实例
    cacheKey A → 内容实例作用域 A
    cacheKey B → 内容实例作用域 B
```

| 内容状态 | 执行规则 |
| --- | --- |
| 活动 | 正常重排、值更新、动画、原生节点及交互 |
| 缓存停用 | 保留逻辑实例和局部状态，暂停 UI 执行，退出原生视觉与交互资格 |
| 销毁 | 逐出或所有者卸载时最终清理作用域、订阅、回调和缓存记录，不可复活 |

- [ ] cacheKey 切换时旧内容进入停用；返回已有 cacheKey 时恢复该内容作用域，以当前输入执行必要重排，不将外部词法变量冻结成快照
- [ ] 缓存内仍遵守普通重排身份规则：同一记录内某位置的定义改变，仍须替换该位置实例，不能用缓存身份强行保住不兼容定义
- [ ] 停用期间不执行结构重排、值提交及内容作用域的普通响应式任务；依赖变化记录为待处理，恢复时按最新状态处理
- [ ] 停用动画不持续申请视觉帧；内容不参与绘制、命中、焦点、指针捕获或输入，失去活动资格的 IME 会话正确结束
- [ ] 原生 LayoutNode、Modifier 实例与回调绑定在停用时可退休，恢复时重新物化；不承诺原生 ID 或 handle 永生，迟到写入不得命中已退休目标
- [ ] 编辑文本、滚动位置、动画当前值等应保留的可观察状态，明确归入逻辑状态或原生保存/恢复机制，不能因退休 Node 而丢失；焦点、捕获和 IME 会话不自动恢复抢占
- [ ] 外部异步结果可以更新仍存活的逻辑状态，但不得重新挂载停用内容或操作旧节点；销毁后迟到结果不能复活内容
- [ ] 提供正式激活/停用生命周期通知，供显式外部订阅处理暂停与恢复；暂停 ReactiveEffect 不冒充自动暂停网络等外部工作，也不为通知暴露实例对象
- [ ] 持续后台工作的业务状态归更长寿的外部作用域，由内容消费，不用 KeepAlive 偷偷维持隐藏页面的全部工作
- [ ] 缓存具有明确的有限容量与逐出策略，具体默认值随实现声明；逐出和 KeepAlive 自身卸载都执行最终清理，不能只删除 Map 引用

### 7.3 上下文与后续展示能力

上下文依赖只使用 provide/inject。迁移 createArrangeLocal、provideArrangeLocal、useArrangeLocal 及其同型便捷封装；确需保留的上下文值使用明确的注入 key 和默认策略。Foundation 不得用 provide/inject 取得颜色、字体风格或其他样式；只有字体解析器、资源服务等与根本行为有关的宿主服务才可显式注入，且不能偷偷改变视觉样式。保持响应式上下文的依赖关系，不读取一次就误冻结为快照；通过 prop 显式传递 Ref 本体遵守 1.3，不改变 provide/inject 的上下文职责。

异地展示若日后确有需求，可以另行设计明确的 Popup、Overlay、Dialog 能力；不是本期为了删除 Teleport 必须顺带新增的一整套功能。

## 8．错误在最早可确定处诊断，真实边界保证契约

| 情况与反例 | 最早诊断处 | 动态或原生边界职责 |
| --- | --- | --- |
| `<Row>恩情</Row>`、`<Row>{{ title }}</Row>` | 模板编译 | 内部组合入口也不得把字符串悄悄转成节点 |
| `<MissingArrangable />` | 能确定定义的名称解析阶段 | 动态目标解析失败时拒绝，不回退为宿主字符串 |
| `<Mamba :undeclared="value" />` | 已知目标声明时检查 | 动态参数对象在 Arrangable 参数入口检查 |
| `<Text :text="someObject" />` | 能确定类型时诊断 | 动态值进入消费者前检查，不 String 强转 |
| `<Input><Text text="子内容" /></Input>` | 已知 Slot 契约时检查 | 动态内容入口拒绝未声明内容 |
| 已退休绑定写入、错误节点关系 | 通常不能静态确定 | 原生身份、代际、结构与事务有效性检查 |

- [ ] 编译诊断和动态参数检查使用同一份正式声明，不分别维护一套规则
- [ ] 区分模板转换、TS 类型检查和打包：能转译、能 bundle 不代表参数类型检查已经完成
- [ ] 明确运行时可验证的类型与约束，不假装完整执行 TypeScript 类型系统；无法提取的声明不能悄悄变成任意值
- [ ] 非法参数在执行对应逻辑前失败；开发和生产同样拒绝，禁止 warn 后继续
- [ ] 不在每层重复检查同一事实；Arrangable 参数错误在其入口终止，原生检查自己的输入、身份和结构
- [ ] 下层提供具体错误，上层补充来源并统一报告，保留文件、位置、Arrangable 名、输入名、预期与实际类型
- [ ] 原生构建失败保留已发布场景与帧，不宣称 JS 副作用也可回滚

验证正向契约和实际不变量即可，不写一大批断言逐个封禁 Web 词汇。删除能力的消费者与解释基础，比保留实现后四处增加拒绝判断更彻底。

## 9．最后把整条链路统一到 Arrange 的生命周期与帧阶段

**已拍板：**Arrange Vue 与 Arrange Framework 使用一个 UI Owner、一个统一调度器、一个生产视觉帧源。业务任务及时执行，视觉工作在 VSync 授权的帧内执行。以下是本期迁移目标，不代表当前微任务、重排与原生提交已经统一；对应实现完成时同步迁移 [调度线程与帧阶段](../../../arch/26-调度线程与帧阶段.md)。

### 9.1 一个 Owner，两种执行边界

- [ ] UI Owner 采用 JUCE message thread，统一拥有 QuickJS、Arrangable 作用域与原生 UI 状态；可以按职责分队列，但不能形成各自独立冲刷 UI 的调度循环
- [ ] 普通任务边界及时处理输入语义回调、资源及异步完成、Promise 后续任务，不要求这些工作等到 VSync
- [ ] 状态写入立即生效，同步读取可见最新值；Ref、按需计算的 computed 保持正常语义，视觉消费者只登记失效并申请帧
- [ ] 同一帧前多次状态变化可以合并视觉求值，不能合并或吞掉业务操作；三次点击各自执行累加，即使最终只更新一次显示，结果仍须增加三
- [ ] VBlank/VSync 是唯一生产视觉帧源；重排、UI 值绑定、动画采样和原生输出统一受帧阶段管理，不再用微任务提前执行一轮视觉更新
- [ ] 无 peer 或不可见时可以暂停视觉工作，但语义任务、取消及最终销毁不得依赖下一次 VSync 才能完成；空闲且无失效、无活动动画时无需每帧执行流水线

### 9.2 明确一帧的执行顺序

正式帧顺序如下，阶段名称是职责描述，不冻结内部类型命名：

1. 完成本帧接纳的普通任务及其微任务检查点，不无限吸入新任务
2. 确立本帧输入截点与唯一帧时间戳；后续到达的外部输入进入之后的处理机会
3. 按该时间戳采样活动动画，收集它们引起的失效
4. 执行重排与 UI 值绑定，处理必要的父子参数传播和动态依赖，形成一致的提交输入
5. 封存提交，按序应用原生事务，执行所需测量、放置、绘制及命中数据构建
6. 成功后发布一份一致的帧结果
7. 执行对应的提交后生命周期通知；通知引起的新视觉失效归下一帧

- [ ] 阶段职责显式建模，不长期依赖 Vue job 的数字排序暗示职责；保住结构和值更新分离、父子传播及实际读取建立的依赖
- [ ] 不规定每个 effect 每帧最多执行一次来截断合法依赖传播；稳定过程必须有界，结构表达式不得依赖写状态后反复执行才能收敛
- [ ] 同帧动画使用同一时间戳；重排中新建动画以当前帧时间初始化，不二次推进时间或另发一帧
- [ ] 新 Foundation/LayoutNode 应用入口使用正式结构操作、绑定注册退休与 typed 输入更新，保留有序提交和候选帧发布
- [ ] 不绕过原生失效、FramePlan、测量/放置/绘制构建及 PublishedFrame，不在参数 setter 或组合回调里直接绘制
- [ ] 原生应用、测量及绘制构建阶段不回调任意用户 JS；禁止嵌套事件派发和帧流水线重入，提交后回调不能递归发布第二份原生帧
- [ ] 首次视图创建与重排同样受帧授权；模块加载等准备工作可提前完成，但不能以初始化为由绕过视觉执行边界
- [ ] 明确重排完成、布局完成、帧发布和屏幕实际呈现的差别；VBlank 时间戳及 PublishedFrame 均不是显示器已经呈现的证明

### 9.3 微任务保留，nextTick 不再等待重排

- [ ] 宿主显式驱动 QuickJS 的 `JS_ExecutePendingJob`，在外层宿主任务或回调返回后执行规定的微任务检查点；不在每次嵌套 FFI 返回时排空微任务，不另引入一套 QuickJS 标准事件循环
- [ ] 移除 Vue `Promise.then(flushJobs)` 独立执行重排和 UI ValueBinding 的权限，移除 JS 宿主 `queueMicrotask` 自行冲刷原生视觉提交的路径，由统一调度器接管阶段推进
- [ ] nextTick 只保留微任务等待语义，不等待重排、布局、帧发布或实际呈现；明确其检查点与回调顺序，不把它定义成无限排空未来任务的承诺
- [ ] 迁移依赖旧 Vue nextTick 等待结构更新语义的调用者与测试，这是正式 breaking change；若需要等待提交，使用另行明确设计的提交信号，不给 nextTick 偷加双重语义
- [ ] 逐项明确 watch 的 pre/post 对应阶段与所属作用域；UI 相关观察遵守帧阶段，sync 观察不得直接启动视觉流水线，也不能靠改名保留第二套 UI 调度

验收例：修改影响模板的状态后，只推进微任务并 `await nextTick()`，同步读取能取得新值，但重排和发布计数均不增加；推进手动原生帧源后，才执行必要视觉工作。

### 9.4 生命周期跟随作用域与提交

- [ ] 实例创建、setup 及相关依赖建立发生在对应首次重排中；mounted、activated、updated 等成功通知在对应提交成功后发出，不宣称已经呈现
- [ ] 独立值更新不凭空产生一次结构 updated；成功通知与实际完成的工作对应，失败候选不能冒充挂载或更新成功
- [ ] KeepAlive 按本篇 7.2 的作用域规则暂停和恢复任务；停用内容不执行 UI 工作，不妨碍其他存活作用域的语义任务，恢复所需视觉工作进入正式帧
- [ ] 停用资格撤销、外部订阅的暂停及输入会话结束及时处理；激活/停用成功通知与对应提交关联，最终销毁、reset 和资源清理在 Owner 上及时完成，不等不可到来的帧
- [ ] 异步工作明确所有者、请求身份、取消和代际；Promise 不因作用域销毁自动取消，迟到完成不得复活已销毁内容或访问退休节点
- [ ] 发布的原生状态保持一致，不承诺回滚已经执行的 JS 副作用；失败后的清理与恢复按明确错误路径处理

### 9.5 JS 与原生之间保持明确的 FFI 边界

- [ ] 同一 Owner 上的同步 FFI 用于有界计算、读取明确快照及捕获 typed 操作，不同步启动布局或发布，不在原生应用期间重入用户 JS
- [ ] 结构事务与值槽批次保持顺序和身份校验，在正式阶段提交；一体化不等于强制拼接成巨型 JSON，也不等于消除必要的职责边界
- [ ] 重 I/O、解码等工作移出 Owner；辅助线程只传递不可变结果及身份，由 Owner 接收，不跨线程访问 JSValue、QuickJS runtime 或 UI 树
- [ ] 音频线程使用符合实时约束的非阻塞通道，不调用 QuickJS，不等待 UI Owner

### 9.6 事件保序，按身份判过期

- [ ] 建立 Owner 入口的事件顺序号与时间戳，携带适用的 runtime/context 代际、目标或回调代际、手势或请求身份，以及关联的已发布命中场景版本
- [ ] 点击、按下、抬起、取消、按键、文本及 IME 提交、手势开始和结束等离散语义保序交付，不因等待时间较长或跳帧而丢弃
- [ ] 绝对位置、悬停和视口快照可在离散事件屏障之间合并；`move → down → move → up` 中的两段 move 不能跨 down 合为最后一个位置
- [ ] 滚轮、拖动等增量只有在能证明语义等价时才聚合；边界裁剪、方向反转、嵌套滚动和速度估算等不能被简单求和破坏
- [ ] 已销毁上下文、已退休回调、无效目标或已被新请求替代的资源结果可拒绝；不得把旧事件重新投递给复用了数字 ID 的新节点
- [ ] 场景版本变化本身不是事件过期的充分条件，毫秒年龄也不是丢弃点击或 IME 的充分条件；按真实身份与语义有效性裁定
- [ ] 邮箱有明确容量与背压、合并及过载处理策略，不能靠无界堆积或静默删除离散事件维持表面流畅

### 9.7 跳过中间画面，不跳过业务动作

- [ ] 不积压并补跑过时的视觉帧票据；错过帧后，在下一次视觉机会按最新有效状态与时间执行
- [ ] 动画按时间推进，不按执行次数乘固定 16ms 推进；必要的积分器可使用有界内部子步，不因此额外发布中间帧
- [ ] 未完成或失败的候选保留上一份成功发布帧，不对外发布半份 JS/原生事务结果；跨帧继续工作须明确一致性，不能将任意执行点视作可安全暂停点
- [ ] 预算同时关注任务数量、实际耗时、递归失效与邮箱压力；仅限制 PendingJob 数量不足以约束一个长回调
- [ ] QuickJS 中断是终止执行，不是可恢复的时间片暂停；需要配套异常与恢复处理，不把它当作任意 JS 任务的续跑机制
- [ ] 测试使用同一生产调度器与可控原生帧源，记录帧身份和阶段计数，不另外模拟一套调度算法
- [ ] 帧内结构调度以 5.4 的 RearrangeScope 为独立执行单位，保留父先子后及退休任务取消；原生阶段按实际失效范围工作，不因局部重排恢复全树扫描或无条件重建

### 9.8 删除 rAF，动画直接纳入统一帧泵

- [ ] 正式删除 requestAnimationFrame/cancelAnimationFrame，包括原生安装的 JS 全局函数、类型声明和运行时依赖，不保留兼容别名，也不换个名字公开同样的手工逐帧循环入口
- [ ] 用户动画统一采用 Compose 模式的 Arrange animated 系列与 Transition 状态对象；其内部采样、完成和取消直接纳入统一帧泵与作用域生命周期，不再经由 rAF 协议
- [ ] 替换当前 defaultAnimationClock 对 rAF 的依赖；仍需存在的异步加载延迟等内部帧期限工作接入正式宿主调度，随所属作用域取消，不为保留它们而留下 rAF
- [ ] 整理动画时钟注入和手动时钟的生产/测试边界，不让这些入口成为用户手工动画帧循环的替代品

删除前的事实仍需准确记录：当前原生 requestAnimationFrame 仅登记回调，由 VBlank 帧泵推进，并非另起浏览器帧源；本次删除是正式收紧动画编程模型。统一 VBlank 帧泵和内部动画采样职责继续存在。Promise/微任务调度与逐帧动画协议不是同一种能力，不因删除 rAF 而一并删除 nextTick。
