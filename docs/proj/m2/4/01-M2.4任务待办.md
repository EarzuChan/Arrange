# 历史基础：已在新底座回归的模板与参数契约

以下第 1–3 节是必须保住的行为基线，不能因换运行时而恢复已经废除的模板和参数语义。

## 1．从模板字面量开始，停止自动造内容和自动转换

### 1.1 裸文本、插值与源码空白

现有反例：

```axml
<Row>恩情</Row>
<Text>恩情</Text>
<Row>{{ { a: 1 } }}</Row>
<Row><Spacer/> <Spacer/></Row>
```

已观察到的后果：裸文本变成原生 Text；Text 子内容被写入文本；对象插值被格式化为 JSON 后显示；最后一例的空格生成第三个子节点，而换行版本只有两个。

- [x] 模板内容位置不支持裸字符串与 `{{插值}}`，有意义的文本内容直接报错
- [x] 标签之间的纯排版空白统一忽略，空格、换行和缩进不得改变节点数与布局间隔
- [x] 显示文本必须经过显式 Text 的 `text` 参数；`<Text :text="title" />` 合法，`<Text :text="({ a: 1 })" />` 应因类型不合而失败
- [x] 彻底删除对象到显示字符串、任意值到文本节点等旧垃圾路径，不能只禁止一种模板写法而保留另一条等价旁路
- [x] 内部结构锚点与可见 Text 分开，不再借文本创建入口表达锚点

### 1.2 参数写法只表达确定的值

**已定：**拒绝 Boolean casting、根据目标类型猜值、未声明默认值却补值，以及类型错误仅警告后继续执行。

**已拍板：**三种写法全部允许，且只具有以下含义。带冒号的绑定必须显式给定表达式，不支持同名自动补全。

| 写法 | 唯一含义 |
| --- | --- |
| `title="abcd"` | 固定字符串表达式，值为 `"abcd"`，不解释为 JS |
| `enabled` | 固定布尔表达式，值为 `true` |
| `:amount="expression"` | JS 表达式的反应式求值结果，常量表达式同样允许 |
| `:xx` | 非法，即使当前作用域存在同名 Ref xx，也不得补成 `:xx="xx"` |

绑定语法保留明确的同族写法，不因允许别名而恢复其他 Vue 协议：

| 写法 | 含义与边界 |
| --- | --- |
| `:amount="value"`、`a-bind:amount="value"` | 等价的显式表达式绑定，两种写法都必须提供表达式 |
| `:[propName]="value"`、`a-bind:[propName]="value"` | 动态求出参数名，归一后仍须匹配目标声明；不允许借动态名字传入未声明参数 |
| `a-bind="params"` | 将对象字段作为本次调用的参数，逐项遵守名称、类型和重复检查，不表示向内部透传 |
| `:some-value.camel="value"`、`:[propName].camel="value"` | 显式 camelize 参数名，不转换参数值；长写 a-bind 同样适用 |

**参数名称规则：**保留 Vue 的 camelize 规则，声明名和传入名均归一后匹配。因此声明 `someValue` 或 `some-value` 都归一为 `someValue`，调用方的两种拼写也匹配同一参数。沿用 Vue camelize 的确定转换算法，不扩大为大小写忽略、全小写猜测、下划线兼容或模糊匹配。此规则只适用于 prop 名称，不扩展到 Arrangable 标签或槽位名。

反例及目标结果：假设 Xxx 明确声明 `flag: boolean`、`amount: number`。

| 调用 | 旧现象或问题 | 本期要求 |
| --- | --- | --- |
| `<Xxx flag="" />` | 空字符串被转成 true | 固定空字符串因 string 不符合 boolean 而失败 |
| `<Xxx flag="flag" />` | 同名字符串被转成 true | 同上，不允许同名特例 |
| `<Xxx flag="false" />` | 警告后传入 truthy 字符串 | 报错，不执行布尔转换 |
| `<Xxx amount="12" />` | 字符串与数字边界易混淆 | 保持 string；要求 number 时失败 |
| `<Xxx />` | Boolean prop 没有 default 仍补 false | 只应用显式默认值，否则保持未传或报告必需参数缺失 |

- [x] 实现三种确定的参数写法，删除 `:xx` 同名绑定简写；检查引号、转义和重复参数处理，移除沿袭上游但没有 Arrange 定义的转换
- [x] 普通模板绑定继续支持 Ref 解包并反应式求值；显式原样绑定允许传递 Ref 本体，语法、声明与依赖语义见 1.3，不依据目标类型偷偷切换解包方式
- [x] 标签统一 PascalCase，按定义的准确名称解析，不兼容 `keep-alive` → `KeepAlive`；prop 声明与传入统一 camelize，Foundation、用户 Arrangable、静态属性、绑定及参数对象采用同一规则
- [x] 保留 a-bind／冒号、动态参数名、对象参数绑定和 `.camel`；不继承 `.prop`、`.attr`、`.sync` 等其他修饰符，不保留无表达式绑定或无效动态名字自动补空字符串等宽松处理
- [x] 同一声明中两个名称归一后冲突，在定义阶段报错；同一次调用中第二次传入同一归一参数立即报错，不覆盖、不合并回调、不按源码先后选胜者
- [x] 静态可确定的重复在编译时报告；动态参数名和对象绑定在参数组装边界一旦确定重复即拒绝，不先执行目标逻辑再报错；参数对象内部已经完成的普通 JS 求值遵守 JS 语义，不追溯对象构造前的覆盖过程
- [x] 动态表达式值变化后同样遵守类型契约，不能仅检查初始值

例如 `<Xxx :someValue="a" :some-value="b" />`、`<Xxx :count="a" a-bind:count="b" />` 均报重复参数；`<Xxx a-bind="params" :count="count" />` 在 params 含归一后同名字段时同样报错。DynamicArrangable 的 props 参数对象进入目标调用边界时也采用同一名称及冲突规则。

### 1.3 显式原样传递 Ref 本体

**已拍板：**允许通过已声明的 prop 显式传递本层Setup定义的 Ref 的引用（而不是解包值），用于共享可写状态、交付只读响应式状态，或将状态容器交给下层逻辑。这里的“原样传递”只表示保留参数值及 Ref 身份，不是什么 attrs fallthrough 的复活（更不是什么自动把参数传给接收方内部的其他 Arrangable）。

调用方在绑定表达式外层使用尖括号标记（这是主人发明的新写法）：

```axml
<Editor :oriRef="<documentRef>"/>
```

尖括号写法仅是 SFA 模板编译语法，不是 JS 运算符、字符串值或类型断言；SFA 编译器识别完整外层标记，再按 TS 表达式处理内部内容，生成保留 Ref 的对象引用，不注入通常的 `.value`／unref 解包。

主人批：我的想法是尖括号包“结果是Ref引用”的表达式，而不是包裹整个表达式填写区域，如我不建议只能`<selectedKey.value ? secondRef : firstRef>`；在我想法中，更好的用户写法是`selectedKey ? <secondRef> : <firstRef>`（解包了selectedKey，保留secondRef、firstRef）。当然因为始终还是包**表达式**，我的构想（尖括号包“结果是Ref引用”的表达式）实际上两种写法都是兼容的（因为最后这个表达式的结果都是一个Ref引用）。

另注：接受方，在Prop声明接受一个外界Ref后，该Ref引用在模板**不会自动解包**（所以也不需要再次使用尖括号来保证不解包，反而取值需要显式`.value`）：因其不是你本地Setup定义的。这个暂时没想着解决。

接收方使用类型式 prop 声明，Something 为业务类型：

```ts
import type { Ref } from '@arrange/framework'

const props = defineProps<{
    oriRef: Ref<Something>
}>()
```

`Ref<Something>` 是 TS 类型。普通 TS 中读取 `props.oriRef` 得到原 Ref，读取 `props.oriRef.value` 才消费其中的值；可写 Ref 允许通过 `props.oriRef.value = nextValue` 写入，但不允许给 `props.oriRef` 重新赋值。只读状态须采用只读 Ref 契约，不因传参获得写权限。

- [x] 原样标记只作用于完整绑定表达式的外层；明确其与比较运算、泛型调用和 TS 类型语法的解析边界，保留源码位置，不以简单替换尖括号处理所有表达式
- [x] 原样模式禁止编译器自动解包，仍遵守内部表达式的正常 JS 求值；显式 `.value`、运算、函数调用或代理本身的取值语义不被撤销，不自动重建已经丢失的 Ref
- [x] 原样绑定仍是反应式求值，不等于首次取值后永久冻结；若选择表达式的依赖改变并返回另一个 Ref，按新身份更新参数
- [x] 仅传递 Ref 本体不读取其 `.value`，同一 Ref 的 value 变化不会仅因这次传参而触发参数替换或结构重排；接收方实际读取 `.value` 的消费者正常订阅，结构读取可触发重排，值绑定读取只唤醒对应值消费者
- [x] 编译产物、prop 存储与传递链完整保留 Ref 身份，不使用普通模板实例代理的解包结果代替本体；继续向内部传递时也必须显式声明和调用，不自动透传
- [x] 冒号与 a-bind 长写、动态参数名及 `.camel` 使用一致的原样值语义；名称转换不影响参数值，参数对象和 DynamicArrangable 目标参数入口不得再次悄悄解包其中显式保留的 Ref
- [x] SFA 编译器识别类型式 Ref 声明，形成与运行时入口一致的 Ref 契约；最终表达式结果不符合声明时拒绝，不能仅靠 TS 类型就宣称运行时已支持，也不假装完整验证任意泛型业务类型
- [x] 明确只读 Ref 与可写 Ref 的类型及运行时可识别约束，不能仅凭 isRef 就视为可写；不克隆状态容器，不建立隐式双向绑定协议或恢复 v-model

### 1.4 唯一的 SFA 文件与脚本模式

**已拍板：**单文件 Arrangable 只使用 `.sfa` 扩展名。文件中的 `<script>` 唯一表示 TS setup，不再要求或接受 setup、lang 属性，不保留普通模块 script 与 setup script 两套模式（默认/开箱即用即是setup体，不再有options体（应移除全部Options API相关）），不保留独立 JS 脚本模式（script体内直接/只能写ts）。Arrange IDE 插件暂不建设，也不作为 M2.4 的交付前提。

正式文件形态，例如 Counter.sfa：

```html
<template>
    <Text :text="String(count)" />
</template>

<script>
import { ref } from '@arrange/framework'

const count = ref(0)
</script>
```

主人注：先写template块再写script块，是不言而喻的约定俗成/默契；在模板内，同级模板节点之间留出空行，也是香香软软的美好实践。

- [x] SFA 最多一个 script 块，无逻辑时可省略；存在时统一按 TS setup 编译，顶层绑定供模板使用，局部状态及初始化逻辑按 Arrangable 实例执行，重排不重新执行初始化
- [x] import 保持模块语义；模块级共享状态、导出及工具逻辑放入独立 `.ts` 模块，不在 SFA 中恢复第二个模块脚本或手写 default export Arrangable 配置入口
- [x] 删除 `<script setup>`、`lang="ts"`、`lang="js"` 及普通 script/setup 双块路径，不保留冗余属性兼容别名或按属性切换行为的分支；JSX/TSX 等其他脚本模式同样不开放
- [x] 未写类型标注的常规代码仍按 TS 解析与推断，不强迫每个局部变量加类型；类型式 defineProps 等宏及模板表达式统一按 TS 处理，脚本转译成功不等于类型检查通过
- [x] 正式源文件、Demo、测试 fixture、脚手架、导入语句及示例迁移为 `.sfa`；Arrange 构建入口停止把 `.vue` 当作 Arrangable 源文件，不保留双扩展名加载或自动回退
- [x] 同步文件发现、模块解析、Vite/构建转换、依赖追踪、HMR、源码映射、诊断文件名及类型检查入口，保证真实 `.sfa` 文件可从源码编译到原生运行；类型支持须保留定义与 prop 契约，不用通配 any 声明冒充完成
- [x] 不依赖 Vue 官方 IDE 插件识别或正确解释 Arrange 专属语法，不把 `.sfa` 自动关联回 Vue 来声称兼容；本期保证编译与命令行诊断链路，不承诺专用补全、跳转或其他 IDE 插件功能

## 2．Arrangable 是参数边界，Modifier 和回调也必须声明

### 2.1 **严肃彻底**删除模板节点透传机制，而非默认关闭透传

当前反例：Xxx 未声明 props，内部仅返回带 `text="内部"` 和 `M.padding(8)` 的 Text，外部调用：

```axml
<Xxx text="abcd" :modifier="M.width(99)" />
```

实测内部文本被覆盖为 `abcd`，Modifier 只剩 width，且没有警告。

- [x] 正式统一 Arrangable 与 SFA 术语，定义、类型、诊断、工具链和公开文档不再设立另一套“组件”概念；具体 API 与工具内部符号重命名清单在实施前列明，文件扩展名和脚本模式按 1.4 正式迁移
- [x] 只能传入目标 Arrangable 明确声明的 prop（且不透传到目标Arrangable内的任何模板节点，而是在目标Arrangable定义脚本内从Props取用（另：目标Arrangable模板直接拿Prop名取用不变）），未声明即报错，不忽略、不收集后转交内部
- [x] 删除 attrs fallthrough、inheritAttrs 开关及等价旁路；内部零根、单根、多根都不改变参数边界
- [x] Modifier 是普通的、需要精确声明的 prop，不因名称为 modifier 就获得系统待遇
- [x] prop 的默认值、必需性与校验来自声明，不能按命名或内外部标签形状推断
- [x] 正式声明直接参与编译优化：已知 Arrangable 定义时预先确定参数位置、默认值处理及内容调用入口，减少运行时名称解析与临时参数对象组装；动态定义仍在真实边界校验，静态与动态调用遵守同一契约，不改变默认值求值时机

对 `<Mamba :modifier="externalModifier" />` 的验收要求：

| Mamba 的实现 | 结果 |
| --- | --- |
| 未声明 modifier | 报错 |

| 显式传给内部一个受体 | 仅作用于该受体 |
| 显式传给多个受体 | 各受体分别物化实例与状态 |

### 2.2 坚决删除模板节点上的 Dom Element ref 与事件、双向绑定协议

以下为退出公共写法的例子：

```axml
<Box ref="box" />

<Xxx @submit="submit" />

<Input v-model="name" />
```

第一个不能再用来取得宿主元素或 Arrangable 实例；第二个不再经过 emit、监听器识别、命名变换与合并；第三个不再隐式展开为 modelValue 与 update 事件。

- [x] 移除模板特殊 prop `ref` 及获取 Dom Element 实例引用的相关公共能力；注意：这里不是指删除响应式系统 `ref()`
- [x] 删除 emits、emit、`v-on`／`@xxx` 事件语法与命名约定驱动的特殊分派
- [x] 删除 v-model、defineModel、系统 modelValue、update:modelValue、modelModifiers 及其 trim/number 等转换
- [x] 交互通知改为明确声明的函数 prop；`onXxx` 若作为普通参数名使用，不产生自动合并、冒泡或多播
- [x] 保留原生交互回调所必需的 typed event slot 与生命周期管理；删除的是用户层隐式协议，不是所有事件输送能力

目标形态示例，具体参数名随正式定义落定：

```axml
<Input :value="name" :onValueChange="value => name = value" />

<Mamba :onConfirm="confirm" />
```

旧清单中一次 submit 导致 count 从 0 变为 2 的反例，须迁移为单一明确调用路径。需要两个回调时由实现显式调用，不按参数名称暗中合并。

`modelValue`、`style` 等单词不建立黑名单；去除系统特权后，用户自行声明的同名普通 prop 不自动拥有任何 Vue/Web 能力。

## 3．保留控制流，明确内容入口与 Slot

### 3.1 控制流属于组合语言

### 3.2 接受内容必须有声明

现有反例：

```axml
<Input>
    <Text text="子节点" />
</Input>
```

旧链路允许提交 Input → Text 父子关系，却没有相应内容契约；这不等于它拥有正确布局行为。

- [x] Arrangable 未声明 Slot 时，外部不得强塞子内容
- [x] 用户 Arrangable 在实现模板中通过 `<Slot />` 显式声明并调用默认内容，通过 `<Slot name="header" />` 显式声明并调用具名内容，不额外要求 defineSlots 声明
- [x] `<Slot />` 只是模板中的槽位代称与内容入口，不是运行时 Arrangable；被提供的内容相当于无参数的 `@Composable () -> Unit`，由接收者明确决定是否调用、在哪里调用，不在外层提前生成一包节点再隐式搬运
- [x] 运行时执行的是填入的 Arrangable 内容，不创建 Slot 包装实例或原生节点；内部可保留内容调用、依赖与生命周期管理机制，但不能将这些机制实体化为 Slot Arrangable，槽位语法不接受业务 prop 或 Modifier
- [x] 内容内部可以有零个、一个或多个 Arrangable，Slot 使用方无需也不能依赖其数量或窥探内部结构；不保留 scoped slot 的出口传参和外部解构协议
- [x] `name="header"` 是静态槽位选择语法，由编译器解析，不是 Slot 的运行时 prop；不接受 `:name="expression"`、`:modifier` 或其他业务参数
- [x] 提供具名内容允许等价的 `<Template a-slot:header>...</Template>` 与 `<Template #header>...</Template>`，其他静态槽位名同理；默认内容可用 default 名显式选择，保留同族写法不恢复动态槽位名、scoped slot 参数或修饰符
- [x] Template 不产生布局节点，不为这个分组凭空增加运行时包装实例；槽位名按声明准确匹配，不随 prop 一起 camelize
- [x] 已声明的默认或具名 Slot 未被提供时，使用默认空 Arrangable（default empty Arrangable）的空内容语义；合法调用且不产生实际 Arrangable 实例或原生节点，不报必需内容缺失
- [x] Foundation Arrangable 与用户 Arrangable 使用一致的内容契约，不能拥有暗中接受任意 children 的特权
- [x] 明确同一内容多次调用时的实例独立性、词法变量来源、响应式订阅及生命周期归属
- [x] 内容调用建立独立的 RearrangeScope，明确提供方词法环境与调用方生命周期归属；内容内部依赖变化只唤醒实际消费者，不无故唤醒提供方或无关外层结构
- [x] 复用可证明安全的内容描述与调用入口，减少重复分配；同一份内容多次调用的状态和订阅仍独立，词法输入变化时刷新，不能冻结提供方变量或通过窥探孩子数量优化，不产生 Slot ArrangableInstance

提供方的正式形态：

```axml
<Containable>
    <Template a-slot:header>
        <Text text="标题" />
    </Template>
    
    <Something :xx="x" />
    
    <Something2 />
</Containable>
```

Containable 的实现模板在自己的布局中显式使用：

```axml
<Column>
    <Slot name="header" />
    
    <Slot />
</Column>
```

默认内容整体作为无参数内容提供给默认槽位。`xx` 是 Something 的 prop，`x` 来自提供方词法作用域，均不是槽位参数。上例运行时执行 Column、Text、Something 和 Something2 等实际 Arrangable，不存在额外的 Slot 实例；内容产生的实际 LayoutNode 接入调用位置的原生父节点。同一份内容在不同位置调用时，其内部 Arrangable 分别具有独立实例和身份。未声明的槽位仍不能强塞，不能将“已声明但未提供时为空”误解为接受任意内容。

## 4．普通 Arrangable 与唯一特权 Layout Arrangable

### 4.1 同一种定义、调用与生命周期

- [x] SFA 编译结果与普通代码 Foundation Arrangable 系同一种 Arrangable，拥有相同参数校验、内容调用、实例初始化、结构执行与清理协议；删除独立 Foundation 注册身份、专属执行分支及 defineFoundationArrangable 等分裂入口

- [x] 普通 Foundation Arrangable 只处理 props、选择 MeasurePolicy、组合 Modifier 并显式调用 Layout 或其他 Arrangable；不直接创建 RearrangeNode、物化 Modifier 或提交原生节点操作
- [x] 删除 capabilities 的声明、调用参数、上下文、注册器、类型、运行时记录和后端旁路；删除通用 Context.layout、可注册布局权限的工厂及 Foundation createState/state 协议，不换名字保留等价机制
- [x] 局部状态、保留控制器及资源按统一实例/内容作用域生命周期初始化与清理；不把 KeepAlive 缓存控制器伪装为框架通用 State，不复制 VNode 内部字段
- [x] 验证用户 SFA 组合 Layout、Policy、Modifier 与等价代码 Foundation Arrangable 的结果一致；所需 UI 行为构造不能只有 Foundation 能调用，用户不需要原生节点权限
- [x] FA 不按名称获得 children、modifier、style、事件、资源或布局盒子；零根、单根、多根均遵守同一边界
- [x] 回归确认空 Modifier 起点使用大写 M，旧 m 退出，Modifier 类型名不变

```

### 4.2 Layout 是唯一深入节点管理层的 Arrangable

Layout 声明 measurePolicy、modifier 与默认内容，任何 SFA 和用代码声明的 Arrangable 均可调用。特权在 Layout 的实际实现内，不在名称解析、定义注册或调用者身份上。

<Layout :measurePolicy="policy" :modifier="M.padding(8)">
    <Something />

```

- [x] Layout 使用普通定义与调用边界，其实现模块唯一接入 framework 节点管理；不得搞什么 define("Layout") 返回节点、字符串标签识别或 renderer 按名称分派
- [x] 一次存续 Layout 调用管理一个 RearrangeNode；首次创建、后续使用/更新/移动和退出退休均可从 Layout 实现与其调用生命周期追踪
- [x] 普通 Arrangable、内容调用、分支和列表不创建 RearrangeNode；源码或执行账本不产生同名节点分支
- [x] Layout 作为唯一最终 Modifier 接收者，接收处理好的描述与 Policy，通过其节点应用链路在原生受体上协调、物化实例链；外部与内部元素顺序写在普通 FA 实现中
- [x] 保持 ArrangableInstance、RearrangeNode、LayoutNode 与 Modifier 实例身份分离；同一描述交给两个 Layout 时状态和 handle 独立，退出后旧绑定拒绝写入
- [x] 验证穿过多层普通包装、Slot、条件及列表后的布局父子关系与顺序；零根不补盒子，多根不生成额外容器
- [x] Layout 的原生结构操作、Policy 更新、Modifier 更新和失败清理接入现有有序提交与候选帧发布；测量、放置、绘制仍由后端独立执行

### 4.3 Policy 与文本 Modifier 各自承担明确职责

MeasurePolicy 是可传给 Layout 的布局算法值，与 Foundation Arrangable 定义身份解耦。正式策略与文本分工见 [内建 Arrangable](../../../arch/12-内建Arrangable.md) 和 [文本输入与绘制](../../../arch/18-文本输入与绘制.md)。

| Policy | 本期使用职责 |
| --- | --- |
| BoxMeasurePolicy | 叠放、内容对齐和最小约束传播 |
| RowMeasurePolicy | 水平排列、间距、交叉轴对齐和 weight |
| ColumnMeasurePolicy | 垂直排列、间距、交叉轴对齐和 weight |
| MinSizeMeasurePolicy | 以最小约束完成空内容布局；Spacer、Image 和文本 Modifier 内侧的空 Layout 使用 |

本次撤销旧清单将 TextMeasurePolicy 作为 Layout 预制策略的要求。文本测量、baseline 和排版缓存归文本 Modifier 所在层；空内容 Policy 不读取宿主文本字段，也不与文本元素重复测量。MinSizeMeasurePolicy 在无子项时返回 constraints.minWidth/minHeight 与空放置过程，不因使用者是 Text 或 Image 获得特例。

- [x] Policy 是独立、可校验的输入，缓存不构成与 FA 的隐式绑定；局部参数变化只影响真实消费者
- [x] Box、Row、Column 明确选择相应 Policy；Spacer 使用 MinSizeMeasurePolicy
- [x] Text/Input 组合显示或编辑 Modifier 元素，将最终链与 MinSizeMeasurePolicy 交给 Layout；显示、编辑、焦点、光标、选区和 IME 全部进入同一 Modifier 实例协调与生命周期
- [x] 删除 Layout 的 textPresentation、text、value、textStyle 等宿主文本旁路及旧 TextMeasurePolicy 入口；保留并复用 TextLayoutService，不另起排版、绘制或输入几何算法
- [x] 文本元素处理链层约束和 baseline，padding/clip/transform 正常包裹文本；颜色更新不重排或重复排版，文本更新只触发必要阶段，回调与输入会话按实例退休
- [x] Image 使用 Layout、MinSizeMeasurePolicy 和 paint Modifier；Icon 调用 Box 并组合 paint/tint，不另造专属 Policy
- [x] 未来 JS MeasurePolicy 使用同一 Layout 契约，在受控测量阶段接收约束与子项测量能力，返回 typed MeasureResult；禁止异步等待、结构修改与任意事件重入，本期不伪造未实现 API

### 4.4 内建 Foundation Arrangable 正式确立必须 styleless

内建 FA 有行为但没有特征样式。禁止 Foundation Arrangable 带入背景、边框、圆角、阴影、装饰性 padding、主题色、默认设计系统字体或输入框皮肤。字体 fallback、文本测量、光标、选区、焦点和 IME 是行为或基础呈现，不等于装饰样式。

- [x] Text、Input、Image、Icon、Box、Row、Column、Spacer 均不偷偷注入主题装饰；Input 删除平台/设计系统默认皮肤，保留编辑、光标、选区、焦点和 IME 行为
- [x] FA 不使用 provide/inject 取得颜色、字体风格或其他样式；不恢复 LocalContentColor、LocalTextStyle 或其他 Local 样式系统
- [x] FA 若需要根本行为或宿主服务（例如字体解析器、资源服务），可使用正式 provide/inject；注入值不得暗中改变 FA 的视觉样式，必须在 prop 或正式行为契约中可追踪

- [x] 回归已定基础呈现：Text/Input 未传文字颜色时使用基础黑色，Icon 未传 tint 时保留 Painter 原色；字体与字号只使用基础排版 fallback，不读取主题

### 4.5 Painter 作为 Image/Icon 的资源与绘制边界

Image 和 Icon 不再直接接收 path、URL 或资源字符串并在实现内魔法加载；二者明确声明 `painter: Painter`。资源获取、解码、异步完成、失败、取消及释放属于 Painter 获取层，Image/Icon 只消费 Painter。

```text
资源来源与加载层
-> Painter
-> paint Modifier
-> LayoutNode 的测量与绘制能力
```

Painter 是正式的绘制能力对象，至少提供固有尺寸（可无）、可绘制内容及内容版本、失效通知、资源归属和释放语义。第一版资源加载管理可以简单，但必须输出 Painter，并处理完成、失败、取消和迟到结果；以后正规化资源系统只替换 Painter 获取与实现层，无需改 Image/Icon 契约。

Painter 的公开形态只表达绘制能力和生命周期，不开放任意绘制回调：

```ts
interface Painter {
    readonly intrinsicSize: Size | undefined
    readonly contentVersion: number
}
```

实际绘制操作由 paint Modifier 和 LayoutNode 的正式受体消费；Painter 可以由资源获取层创建，资源路径、解码器和缓存实现不进入 Image/Icon 的 prop 语义。

- [x] Painter 进入正式 UI 能力入口；不把任意 `onDraw` JS 函数冒充 Painter，不在绘制深处任意回调 JS
- [x] Image 声明 painter、contentScale、alignment 等正式 prop，代码定义调用 Layout、使用 `MinSizeMeasurePolicy` 并显式组合 paint Modifier
- [x] Icon 声明 painter、tint 等正式 prop，代码定义调用 Box 并显式组合 paint Modifier；tint 转换为 colorFilter，不读取主题色，不暗加默认尺寸
- [x] 删除 Image/Icon 的 path、source 字符串魔法加载和按标签名分派的资源路径；资源路径若保留，只能由独立资源获取 API 先转换为 Painter，再传给 FA
- [x] Painter 的固有尺寸、内容版本和失效归属接入统一 getter、Rearrange、LayoutNode 及帧阶段；资源迟到结果不能写入退休的 Painter 或 LayoutNode

### 5.3 RearrangeScope：可独立重启的重排作用域

**已拍板：**RearrangeScope／重排作用域是可独立失效、调度和重新执行的结构单位，纳入新的第一趴正式实现与验收，不能延后到第二趴。RearrangeNode 是 Layout 所属运行时节点，RearrangeScope 是可重启的结构执行单位；后者自身不增加 ArrangableInstance、RearrangeNode 或 LayoutNode，不向用户公开手动执行入口。

```text
ArrangableInstance
└─ 根 RearrangeScope
   ├─ 条件 RearrangeScope
   │  └─ 当前分支内的调用及内部作用域（只有 Layout 拥有 RearrangeNode）
   └─ 列表 RearrangeScope
      ├─ 条目 RearrangeScope（key=A）
      └─ 条目 RearrangeScope（key=B）
```

- [x] 编译器为根模板、a-if／a-else-if／a-else 分支链、a-for 列表及其条目生成明确的结构执行边界；内容调用按 3.2 建立调用作用域，不要求用户拆成大量小 SFA 来获得细粒度
- [x] 每个作用域保存所属 ArrangableInstance、父作用域、执行函数、存续调用账本、Layout 输出范围、依赖、脏状态及退休状态，并保留源码归属；作用域身份在所属调用和编译位置内确定，列表条目结合明确的 Rearrange key 或既定无 key 协调规则，不建立全局 key 身份
- [x] 结构读取在当前作用域内追踪，嵌套作用域建立自己的依赖；条件变化只唤醒对应条件作用域，条目内部条件变化只唤醒必要的条目或条件作用域，不重新执行根结构和无关兄弟
- [x] 列表作用域负责集合、条目身份与顺序，条目作用域负责条目内部结构；插入、移动、删除使用正式 Rearrange 协调，同 key 移动保留作用域，item/index 等词法输入改变时刷新闭包和实际消费者，不把无响应式读取的闭包永久当作常量
- [x] 分支切换退休退出分支内的作用域，保留分支选择作用域；条目删除清理依赖与待执行任务，迟到工作不得命中复用后的新身份；KeepAlive 停用暂停所属作用域，恢复按最新输入执行必要工作
- [x] 作用域只加入统一帧调度器的结构阶段；父子同时失效时先处理父层，已删除子作用域不再执行，保留的子作用域按最新输入处理，已经处理的脏版本不重复执行，新失效仍按依赖顺序有界处理
- [x] 普通 prop 求值和 Modifier 参数继续独立追踪，不回流到结构作用域；纯值更新可以不执行任何相关 RearrangeScope，不把 block 协调优化冒充独立作用域重启

本期落实上述明确边界，不建设完整 Snapshot 隔离、多线程重排或照搬 Compose 的全部 Group／dirty 位体系。依赖版本不冒充状态快照；统一 VSync 决定何时执行，RearrangeScope 决定执行哪里，两者共同参与正式调度。

### 5.4 原生、FFI 与生命周期的驱动边界

- [x] Layout 节点应用直达正式后端结构和输入操作，不再经过一棵通用 JS 宿主视图树；RearrangeNode、原生 ID/代际和 Modifier handle 分别管理
- [x] FFI 按明确类型接收节点操作、已校验的 Policy/Modifier 值与事件，管理 callback 引用和绑定代际；不传 JS getter 给原生绘制阶段，不建立序列化 command buffer 或第二套布局语义
- [x] 新建、使用、移动、停用、恢复与最终退休均能追踪到所属实例/作用域和 Layout；成功挂载/更新通知在对应提交成功之后，不能把 FFI 调用返回当作屏幕已经呈现
- [x] 重排准备变化与后端应用有明确边界；失败清理未提交的新建节点、实例、绑定及资源，不发布半成品，保留上一成功帧，不声称能回滚用户任意业务副作用

- [x] 第一趴接入现有 Owner/提交机制并提供结构/值任务的调度、取消及提交通知边界；第三趴统一生产帧授权时只接管执行时机，不再重造本趴的作用域、节点或 getter 协议

## 6．第一趴：删除 arrangeValue，内化全部 prop 的延迟求值

**已拍板，属于新的第一趴必做项，与重排和 RearrangeScope 同步完成：**内部 Arrangable 调用的每个 prop 一律提供 `() => T` 求值函数，不得裸传 T。动态值、固定字符串、固定布尔、常量、业务回调和 Ref 本体全部遵守同一协议。彻底删除 `arrangeValue(() => value)` 包装及其识别机制，不再保留“裸值或特殊包装值”双轨输入，也不换个 helper 名字继续包一层对象。

这是将延迟求值内化为默认协议，不是删除延迟求值、依赖追踪或独立值绑定。普通用户仍按模板语法传参，由 SFA 编译器生成 lambda；内建 FA 的代码定义与内部调用必须直接遵守相同协议。

### 6.1 全部输入生成求值函数，不按静态或动态分两条路

| 模板写法 | 内部 prop 求值入口示意 | 语义 |
| --- | --- | --- |
| `text="abcde"` | `() => "abcde"` | 固定字符串也必须包 lambda |
| `:text="'abcde'"` | `() => "abcde"` | JS 字符串常量也必须包 lambda |
| ``:text="`abcde`"`` | `() => "abcde"` | 无插值的 JS 模板字符串同样是常量 getter |
| `:text="abcde"` | `() => abcde` | abcde 是变量表达式，不能擅自变成同名字符串；实际编译遵守普通 Ref 解包规则 |
| `enabled` | `() => true` | 固定布尔值同样包 lambda |
| `:width="size + gap"` | `() => size + gap` | 整个表达式在求值作用域内执行，不在父层先计算再包裹 |
| `:on-value-changed="callable"` | `() => callable` | getter 返回业务回调，不执行 callable |
| `:onValueChanged="value => save(value)"` | `() => (value => save(value))` | 外层是参数求值，内层是业务回调 |
| `:oriRef="<documentRef>"` | `() => documentRef` | 外层仍是 getter，返回原 Ref 本体，不自动解包 |
| `:modifier="M.padding(gap)"` | `() => M.padding(gap)` | 保留正式 Modifier 参数细分优化，不恢复 arrangeValue 包装 |

上述为语义示意；源码位置、常量证明等元信息可以另行记录，但不能要求用户或 FA 用包装对象标记“这是动态值”。长写 a-bind、动态参数名及 `.camel` 的值部分遵守同一协议，名称规则不改变取值规则。

内部类型职责示意：

```ts
type PropGetter<T> = () => T
type PropInputs<P> = { [K in keyof P]: PropGetter<P[K]> }

const inputs = {
    text: () => 'abcde',
    modifier: () => M,
    onValueChanged: () => callable,
}
```

getter 的位置由协议确定，不以 `typeof value === 'function'` 猜测是否需要求值。声明为函数的业务 prop 也先经过外层 getter，绝不能裸传 callable 后被运行时误执行。

### 6.2 独立求值、精细订阅与常量缓存

- [x] 每个参数求值入口由独立的值消费机制管理依赖、缓存与更新；不得在父层 RearrangeScope 中批量调用全部 getter，导致所有 Ref 读取重新订阅到整个结构
- [x] 接收方声明的是结果类型：`defineProps<{ text: string }>()` 的 `props.text` 仍是字符串，不要求用户写 `props.text()`；内部 getter 协议不泄漏为用户 prop 类型
- [x] 父层参数变化只唤醒实际读取它的消费者；被结构条件读取时才影响对应 RearrangeScope，被原生值绑定读取时只更新对应输入，不无条件重新运行整层结构
- [x] 可证明不变的输入在每次存续的调用实例中初始化求值一次并缓存，仍以 lambda 交付，不为常量开放裸值通道；结构再次执行、无关状态变化或无关帧不得重复求值该常量
- [x] 可复用无捕获的常量 getter 函数，但求值缓存归所属调用或绑定，不把有状态结果跨实例错误共享；不能仅因 getter 函数身份新建就判定参数值已变化
- [x] 一次执行没有读到 Ref 不代表永久不变：列表 item/index、Slot 词法环境和参数来源替换时，刷新闭包及必要求值，退休旧依赖；`() => index` 不得被误缓存为首次位置
- [x] 原样 Ref 的 getter 不读取 `.value`，Ref 内容变化不会仅因传递本体触发结构执行；下游实际读取 `.value` 的消费者正常订阅，替换 Ref 时按新身份更新并清理旧依赖
- [x] 动态参数名和对象绑定区分参数形状与字段值：最终逐 prop 建立 getter，不在结构作用域提前展开求值全部字段；普通 JS 已经执行的表达式不能由运行时反推，编译转换须保持原求值顺序与副作用语义
- [x] 未传 prop 按明确默认值契约处理，默认值结果同样进入统一求值与缓存机制；保留每实例默认值工厂的时机和独立性，不以静态优化偷偷共享可变默认状态
- [x] 名称、必需性、重复参数在最早可确定的边界检查；动态结果在独立求值入口校验，错误值不得继续进入原生受体，求值报错保留 SFA/FA 来源

### 6.3 编译、FA、运行时和原生消费者一并迁移

### 8.1 DynamicArrangable：动态调用定义

DynamicArrangable 自己明确声明 `is` 和 `props`：`is` 接收 Arrangable 定义，`props` 接收目标调用的参数对象。两层参数边界分别成立，不接受未声明的顶层参数后再整体转交目标。

```axml
<DynamicArrangable :is="currentPage" :props="{ document }" />
```

这里 currentPage 是 SFA 或 FA 的定义值，例如导入的 Overview；也可以是保存该定义的 Ref，经模板解包后传入。用户只是在选择定义，实例创建仍由模板调用和运行时完成。

| 写法或输入 | 结果 |
| --- | --- |
| `<DynamicArrangable :is="Overview" :props="{ document }" />` | Overview 定义合法且声明兼容的 document 时成立 |
| `<DynamicArrangable :is="Overview" :document="document" />` | DynamicArrangable 自己没有声明 document，报错 |
| `is="Overview"` | 固定字符串不是 Arrangable 定义，报错，不按名称查找 |
| `:is="null"` | 报错；无内容时用 a-if 明确表达 |
| is 收到 ArrangableInstance、LayoutNode、RearrangeNode、普通函数/对象或 Promise | 报错；异步加载须完成并取得定义后再显式选择 |

- [x] 按 is 的定义身份验证目标；编译/类型工具尽早检查目标与 props 的兼容性，动态选择在运行时按目标声明检查
- [x] 定义、参数与内容作为一次完整调用输入校验和应用，不先切换目标再以旧目标的参数执行新实例
- [x] 定义与调用身份均不变时保留实例并更新参数；定义变化或Rearrange key 变化时退休旧实例并建立新实例，需要缓存退出内容时使用 KeepAlive
- [x] 动态内容交付属于该 FA 的明确调用职责，目标 Slot 名称按定义校验；不窥探 Slot 内部结构，也不恢复 scoped slot 参数协议

### 8.2 KeepAlive：保存整份内容实例的逻辑生命

KeepAlive 缓存的是默认 Slot 一次调用对应的内容实例作用域，包含其创建的全部 Arrangable 实例、局部状态、后代与上下文关系。内容可以有零个、一个或多个 Arrangable，不要求默认 Slot 恰好一个孩子，不窥探孩子来猜缓存对象。

```axml
<KeepAlive :cacheKey="pageId">
    <PageToolbar />
    
    <DynamicArrangable :is="currentPage" :props="{ document }" />
</KeepAlive>
```

KeepAlive 明确声明 cacheKey，用于选择其内部的内容缓存记录。普通 Rearrange key 标识 KeepAlive 自身，二者不可混用：`<KeepAlive :key="pageId">` 会改变 KeepAlive 调用身份，不表达在同一缓存所有者内切换页面。

```text
KeepAlive 实例
    cacheKey A → 内容实例作用域 A
    cacheKey B → 内容实例作用域 B
```

| 内容状态 | 执行规则 |
| --- | --- |
| 活动 | 正常重排、值更新、动画、原生节点及交互 |
| 缓存停用 | 保留逻辑实例和局部状态，暂停 UI 执行，退出原生视觉与交互资格 |
| 销毁 | 逐出或所有者卸载时最终清理作用域、订阅、回调和缓存记录，不可复活 |

- [x] KeepAlive 使用统一实例初始化与内容作用域保留机制，不使用专属 createState、retainsContent、ContentHost 权限或 VNode 字段复制；保留不创建新的 RearrangeNode，后端资源仍由内容中的 Layout 管理
- [x] cacheKey 切换时旧内容进入停用；返回已有 cacheKey 时恢复该内容作用域，以当前输入执行必要重排，不将外部词法变量冻结成快照
- [x] 缓存内仍遵守普通重排身份规则：同一记录内某位置的定义改变，仍须替换该位置实例，不能用缓存身份强行保住不兼容定义
- [x] 停用期间不执行结构重排、值提交及内容作用域的普通响应式任务；依赖变化记录为待处理，恢复时按最新状态处理
- [x] 停用动画不持续申请视觉帧；内容不参与绘制、命中、焦点、指针捕获或输入，失去活动资格的 IME 会话正确结束
- [x] 被保留内容的实例与 Layout 所属 RearrangeNode 保留逻辑归属；原生 LayoutNode、Modifier 实例与回调绑定在停用时可退休，恢复时由原 Layout 链路重建实体并重新物化 Modifier；不承诺原生 ID 或 handle 永生，迟到写入不得命中已退休目标
- [x] 编辑文本、滚动位置、动画当前值等应保留的可观察状态，明确归入逻辑状态或原生保存/恢复机制，不能因退休 Node 而丢失；焦点、捕获和 IME 会话不自动恢复抢占

- [x] 提供正式激活/停用生命周期通知，供显式外部订阅处理暂停与恢复；暂停 ReactiveEffect 不冒充自动暂停网络等外部工作，也不为通知暴露实例对象
- [x] 持续后台工作的业务状态归更长寿的外部作用域，由内容消费，不用 KeepAlive 偷偷维持隐藏页面的全部工作
- [x] 缓存具有明确的有限容量与逐出策略，具体默认值随实现声明；逐出和 KeepAlive 自身卸载都执行最终清理，不能只删除 Map 引用

### 8.3 上下文与后续展示能力

上下文依赖只使用 provide/inject。肃清 createArrangeLocal、provideArrangeLocal、useArrangeLocal 及其同型便捷封装；确需保留的上下文值使用明确的注入 key 和默认策略。Foundation 组件不得用 provide/inject 取得颜色、字体风格或其他样式（即我说的严正 styleless）；只有字体解析器、资源服务等与根本行为有关的宿主服务才可显式注入，且不能偷偷改变视觉样式。保持响应式上下文的依赖关系，不读取一次就误冻结为快照；通过 prop 显式传递 Ref 本体遵守 1.3，不改变 provide/inject 的上下文职责。

- [x] 应用级默认提供值在 `createApp` 创建 `provides` 后立即注册，后续用户自己 `app.provide()` 和在 Arrangable 内（作用域级）`provide` 可覆盖默认值。此规则适用于 Density，也适用于未来的本地化及能力接口；统一使用 AppContext 与既有 provide/inject 查找链，不为注册默认值增加内部根 Arrangable，也不让 RearrangeSession 承担服务装配
- [x] 只有必须依赖挂载目标的资源才在 `mount` 中初始化，并在卸载或挂载失败时清理框架创建的资源；不擅自销毁用户提供的对象。挂载后的动态环境更新通过已注入对象的响应式状态进行，不把替换 provides 表中的对象误当作已建立消费者会自动重新注入

异地展示若日后确有需求，可以另行设计明确的 Popup、Overlay、Dialog 能力；不是本期为了删除 Teleport 必须顺带新增的一整套功能。

## 9．错误在最早可确定处诊断，真实边界保证契约

注：主人不建议一种情况搞出多次（多点）、繁复检测，以造成代码量激增（维护繁琐）、性能羸弱。

| 情况与反例 | 最早诊断处 | 动态或原生边界职责 |
| --- | --- | --- |
| `<Row>恩情</Row>`、`<Row>{{ title }}</Row>` | 模板编译 | 内部组合入口也不得把字符串悄悄转成节点 |
| `<MissingArrangable />` | 能确定定义的名称解析阶段 | 动态目标解析失败时拒绝，不回退为宿主字符串 |
| `<Mamba :undeclared="value" />` | 已知目标声明时检查 | 动态参数对象在 Arrangable 参数入口检查 |
| `<Text :text="someObject" />` | 能确定类型时诊断 | 动态值进入消费者前检查，不 String 强转 |
| `<Input><Text text="子内容" /></Input>` | 已知 Slot 契约时检查 | 动态内容入口拒绝未声明内容 |
| 已退休绑定写入、错误节点关系 | 通常不能静态确定 | 原生身份、代际、结构与事务有效性检查 |

- [x] 编译诊断和动态参数检查使用同一份正式声明，不分别维护一套规则
- [x] 区分模板转换、TS 类型检查和打包：能转译、能 bundle 不代表参数类型检查已经完成
- [x] 明确运行时可验证的类型与约束，不假装完整执行 TypeScript 类型系统；无法提取的声明不能悄悄变成任意值
- [x] 非法参数在执行对应逻辑前失败；开发和生产同样拒绝，禁止 warn 后继续
- [x] 不在每层重复检查同一事实；Arrangable 参数错误在其入口终止，原生检查自己的输入、身份和结构
- [x] 下层提供具体错误，上层补充来源并统一报告，保留文件、位置、Arrangable 名、输入名、预期与实际类型
- [x] 原生构建失败保留已发布场景与帧，不宣称 JS 副作用也可回滚

验证正向契约和实际不变量即可，不写一大批断言逐个封禁 Web 词汇。删除能力的消费者与解释基础，比保留实现后四处增加拒绝判断更彻底。

## 10．单位转换、生命周期与帧阶段使用统一执行链路

**已拍板：**Arrange TsSide Runtime 与 Arrange Framework 使用一个 UI Owner、一个统一调度器、一个生产视觉帧源。业务任务及时执行，视觉工作在 VSync 授权的帧内执行。本节已完成自动化验收，对应长期规则见 [调度线程与帧阶段](../../../arch/26-调度线程与帧阶段.md)。

### 10.1 一个 Owner，两种执行边界

- [x] UI Owner 采用 JUCE message thread，统一拥有 QuickJS、Arrangable 作用域与原生 UI 状态；可以按职责分队列，但不能形成各自独立冲刷 UI 的调度循环
- [x] 普通任务边界及时处理输入语义回调、资源及异步完成、Promise 后续任务，不要求这些工作等到 VSync
- [x] 状态写入立即生效，同步读取可见最新值；Ref、按需计算的 computed 保持正常语义，视觉消费者只登记失效并申请帧
- [x] 同一帧前多次状态变化可以合并视觉求值，不能合并或吞掉业务操作；三次点击各自执行累加，即使最终只更新一次显示，结果仍须增加三
- [x] VBlank/VSync 是唯一生产视觉帧源；重排、UI 值绑定、动画采样和原生输出统一受帧阶段管理，不再用微任务提前执行一轮视觉更新
- [x] 无 peer 或不可见时可以暂停视觉工作，但语义任务、取消及最终销毁不得依赖下一次 VSync 才能完成；空闲且无失效、无活动动画时无需每帧执行流水线

### 10.2 明确一帧的执行顺序

正式帧顺序如下，阶段名称是职责描述，不冻结内部类型命名：

1. 完成本帧接纳的普通任务及其微任务检查点，不无限吸入新任务
2. 确立本帧输入截点与唯一帧时间戳；后续到达的外部输入进入之后的处理机会
3. 按该时间戳采样活动动画，收集它们引起的失效
4. 执行重排与 UI 值绑定，处理必要的父子参数传播和动态依赖，形成一致的提交输入
5. 封存提交，按序应用原生事务，执行所需测量、放置、绘制及命中数据构建
6. 成功后发布一份一致的帧结果
7. 执行对应的提交后生命周期通知；通知引起的新视觉失效归下一帧

- [x] 阶段职责显式建模，不的依赖什么鸡巴 Vue job 的数字排序暗示职责；保住结构和值更新分离、父子传播及实际读取建立的依赖
- [x] 不规定每个 effect 每帧最多执行一次来截断合法依赖传播；稳定过程必须有界，结构表达式不得依赖写状态后反复执行才能收敛
- [x] 同帧动画使用同一时间戳；重排中新建动画以当前帧时间初始化，不二次推进时间或另发一帧
- [x] 新 Foundation/LayoutNode 应用入口使用正式结构操作、绑定注册退休与 typed 输入更新，保留有序提交和候选帧发布
- [x] 不绕过原生失效、FramePlan、测量/放置/绘制构建及 PublishedFrame，不在参数 setter 或组合回调里直接绘制
- [x] 原生应用、测量及绘制构建阶段不回调任意用户 JS；禁止嵌套事件派发和帧流水线重入，提交后回调不能递归发布第二份原生帧
- [x] 首次视图创建与重排同样受帧授权；模块加载等准备工作可提前完成，但不能以初始化为由绕过视觉执行边界
- [x] 明确重排完成、布局完成、帧发布和屏幕实际呈现的差别；VBlank 时间戳及 PublishedFrame 均不是显示器已经呈现的证明

### 10.3 微任务保留，nextTick 不再等待重排

- [x] 宿主显式驱动 QuickJS 的 `JS_ExecutePendingJob`，在外层宿主任务或回调返回后执行规定的微任务检查点；不在每次嵌套 FFI 返回时排空微任务，不另引入一套 QuickJS 标准事件循环
- [x] 彻底移除 Vue `Promise.then(flushJobs)` 独立执行重排和 UI ValueBinding 的权限，移除 JS 宿主 `queueMicrotask` 自行冲刷原生视觉提交的路径，由统一调度器接管阶段推进
- [x] nextTick 只保留微任务等待语义，不等待重排、布局、帧发布或实际呈现；明确其检查点与回调顺序，不把它定义成无限排空未来任务的承诺
- [x] 肃清（删除旧实现，重写新实现）依赖旧 Vue nextTick 等待结构更新语义的调用者与测试，这是正式 breaking change；若需要等待提交，使用另行明确设计的提交信号，不给 nextTick 偷加双重语义
- [x] 逐项明确 watch 的 pre/post 对应阶段与所属作用域；UI 相关观察遵守帧阶段，sync 观察不得直接启动视觉流水线，也不能靠改名保留第二套 UI 调度

验收例：修改影响模板的状态后，只推进微任务并 `await nextTick()`，同步读取能取得新值，但重排和发布计数均不增加；推进手动原生帧源后，才执行必要视觉工作。

### 10.4 生命周期跟随作用域与提交

- [x] 实例创建、setup 及相关依赖建立发生在对应首次重排中；mounted、activated、updated 等成功通知在对应提交成功后发出，不宣称已经呈现
- [x] 独立值更新不凭空产生一次结构 updated；成功通知与实际完成的工作对应，失败候选不能冒充挂载或更新成功
- [x] KeepAlive 按本篇 8.2 的作用域规则暂停和恢复任务；停用内容不执行 UI 工作，不妨碍其他存活作用域的语义任务，恢复所需视觉工作进入正式帧
- [x] 停用资格撤销、外部订阅的暂停及输入会话结束及时处理；激活/停用成功通知与对应提交关联，最终销毁、reset 和资源清理在 Owner 上及时完成，不等不可到来的帧
- [x] 异步工作明确所有者、请求身份、取消和代际；Promise 不因作用域销毁自动取消，迟到完成不得复活已销毁内容或访问退休节点
- [x] 发布的原生状态保持一致，不承诺回滚已经执行的 JS 副作用；失败后的清理与恢复按明确错误路径处理

### 10.5 JS 与原生之间保持明确的 FFI 边界

- [x] 同一 Owner 上的同步 FFI 用于有界计算、读取明确快照及捕获 typed 操作，不同步启动布局或发布，不在原生应用期间重入用户 JS
- [x] 结构事务与值槽批次保持顺序和身份校验，在正式阶段提交；一体化不等于强制拼接成巨型 JSON，也不等于消除必要的职责边界
- [x] 重 I/O、解码等工作移出 Owner；辅助线程只传递不可变结果及身份，由 Owner 接收，不跨线程访问 JSValue、QuickJS runtime 或 UI 树
- [x] 音频线程使用符合实时约束的非阻塞通道，不调用 QuickJS，不等待 UI Owner

### 10.6 事件保序，按身份判过期

- [x] 建立 Owner 入口的事件顺序号与时间戳，携带适用的 runtime/context 代际、目标或回调代际、手势或请求身份，以及关联的已发布命中场景版本
- [x] 点击、按下、抬起、取消、按键、文本及 IME 提交、手势开始和结束等离散语义保序交付，不因等待时间较长或跳帧而丢弃
- [x] 绝对位置、悬停和视口快照可在离散事件屏障之间合并；`move → down → move → up` 中的两段 move 不能跨 down 合为最后一个位置
- [x] 滚轮、拖动等增量只有在能证明语义等价时才聚合；边界裁剪、方向反转、嵌套滚动和速度估算等不能被简单求和破坏
- [x] 已销毁上下文、已退休回调、无效目标或已被新请求替代的资源结果可拒绝；不得把旧事件重新投递给复用了数字 ID 的新节点
- [x] 场景版本变化本身不是事件过期的充分条件，毫秒年龄也不是丢弃点击或 IME 的充分条件；按真实身份与语义有效性裁定
- [x] 邮箱有明确容量与背压、合并及过载处理策略，不能靠无界堆积或静默删除离散事件维持表面流畅

### 10.7 跳过中间画面，不跳过业务动作

- [x] 不积压并补跑过时的视觉帧票据；错过帧后，在下一次视觉机会按最新有效状态与时间执行
- [x] 动画按时间推进，不按执行次数乘固定 16ms 推进；必要的积分器可使用有界内部子步，不因此额外发布中间帧
- [x] 未完成或失败的候选保留上一份成功发布帧，不对外发布半份 JS/原生事务结果；跨帧继续工作须明确一致性，不能将任意执行点视作可安全暂停点
- [x] 预算同时关注任务数量、实际耗时、递归失效与邮箱压力；仅限制 PendingJob 数量不足以约束一个长回调
- [x] QuickJS 中断是终止执行，不是可恢复的时间片暂停；需要配套异常与恢复处理，不把它当作任意 JS 任务的续跑机制
- [x] 测试使用同一生产调度器与可控原生帧源，记录帧身份和阶段计数，不另外模拟一套调度算法
- [x] 帧内结构调度以 5.3 的 RearrangeScope 为独立执行单位，保留父先子后及退休任务取消；原生阶段按实际失效范围工作，不因局部重排恢复全树扫描或无条件重建

### 10.8 删除 rAF，动画直接纳入统一帧泵

- [x] 正式删除 requestAnimationFrame/cancelAnimationFrame，包括原生安装的 JS 全局函数、类型声明和运行时依赖，不保留兼容别名，也不换个名字公开同样的手工逐帧循环入口
- [x] 用户动画统一采用 Compose 模式的 Arrange animated 系列与 Transition 类（Transition 对齐 Compose的androidx.compose.animation.core.Transition）；其内部采样、完成和取消直接纳入统一帧泵与作用域生命周期，不再经由 rAF 协议
- [x] 替换当前 defaultAnimationClock 对 rAF 的依赖；仍需存在的异步加载延迟等内部帧期限工作接入正式宿主调度，随所属作用域取消，不为保留它们而留下 rAF
- [x] 整理动画时钟注入和手动时钟的生产/测试边界，不让这些入口成为用户手工动画帧循环的替代品

删除前的事实仍需准确记录：当前原生 requestAnimationFrame 仅登记回调，由 VBlank 帧泵推进，并非另起浏览器帧源；本次删除是正式收紧动画编程模型。统一 VBlank 帧泵和内部动画采样职责继续存在。Promise/微任务调度与逐帧动画协议不是同一种能力，不因删除 rAF 而一并删除 nextTick。

### 10.9 单位区分、Density 与 SFA 包装消融

本节已完成第三趴实现与自动化验收。目标是保留单位语义、转换职责和响应式依赖，不要求靠持续分配包装对象实现区分。长期契约已同步至 [基础类型](../../../arch/10-基础类型.md)，模板规则同步至 [SFA 与模板写法](../../../arch/33-SFA与模板写法.md)。

**已拍板的边界：**`px` 是后端布局和绘制坐标单位，当前就是 JUCE 逻辑像素；Arrange 不接管 JUCE 的设备像素缩放。`dp`、`sp` 是前端声明单位，必须在前端经过 Density 转换成 px（当前Density默认实现中为 1∶1转换，虽然**无趣**，但这转换职责不能缺位）。原生只接收 px，不建立第二套原生 Density 或 dp/sp 换算链路。保留这些边界是为了其他后端及不同转换环境的扩展。

- [x] 在 Framework 的 UI 能力层建立 Dp、Sp、Px 与 Density 契约，由 `@arrange/framework/ui` 导出；Density 不归属响应式核心、编译器或原生层，dp 与 sp 的转换明确分开，不用无单位的 `toPx(number)` 猜测含义
- [x] 每个 App 按 8.3 的应用级默认提供规则注册默认 Density，局部覆盖复用正式 provide/inject 与实例上下文；不得搞什么全局当前倍率或逐个 FA 转传的 Density prop。Density 是单位转换环境，不是主题或样式注入，不改变 Foundation 的 styleless 约束
- [x] Layout Arrangable 在 setup 中提取 Density（的群众演员）；读取 Modifier 链的值绑定中执行 dp/sp → px 解析，MeasurePolicy 中的单位参数在对应绑定中同样解析。转换发生在依赖追踪开启的读取阶段，不放进暂停追踪的原生写入回调，也不在 Modifier 构造时按偶然环境提前换算
- [x] 保持前端声明与原生 px 输入的明确职责：不修改原始 Modifier 或 Policy；同一声明被多个 Layout 使用时，各自按注入的 Density 解析。保留 Modifier 实例身份、局部元素更新和相等结果抑制，不恢复全链或全树无条件重建
- [x] 注入取得环境后，转换执行时读取其响应式配置；环境变化使实际消费者失效，经第三趴统一值阶段与事务提交更新。纯 px 消费不依赖 Density，停用与销毁遵守作用域规则，恢复使用最新环境；不能要求用户重新设置 prop 才刷新
- [x] 逐项确定公开参数和内部字段的单位：声明式布局尺寸、间距、padding、布局 offset、圆角及边框宽度采用 DP，字号和文本行高采用 SP；后端约束、测量结果、绘制与命中坐标采用 PX。比例、权重、数量等不误当长度；其他带尺寸字段必须明确所属单位，不批量把所有 number 改称 DP
- [x] 普通 `.ts` 保持标准 TS 执行语义，不要求专用 transform 或新扩展名；允许在单位契约明确的位置手写 number，例如 width 的数字输入表示 DP。单位区别由正式参数、字段或操作保留，不能让同一个裸数入口自动猜 DP/SP/PX，也不宣称可以追踪任意普通 TS 数字的来源
- [x] SFA 中的单位值显式表达单位（用户在SFA中不得裸传数字，在ts中才是裸传数字，背后的原因：SFA要作此消融Transform，而是TS不带（因不需）Transform），已有单位类型的变量可以传递；编译器识别正式单位构造及消费契约，消融包装后生成与普通 TS 相同的声明输入。禁止仅按函数名字替换，须处理导入身份和遮蔽；消融和运行期 Density 转换“无关”（即不影响 Density 转换的继续会搞。消融≈编译Kotlin时DataValue的拆箱。但消融后，和ts一样，数字作为Param有“意味”，代表Dp的数字在处理链路上仍途经Destiny的处理）
- [x] 覆盖 SFA 的变量、条件、prop、函数参数及跨模块消费：通过明确单位契约保留含义，无法确定时要求明确声明或转换，不在删除包装后凭裸数猜测。已知单位不匹配在最早可确定处诊断，动态输入由其正式边界负责，不沿链路重复叠加检查
- [x] 完整迁移嵌套 Padding、Shape、文本样式及默认值、布局策略间距和动画输入；前端声明样式与提交给原生的 px 样式区分。声明单位动画在对应单位域采样后转换，原生几何动画使用 px，阈值等参数的量纲明确，不因 Density 更新无故重启动画
- [x] 滚动位置与范围、测量和输入反馈保持 px，Painter 固有尺寸按后端坐标契约解释；资源源像素与固有尺寸的适配不冒充 Density 转换。需要把 px 反馈用于 dp/sp 声明时提供明确转换，不丢弃来源单位后随意套用
- [x] 颜色沿用明确的 Color 语义与构造契约，不把 ARGB 当长度或交给 Density；模板中的颜色包装优化同样不得丢失消费契约或必要的值校验
- [x] 提供非恒等 Density 验收，例如 DP 乘 2、SP 乘 3、PX 直通；覆盖同一 Modifier 在不同上下文复用、只改 Density 的刷新、无关消费者不执行、相等 px 不提交、停用恢复及失败保留旧帧。验证 SFA 消融与普通 TS 输入结果一致，文本、布局、滚动、命中及 IME 坐标一致，不能只凭默认 1∶1 下画面正常宣布完成

### 10.10 Text 参数改名

- [x] 将 Text 的 `textStyle` prop 及 text Modifier 的选项和内部字段改为 `style`，同步定义、模板调用、Demo、测试、诊断和当前 API 文档；旧 Text 调用不保留兼容别名。Input 与 TextFieldOptions 仍用 `textStyle`，TextStyleProp 等类型名称不改。这只是对应参数改名，不扩展为文本模型重建
