本文记录 M2.3 的具体施工任务。M2 按任务组织，不按时间、工期或阶段性凑数组织。

M2.3 的核心目标是把 Arrange 从“外部 Vue renderer 驱动 native UI”的形态，推进为“内部 Arrange Vue 与 Arrange runtime 一体化驱动 native UI”的形态。

M2.3 只有这个大方向：改造出并接入 Arrange Vue，完成内部运行时正规化。

Arrange Vue 不完成，就搞不出来我要的恩情。

# 总原则

M2.3 不允许“最小闭环”“兼容性实现”“过渡期实现”“先做一点以后再说”这类口径。项目还不是完全体，旧实现没有兼容性价值。`/docs`的文档中的最终目标是最终事实源，本`/m2`下的文档要求达到的是本期任务的目标，旧代码只要不符合最终目标，就必须被替换、删除或重写。

施工原则：

- 交付状态是0%和100%的，要么做了，要么没做：不可拿所谓“最小闭环”糊弄主人。
- 不保护旧实现，完全打破：对一个方面进行重写时，重写必须是严格彻底的，不应保留任何历史代码，宣称什么“兼容性”也是非法的：我们没有历史包袱。
- 链路必须统一，任何核心逻辑不能“多头维护”，只能有存在单一地方的、真正的最佳实现。
- 不用“先跑起来”替代真正的底层都好干的实现。
- 不允许表面 API 看起来完成、内部仍靠字符串、魔法字段、旁路调度糊住。
- 每个任务都必须保证最后有生产实现、内部模型、干净的生命周期、克制精简（不能高很多）的必要性持久测试项。
- 继续遵循主人的码风：C / C++ 新代码遵循 Google 风格；TypeScript / JavaScript 默认不可带有行末分号，除非不加会导致语法错误；代码缩进 4 个空格。

### 1．重写原生 UI 执行模型：Modifier、布局、绘制、命中一起改。已完成

这一批不是“给 `CompiledModifier` 加实例 ID”，而是替换它所代表的聚合模型。

施工顺序：

1. **定义 descriptor 与实例的边界。**  
   Descriptor 是有序、类型化的元素描述；原生协调生成实例链，实例拥有身份、输入、生命周期及必要的阶段数据。类型、当前位置和实例身份分开。明确无 key 重复元素的匹配规则，以及显式 key 的作用；handle 不因数组下标变化而变化。

2. **实现协调与退休。**  
   处理复用、参数更新、插入、删除、替换。实例退休时解除绑定和交互资源；迟到更新不能命中新实例。这里同时确定后续 slot 要使用的目标身份。

3. **重写测量和放置。**  
   按 Modifier 包裹顺序传递约束、返回尺寸、记录各层几何及放置关系。测量结果保留，放置可以单独执行。padding、required size、offset、scroll 等在自己所在层生效，不再靠最后一个节点矩形推算整条链。

4. **重写绘制和命中。**  
   两者消费同一套层级几何及变换关系。background、clip、graphicsLayer、交互元素按其所在位置执行；重复元素独立存在。绘制有正确的进入、内容执行、退出顺序，命中有对应的坐标逆变换和裁剪范围。

5. **改写 QuickJS reader 与 Framework descriptor。**  
   JSValue 直接解码成类型化描述；协调、输入校验和失效语义归原生统一实现。事件回调必须关联具体交互实例，不再让同一节点上的重复 clickable 共用唯一槽位。删除旧的 transform/input 等聚合路径。

这一批会一起动 `Modifier`、`Layout`、`Paint`、`HitTest`、滚动和指针分发、QuickJS reader，以及相关测试。**不留下“新实例链外壳、内部仍调用旧聚合算法”。**

退出证据：真实 Demo 使用新模型；覆盖重复元素、顺序变化、插删复用、内外层尺寸、变换与裁剪后的命中，以及实例退休。第 1 步结束时，“更新哪一层”和“这一层包裹什么”都已有确定答案。

### 2．重写提交与帧执行：让结构、绑定、原生阶段形成一条正式链路。已完成

这一批建立原生运行时对 JS 的正式契约，并接入现有 Framework。不会只定义一个没有生产调用者的 `SlotUpdateBatch`。

施工顺序：

1. **定义类型化输入与 binding 生命周期。**  
   目标包括 host 输入和具体 Modifier 实例输入。Binding 注册时确定目标、输入类型与所有者；更新携带 binding 身份及代际；解除绑定、节点删除、实例替换、reload、context reset 都能使旧更新失效。  
   **不使用任意字符串字段加调用者指定 dirty flag。** 哪些阶段失效，由原生输入语义和实际差异决定。

2. **实现统一提交单元。**  
   结构 mutation、binding 注册与退休、typed 值更新、事件变更进入同一次提交，明确应用顺序。处理同一批次内“创建后写入”“替换后旧绑定写入”“删除后迟到写入”等情况。结构与值可以分开表达，但必须共同确定一帧的状态。

3. **接通真实 QuickJS 与 Framework。**  
   正式提供注册、更新、释放入口，现有 runtime 经这些入口提交。此时还没有第 3 步的模板独立依赖追踪，但已经使用将来同一套生产协议，不另造演示接口。

4. **统一调度与动画入口。**  
   输入、资源、resize、reload 请求工作；VBlank 组织视觉帧。每帧采样动画一次，再稳定处理 JS 工作和提交队列，最后封闭本帧输入。删除生产视觉帧的 timer fallback，以及输入回调中另行直接跑视觉流水线的旁路。ManualVBlankSource 调用同一个入口。

5. **真正拆开原生阶段。**  
   分别执行 measure、place、绘制构建、命中构建、发布。颜色更新跳过测量和放置；offset 更新复用测量结果；尺寸更新进入测量；回调替换不重建无关画面。命中构建必须产出真实可用结果，不能只在日志里写“已失效”。

6. **确立发布与失败边界。**  
   构建中的场景结果与已发布帧分开，绘制和输入不能消费不同版本的几何。明确提交校验失败、阶段执行失败、reload 时保留或替换什么，以及如何恢复。`paint` 只消费已发布内容。

同步加入实际执行计数：提交、拒绝的过期更新、活跃 binding/实例/回调、测量、放置、绘制构建、命中构建、发布。计数来自执行位置，不来自计划中的布尔值。

退出证据：真实 QuickJS App 在同一 FramePlan 内提交结构和值；阶段跳过、生命周期、失败恢复和被动 paint 都有行为验证。这里先保证阶段分离正确，后续性能批次再收紧到局部子树和缓存。

### 3．重写 Arrange Vue：反应式执行域、模板编译、组件传值一起落地。已完成

这一批不以“复制 Vue 并换包名”为完成，也不把 native slot 接口存在当成 Vue 已接通。

施工顺序：

1. **建立反应式执行域与调度归属。**  
   保留 Ref/reactive/computed 的动态依赖基础，加入结构执行域、值绑定执行域及其所有者和清理机制。读取发生在哪个执行域，就订阅哪个消费者；Ref 本身没有固定阶段用途。执行域调度接入第 2 步的统一帧模型。

2. **改模板编译与运行时协同。**  
   模板生成可重执行的结构部分，以及存活期间独立更新的绑定。先把 host 输入、文本、事件回调表达式和整条 Modifier 表达式打通，再接条件分支、keyed 列表及动态节点。结构协调时明确绑定是保留、迁移还是销毁，不能每次 render 都无条件重建。

3. **改组件 props 与 slots 边界。**  
   父表达式独立更新子组件只读反应式 props，由子组件实际消费者响应；移除“prop 变了就必然重跑子 render”的前提。一起处理动态 slots、默认值、attrs 等保留语义，避免用户封装组件后优化失效。

4. **打通普通表达式和 Modifier 协调。**  
   TS helper、computed、条件表达式正常参与动态依赖追踪。整条 Modifier 表达式在独立 binding 中求值，再协调到原生实例；先把通用语义做正确，不把“必须传 Ref/getter”强加给用户，也不承诺追溯普通 TS 已经读出的值。

5. **收齐 Vue 的执行与生命周期语义。**  
   接入 watch 的调度顺序、事件执行、组件生命周期、错误处理、分支清理和作用域释放。保留一次 setup；不照搬 remember。明确 `nextTick`、逻辑挂载、结构更新与原生布局/帧完成的区别。

6. **切换 SFC/Vite 和真实 Demo 主链路。**  
   编译、运行、开发重载统一走 Arrange Vue。移除本次已被替换的 Vue/VNode 更新旁路与 Web 假设，不等待后面的“清理批次”替核心语义收尸。

退出证据：真实 Demo 中，颜色和位置动画穿过多层组件、computed、helper、slots 仍走独立绑定；文本变化进入必要的原生测量；同一个 Ref 同时驱动结构和颜色时，两条依赖都正确；列表重排、分支删除、组件替换和 HMR 后没有错绑或泄漏。

**三步之间的关系是：第 1 步确立原生执行语义，第 2 步确立提交与帧契约，第 3 步让 Vue 的编译和反应式执行真正使用这套契约。** 跨步接口提前设计，跨模块修改直接做；施工中的断裂逐项接完，不再用保住旧实现的方式回避重构。

### 8．文本排版资源化，统一测量与绘制复用。待实施

本 Part 与第 9 Part 是在第 1–7 步基础上追加的正式任务。

**目标：**文本节点保留可复用的排版成果，测量和绘制消费统一结果；颜色、透明度、位置、滚动等不影响排版的变化不重新排版。正式 `paint` 只消费已准备、已发布的文本资源。

参考 Compose 的节点排版缓存、测绘共用和有限测量缓存，但实现按 Arrange、JUCE 和 DrawOps 的实际能力设计。Compose 不是行为正确性的最终依据；不引入 Skia，也不照搬其颜色变化触发 `markDirty + layout` 的后端限制。文本与输入的长期语义见 [文本输入与绘制](../../../arch/18-文本输入与绘制.md)，后端边界见 [渲染设计](../../../arch/05-渲染设计.md)。

#### 8.1．建立唯一的文本排版结果与资源接口

- 改造 `TextLayoutService`、`TextMeasurer` 及 JUCE 实现，使排版返回可复用结果：尺寸、真实基线、行布局、必要的字符/字形几何、保守绘制边界，以及后端绘制资源句柄。绘制边界是覆盖实际可能绘出内容的范围，可以比布局矩形大。
- core 定义平台无关的输入、结果与资源契约；JUCE 字体、TextLayout、GlyphArrangement 等具体对象由 JUCE 后端封装。JS 不持有后端对象，core 不依赖 JUCE 头文件。
- Text 节点保留最近有效排版结果；布局读取其尺寸和基线，绘制操作引用相应资源。候选 scene 复制时共享不可变排版成果，不深拷贝字形数组。
- 明确区分文字的排版输入、布局返回尺寸、最终分配区域和绘制原点。最终区域只改变对齐或位置时复用排版；最终有效宽度、行数或省略条件确实改变排版时，在布局或发布准备阶段生成正确结果，不强行复用旧结果。
- 消除测量端创建布局后只留下宽高、绘制端又按另一组规则重新排版的双头实现。intrinsic 查询和最终约束布局可以是不同请求，但必须走同一服务和同一语义。

#### 8.2．统一排版规则与失效条件

- 统一现有 Text 的单行/多行、换行、显式换行符、行高、最大行数、对齐、clip/ellipsis/visible 与空文本行为。`maxLines == 0` 保持不限行，不能在新路径中被当作单行。
- 缓存输入必须覆盖当前真实支持且会影响结果的参数：文本、字号、行高、有效约束、换行与行数/省略规则，以及影响字形度量的字体环境。对齐等参数如果烘焙在结果中就参与失效；如果仅在绘制时定位，就作为绘制参数处理。不得漏掉影响结果的输入，也不为尚未提供的字体或富文本 API 扩张公开接口。
- 颜色、透明度、绘制原点、纯 placement/graphics transform、输入文字 viewport offset 不进入排版缓存键。缩放环境、字体解析或字体资源变化是否需要失效，依据后端度量依赖明确处理，不能把屏幕像素缩放与纯绘制变换混为一谈。
- 文本相同且排版输入等价时复用结果；约束变化但排版结果仍有效时更新外部尺寸/定位即可。需要重新排版时正确传播 measure/place/paint/hit 失效，不以缓存命中为由保留错误几何。

#### 8.3．准备与颜色无关的 JUCE 绘制资源

- 在排版完成时准备字体、glyph 编号、位置等稳定绘制数据；单行与多行各自使用合适的后端表示，但共用正式服务、缓存和生命周期，不保留两个相互矛盾的文本模型。
- 绘制时单独提供颜色、透明度、原点与变换。纯颜色变化必须不调用 Arrange/JUCE 的文本布局创建或重排入口，不重新 shaping，不为更新颜色复制完整段落或字形数组。
- JUCE 现有 `TextLayout::draw` 将 run 颜色与布局对象绑定，并在调用中组织 glyph 数组；应封装对已准备字形数据的重放，使颜色由本次绘制参数决定。具体后端调用须保持字体 fallback、字形位置、基线、对齐与裁剪行为正确，不能用逐字符宽度估算替代真实排版。
- 已共享的排版资源保持不可变；禁止在 paint 中修改共享 run 颜色，污染其他节点、候选帧或旧 PublishedFrame。
- 新建或失效资源在候选帧准备完成后才能发布。正常 paint 不补做排版、不调用 JS、不触发场景状态迁移；准备失败沿现有错误与保留帧机制处理。

#### 8.4．完成两级缓存及资源生命周期

- 第一级是节点持有的最近有效结果，稳定节点重复绘制直接复用，不要求每次 paint 重新构造文本键或查全局缓存。
- 第二级是文本服务内部有上限的 LRU，用于相同请求、intrinsic 或临时测量复用。作用域与 UI runtime/后端资源上下文一致，不做跨 runtime 的无界静态缓存。
- LRU 设定明确条目和内存预算，超大单项不无限撑大缓存；淘汰只释放缓存自身引用，不能使节点或 PublishedFrame 正在使用的资源失效。分别统计缓存保留与实际存活资源，不能把 LRU 上限说成整个场景的内存上限。
- 节点删除、替换、分支卸载、KeepAlive 保留/退休、reload、HMR、context reset 与 editor 销毁都要有明确资源归属。旧帧仍被保留时允许持有旧资源；最后持有者释放后必须回收，不让 NodeId 重用命中过期资源。
- 候选帧构建失败不得清除或改写当前帧使用的资源。缓存可以丢弃未被使用的结果，不能改变失败前成功帧的内容和输入几何。

#### 8.5．迁移全部正式文本消费者

- 迁移 Text 测量/绘制、Input 正文与占位符、输入覆盖层中的文本，以及诊断页、badge、toast 等正式文字绘制入口。正式链路不能因主页面已接通就遗留另一套每次 paint 排版的路径。
- Input 继续使用现有输入状态与事件语义，文本变化更新必要排版；光标闪烁、选区变化和水平 viewport 移动复用稳定文本资源。caret、selection、IME bounds 与 point-to-index 必须遵守母文档的统一文本原点和几何约定，不能因接入缓存另造一套估算链路。
- 本 Part 不新增富文本编辑、公开字体体系或完整 Canvas 数据通道；已经存在的 DrawText 消费者须迁移，尚未实现的能力不以性能改造名义扩张范围。
- 删除被替代的测量/绘制实现与旁路，不保留正常 paint 中“缓存未命中就走旧排版”的兼容兜底。

#### 8.6．退出条件与必要证据

- 实际执行处记录排版创建/重排次数、节点复用、服务 LRU 命中/未命中/淘汰、资源存活与估算字节、文字重放次数；区分排版耗时与字形绘制提交耗时。使用轻量计数，不逐字形输出文件日志，不把建设 profiler/devtools 作为前置任务。
- 真实 Showcase/Gallery 完成预热后，稳定文字的重复 paint、纯颜色/透明度动画、纯位置变化和滚动不新增排版；同一帧重复 paint 也不重新排版。尺寸动画在有效排版宽度变化时允许必要重排。
- 改文字、字号、行高、宽度、行数限制后，尺寸、基线、换行、省略与可见结果正确；缓存键差异不会造成串色、串字、错误复用或旧结果覆盖新结果。
- 必要行为测试覆盖中文/英文混排、组合字符/emoji 的现有支持行为、空文本、长文本、输入 viewport 与覆盖层；同一共享资源以不同颜色同时绘制不相互污染。对底层能力有实际限制的项如实记录，不宣称完整 Unicode 编辑能力已经实现。
- 覆盖资源淘汰、节点代际重用、删除/恢复、HMR/reset 和准备失败保留旧帧。测试保护正确行为与资源寿命，不维护已经删除的内部结构断言。
- 正式 Demo 和相关自动化使用新链路，相关构建与测试通过；记录 Debug/Release 的实际绘制与排版成本，并明确平台和测量范围。不以修改优化级别、删减 Demo、关闭动画或排除有效输入代替改造完成。

**第 8 Part 完成的标志是：测量与绘制拥有统一、可复用、生命周期正确的文本排版成果，稳定文本在 paint 中不再重新排版。不能以“加了一个缓存类”代替交付：不能糊弄、凑合。**

### 9．复用已发布绘制片段，实施可靠的可见性裁剪。待实施

**目标：**让已有 DrawOps/PaintFragment 的保留与复用延续到发布和 JUCE 消费端；在保证绘制语义的前提下跳过不可见操作和片段。以第 8 Part 的文本资源及绘制边界为基础，接入同一 SceneFramePipeline → PublishedFrame → PassivePaint 链路。

本 Part 处理绘制工作量和稳定内容复用，不给普通 scroll 附加 Lazy 组合、测量或节点生命周期。布局与 Modifier 的既有语义分别见 [布局](../../../arch/09-布局.md)、[Modifier](../../../arch/11-Modifier.md)，线程与发布契约见 [调度线程与帧阶段](../../../arch/26-调度线程与帧阶段.md)。

#### 9.1．把 DrawOp 可见性建立在真实绘制状态上

- 为可绘制操作建立保守绘制边界。文字使用第 8 Part 的字形绘制边界，线条/描边计入粗细，现有阴影及其他外扩效果计入覆盖范围；不能一律拿节点布局矩形代替。
- 在操作消费时尊重完整的 clip/transform 状态和顺序，再判断操作是否确定不可见。覆盖平移、缩放、旋转、嵌套 clip、滚动 viewport 与宿主 clip，坐标转换和浮点向外取整必须保守。
- `overflow: visible` 的文本可以超出自身区域；Text 自裁剪、祖先 clip 和 scroll viewport 各自按既有语义生效。新增剔除不能偷偷改变裁剪范围，也不照搬 Compose 的固定阴影外扩常量。
- 只有确定不可见的绘制操作才跳过后端绘制及与该次绘制有关的准备工作；边界未知、变换或效果无法可靠判断时保留绘制。保守误画可以接受，错误漏画不可接受。
- 绘制操作剔除不得丢失 PushClip/PopClip、PushTransform/PopTransform 等状态操作，不能使后续兄弟节点处于错误状态。

#### 9.2．让共享绘制片段成为正式发布与重放单位

- 扩展已有 `PaintFragment`、Modifier 层片段与发布内容，使 PublishedFrame 持有不可变片段及资源引用，后端能够直接重放。片段是保留的绘制命令和资源，不等于位图缓存。
- 删除正式场景路径中每次发布都把整棵已缓存片段树重新展平成完整 DrawOps 数组的强制步骤。诊断导出或必要测试可以遍历展开，但不能把展开副本继续作为实际绘制所依赖的另一套事实源。
- 稳定片段使用局部坐标或等价的内容/放置分离表示，放置、滚动偏移和纯 graphics transform 不改写其中每条稳定操作。变化由外层放置或变换表达；真正影响内容的输入才重建对应片段及必要祖先引用。
- 保留 Modifier 的 before/content/after 顺序、子节点顺序、透明度组合和 overlay/diagnostics 的正确层次。复用不得改变半透明叠加或遮挡关系，也不能把整层合成与每条操作乘 alpha 混为一谈。
- 稳定文字片段直接引用已准备文本资源；禁止因片段缓存命中仍逐帧重新组织完整文字数据或复制全部字形。
- 后端重放始终读取 PublishedFrame；不在 paint 内查可变 LayoutTree 补几何，不执行帧流水线，不改变资源身份。

#### 9.3．实现整片段剔除与边界失效

- 片段维护其内容和子片段的保守绘制边界，并明确边界所在坐标系。结构、文字几何、尺寸、放置、变换、裁剪和外扩效果变化时，更新受影响边界及必要祖先。
- 内容边界与外层变换分开维护，使稳定内容随滚动或移动时可以复用内部边界，按当前变换投影后判断可见性。
- 只有片段的全部绘制影响都在有效裁剪区外时，才能跳过整段。节点自身不相交但可溢出子节点相交时，不能跳过；未知边界须向上传播为不能可靠剔除。
- 每个可独立跳过的片段必须有完整的绘制状态作用域，进入/退出成对且状态不泄漏。跳过整段不会遗漏后续绘制依赖的状态变化。
- 先建立 DrawOp 级别的正确剔除，再接整片段剔除；两级最终都进入正式实现，不以单项操作优化替代片段复用交付。

#### 9.4．保持普通滚动、输入与发布一致性

- 普通滚动内容仍参与必要测量和布局，正确计算内容尺寸、换行、子节点位置、滚动范围与命中关系。屏外不是冻结响应式更新、结构协调或脏状态传播的理由。
- 约束和内容未变时，滚动复用已测量结果、文本资源和稳定绘制片段，更新必要放置/变换、可见性及命中数据。屏外内容变化后再滚入视口，必须立即显示正确结果。
- 绘制剔除只减少绘制工作，不销毁节点、不卸载组件、不取消事件绑定、不擅自丢弃焦点或暂停动画，不把普通 scroll 变成 Lazy。
- 命中仍消费同一次成功发布的几何与祖先裁剪关系；绘制剔除结果不作为删改命中快照的旁路，也不以拒收鼠标事件、降低输入频率来掩盖忙碌。
- 候选片段、资源和几何一起发布，构建失败保留上次成功帧；旧片段不得原地改写。节点退休、reload/reset 后的片段和资源引用可正确回落。
- 本 Part 允许宿主继续请求完整 editor repaint，但每次 paint 应复用稳定内容并剔除不可见部分。复杂脏区域合并、位图/离屏图层缓存、遮挡剔除、GPU 专用渲染器、线程模型重构和 Lazy 组件均不属于这两个 Part 的退出前提。

#### 9.5．退出条件与必要证据

- 计数来自实际构建和重放位置，至少区分片段新建/复用、片段访问/整段跳过、DrawOp 访问/跳过、文字实际提交、被动 paint 次数；分别记录绘制列表准备与后端绘制耗时，不把 paint 次数减少当作唯一成功标准。
- 对相同已发布帧，用同一绘制实现分别开启/关闭剔除进行图像比较，必要时辅以实际窗口验证。对照只关闭优化，不维持第二套旧生产 renderer。覆盖嵌套滚动、变换、非矩形 clip、文字 visible 溢出、描边/现有效果外扩、半透明叠加及视口边缘。
- 当整个片段不可见且可安全剔除时，确认不访问其内部 DrawOps；局部可见时，确认保留必要命令且不漏画；剔除后相邻片段的绘制状态正确。
- 真实 80 项列表滚动时，屏外稳定文字不提交 glyph 绘制，稳定文字不新增排版，稳定片段不因整体滚动被逐条重建。滚回、屏外更新后滚入、列表重排/插删、resize、输入与动画同时进行均正确。
- 单个颜色变化只更新必要绘制内容，保留无关文本资源与兄弟片段；不发生整棵绘制列表的强制复制展平。尺寸/结构变化仍执行必要布局和边界传播，不为降低计数漏算。
- 验证跨帧保留、候选失败、删除/HMR/reset 的片段与资源寿命；复用不能造成引用累积或读取过期资源。
- 相关原生测试、真实 compiler → QuickJS → native → PublishedFrame 集成验证及 Demo 构建通过。Windows/macOS 分别记录已完成的平台验证，不拿一个平台结果替代另一个；机器 profiler 由主人另行安排，不是实现的前置条件。

**第 9 Part 完成的标志是：发布和实际绘制都复用稳定片段，并能可靠跳过不可见工作；普通滚动、绘制、输入与失败恢复的语义保持正确。不能以“调用了 graphics clip”或“生成列表有缓存”代替交付。**
