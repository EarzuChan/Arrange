# 实现

## 主要矛盾：确立 CLI 应用层架构

- CLI 不再按“命令脚本”继续堆功能，而要确立清楚的应用层。
- 应用层应分清：交互、配置、版本解析、工程维护、工具链准备、外部命令执行、dev 生命周期、产物整理、错误报告。
- 业务流程不得直接散用 `process.cwd()`、裸 `spawn`、临时字符串拼接和隐式状态。
- 工程根必须是一等概念。既有工程命令只认当前运行目录的 `arrange.config.yaml`。
- 本期不改变 Arrange CLI 的总方向，只把已经跑通的链路整理成可继续维护的正规形态。

## 交互层正规化

- 统一 CLI 输出语言。公开 CLI 文案不得中英文混杂。
- create / adopt 使用现代交互：选择项用上下键切换，不再要求用户输入编号。
- confirm 必须要求明确选择，不允许回车误触发退出。
- 必填字段不得提供默认值：用户需亲手填写。额外要求：公司名、公司代码、插件代码等用户元数据不得使用Earzu的个人数据作为默认值。
- 字段输入时必须提示类型、约束和自然语言的填法规范。
- create 最后应询问工程创建位置：在当前目录创建，或创建到项目名子目录。工程创建到子目录后，用户在流程完成后系需亲手`cd`入子目录（工程目录），方可使用 CLI 管理工程。

## 配置层正规化

- YAML 解析与序列化必须使用`yaml`库。
- CLI 不得再手写 YAML parser。
- YAML 库只负责语法；Arrange 自己负责配置字段、类型、取值、默认值和未知字段校验。
- `arrange.config.yaml` 与 `arrange.local.yaml` 的读取、写入、校验应共用稳定的配置基础设施。
- 配置错误必须定位到明确字段，并给出可行动的修复说明。

## Framework 版本选择正规化

- framework 版本候选来自 registry packument。
- `latest` tag 单独一行展示，但不得吞掉最近版本列表中的同一版本。
- 最近版本列表按发布时间从新到老展示前五个。
- 缺少 `arrange.cliCompatibility` 的版本必须展示，但不可选，并标注 `不兼容：无兼容码`。
- 兼容码不一致的版本必须展示，但不可选，并标注 `不兼容，该版本兼容码为：<该版本兼容码>`。
- 自定义版本必须校验存在性与兼容性，校验失败不得写入配置。

## 工程维护正规化

- sync 更新受控区域时必须打印明确日志。
- 日志应说明更新了哪个文件、哪个受控区域。
- 损坏的受控区域继续跳过，不得覆盖用户文件。
- 跳过时必须打印损坏原因和修复方式。

## dev 行为正规化

- dev 默认启动 UI dev server 与 native debug Standalone。
- 若 native debug Standalone 不存在，dev 应打日志，并自动构建所需 debug 产物（正式地走去构建命令的流程，而不是另外偷偷维护一套构建逻辑）。
- 当前并行启动策略可以保留。未来再考虑把 dev 进程管理收敛成统一 supervisor：管理 Vite、native 进程、退出、信号和状态展示（不是目前本期要做的）。
- Vite 原始输出可以先保留；未来再改成 Arrange 自己的 dev 状态文案（同上条，不是目前本期要做的）。

## package 产物布局正规化

- package 逻辑必须按产品类型分派。
- Standalone 与 VST3 不得共用同一套简单复制规则。
- VST3、mac Bundle 的 UI dist 必须正确放入：`Contents/Resources/ui`
- package 必须清楚报告复制了哪些 native 产物和 UI 资源。
- 找不到产物时，错误信息必须包含 flavor、product 和建议命令。

## 错误输出与日志正规化

- 所有异常退出必须打印明确错误。
- 错误输出应包含 stack。
- 外部命令失败应包含命令、工作目录和退出码。
- 若有记录日志文件，错误输出必须打印日志路径。
- 不得只打印 `error.message` 后静默退出。

## 测试与验证闭环

- 补齐 create / sync / dev / build / package 的实机场景验证。
- 补齐 framework 版本候选展示测试。
- 补齐 YAML 库解析与 schema 校验测试。
- 补齐 VST3 package 布局测试。
- 补齐 dev 缺 debug native artifact 时的行为测试。
- 补齐错误输出测试，确保失败时可诊断。
