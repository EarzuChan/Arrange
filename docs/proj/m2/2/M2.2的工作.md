# 实现

## CLI 包与唯一命令入口

- 新建 `@arrange/cli`，由它独占 `arrange` 命令。
- `@arrange/framework` 绝不再有任何 CLI、bin 或命令入口：原先 `framework的ui：arrange dev` 职能由我们新统一 CLI 发挥。
- `arrange --version`、`arrange --help` 必须体现 Arrange CLI 的唯一入口地位。
- 包发布验证必须覆盖 `@arrange/cli` 与 `@arrange/framework`。

## 工程模式与配置真源

- 标准工程根目录由 `arrange.config.ts`、`ui/`、`native/`、`artifacts/` 组成。
- 根目录不是 Node 项目，不要求根 `package.json`。
- `arrange.config.ts` 是唯一配置真源，不提供 JSON、YAML 或 TOML 配置入口。
- CLI 根据配置定位 UI 项目、native 项目、构建 profile、产物类型与 artifacts 布局。

## create

- `arrange create` 走向导流程。
- 向导收集项目名、版本号、JUCE 公司名、公司代码、插件代码、插件类型、UI 包管理器、JUCE 产物类型与创建目录。
- C++ 标准、UI 语言、TypeScript 版本、JUCE 版本、QuickJS-NG 版本不提供选择。
- 写文件前必须展示最终信息并等待用户确认。
- create 生成 `arrange.config.ts`、`ui/`、`native/` 与必要工程文件。

## adopt

- `arrange adopt` 走向导流程。
- 先选择 native path；没有则进入 native 创建流程。
- 再选择 UI path；没有则进入 UI 创建流程。
- 对已有 native / UI 子工程分别处理复制或原位引用；特殊情况下不可原位引用时不展示该选项。
- 自动识别可确定信息，对缺失或冲突信息专项询问。
- 写文件前展示最终工程信息与将要修改的文件。

## 工程文件维护

- create 可以整篇模板生成工程文件。
- create 之后，CMake 只维护 Arrange managed region。
- 没有 managed region 时，CLI 不静默改写 CMake；doctor 或 adopt 只能提出补丁并等待确认。
- `package.json` 使用语义维护：可添加或更新 Arrange 相关依赖和 scripts，不删除未知字段，不擅自覆盖用户脚本。

## 在工程路径下运行 dev / build / package

- `arrange dev` 从工程根启动开发链路。
- `arrange build` 调用 UI 与 native 构建，并默认执行 package phase。
- `arrange build --no-package` 只执行 build phase。
- `arrange package` 不重新编译，只把已有 UI 与 native 产物整理到 `artifacts/`。
- `dist/` 只作为 UI 项目内部构建输出概念；最终交付物只进 `artifacts/`。

## doctor 与 Demo

- `arrange doctor` 检查工程模式、依赖、版本、CMake 接入、UI package 与 artifacts 布局。
- doctor 不擅自修改文件。
- Demo 先不改动，在CLI建立完成后，主人再命令把 Demo 迁移为标准 Arrange 工程。
- 验证不能依赖任何特供路径或仓库内部源码直连。
