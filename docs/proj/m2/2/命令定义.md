# 总原则

1. **命令少，但语义确定。**
2. **命令参数不承担复杂配置。** 长期事实进 yaml，命令参数只决定本次动作范围。
3. **所有命令都围绕工程根执行。** 不搞 `--cwd`、不向上找 root。
4. **交互用 Clack。**
5. **配置 schema 用 Zod。**
6. **YAML 用 `yaml` 库。**

# 1. `arrange create`

## 形态

```bash
arrange create [--registry <url>]
```

暂时不加 `--name`、`--template` 之类参数。create 是强交互命令。

## 大致流程

```txt
选择创建位置
   - 当前目录
   - 项目名子目录

选择 / 输入基础信息
   - project name
   - project version
   - framework version
   - vendor name
   - vendor code
   - plugin code
   - plugin type
   - package manager
   - products

选择哪些块持续 managed
   - native FetchContent
   - native plugin target
   - native link framework
   - ui package dependency
   - if custom registry: npmrc src override
   
选择 Arrange 工程根

展示最终信息

生成工程
   - arrange.project.yaml
   - ui scaffold
   - native scaffold
   - .gitignore
   - 初始 CMake / package.json / App.vue / Processor

询问是否立即 sync
```

create 的核心是：**生成新工程 + 建立初始管理策略。**

# 2. `arrange adopt`

## 形态

```bash
arrange adopt [--registry <url>]
```

adopt 也必须是强交互命令，不适合靠一堆 flag 表达。

## 大致流程

```txt
处理 raw native
   - 新建 native
   - 复用已有 native
       - 复制进工程
       - 原位引用

扫描 raw native
   - CMakeLists
   - FetchContent
   - juce_add_plugin
   - target_link_libraries
   - source layout
   - project/version/product/plugin type 线索

对 native detected features 逐项确认
   - 是否 managed
   - 能否自动接管
   - 不能自动接管时打印 managed block，让用户手动替换
   - 用户完成后二次检测
   - 用户拒绝则 managed=false

处理 raw ui
   - 新建 ui
   - 复用已有 ui
       - 复制进工程
       - 原位引用

扫描 raw ui
   - package.json
   - deps
   - package manager 线索
   - existing scripts
   - framework version 线索

对 ui detected features 逐项确认
   - dependencies 是否 managed
   - package manager 是否沿用
   - 是否需要自动 patch package.json
   - 展示 diff
   - 或让用户手动处理后二次确认

选择 Arrange 工程根
   - 当前目录
   - 项目名子目录
   
汇总 adopt draft
   - 自动识别到的数据先列出来
   - 让用户确认 / 修改
   - 缺失项再询问

展示最终工程信息 + 将要修改的文件

用户确认后 apply
   - 写 arrange.project.yaml
   - 必要时复制 raw 子工程
   - 必要时写 managed block / patch package.json

询问是否 sync
```

adopt 的核心是：**识别 raw 工程 → 建立托管策略 → 形成 config → 最小侵入接入。**

# 3. `arrange sync`

## 形态

```bash
arrange sync [--check] [--config-only | --toolchain-only] [--ui | --native]
```

暂时保留这几个参数即可。

## 语义

- 无参：完整 sync。
- `--check`：只检查，不 perform。
- `--config-only`：只处理子项目配置项。
- `--toolchain-only`：只处理 local 工具链和 ready 状态。
- `--ui` / `--native`：限制作用范围。

## 大致流程

```txt
1. load project context

2. check phase
   A. 检查子项目配置项内容
      - managed block 是否存在
      - managed block 是否完整
      - 内容是否可识别
      - 内容是否过期 / 与 config 不一致

   B. 检查 local 工具链配置
      - 有 local：验证工具存在且可用
      - 无 local：
          - 完整 sync 中进入交互式创建
          - --check 中只报告缺失

   C. 检查子项目 ready 状态
      - ui deps 是否安装
      - framework 实际版本是否对齐
      - cmake 是否 configure
      - target 是否存在

3. 生成 SyncReport

4. 如果 --check
   - 打印报告
   - 有问题则非 0 退出
   - 不写文件，不执行外部命令

5. perform phase
   A. 修复 / 更新 managed 项
      - 损坏：交互式修复 / 用户手动替换 / 关闭 managed
      - 过期：打印 diff 后更新

   B. 准备 local 工具链
      - 探测
      - 用户补充
      - 验证
      - 写 arrange.local.yaml

   C. 准备 ready 状态
      - install ui deps
      - configure cmake
```

sync 的核心是：**check → report → perform(report)。**

# 4. `arrange dev`

## 形态

```bash
arrange dev [--ui-only | --native-only] [--flavor debug|release]
```

## 大致流程

```txt
1. load project context

2. run sync check
   - managed 项不一致：失败，提示 arrange sync
   - local 工具链不可用：失败或进入必要准备？这里要再定，但我倾向 dev 不修工程，只提示 sync
   - 子项目 not ready：失败，提示 arrange sync

3. 判断 dev mode
   - ui-only：只启动 Vite
   - native-only：只启动 Standalone
   - 默认：启动 Vite + Standalone

4. 检查 standalone product
   - project.products 没 standalone：
       - 默认 dev 不能启动 editor
       - 提示用 --ui-only 或开启 standalone 后 sync

5. 检查 standalone artifact
   - target 存在但 artifact 缺失：
       - 走正式 native build step 构建所需 flavor/product

6. 启动进程 supervisor
   - Vite
   - native Standalone
   - 信号处理
   - native 退出时停止 Vite
   - Ctrl+C 不渲染成错误
```

dev 的核心是：**只开发，不静默修工程结构；但可构建缺失的 native dev artifact。**

# 5. `arrange build`

## 形态

```bash
arrange build [--flavor debug|release] [--ui-only | --native-only] [--no-package] [--product standalone|vst3]... [--clean]
```

默认情况下是UI+Native都构建并自动打包。然后：Native方面，默认是Release风味的工件全都构建，选择其一工件，则只构建该工件

## 大致流程

```txt
1. load project context

2. sync check
   - managed 项不一致：失败，提示 arrange sync
   - local 工具链不可用：进入工具链准备
   - ui deps 缺失：提示 arrange sync
   - cmake 未 configure：可在 build 内 configure native

3. resolve build plan
   - flavor 默认 release
   - products 默认 project.products
   - ui-only 不 package
   - native-only 不 package
   - no-package 不 package
   - clean 仅完整 build + package 合法

4. build ui
   - Vite build

5. configure native
   - CMake configure

6. build native products
   - CMake build target per product

7. package artifacts
   - 除非 ui-only/native-only/no-package
```

build 的核心是：**执行构建，但不修 project managed 配置。**

# 6. `arrange package`

## 形态

```bash
arrange package [--flavor debug|release] [--product standalone|vst3]... [--clean]
```

## 大致流程

```txt
1. load project context

2. 不 install
3. 不 configure
4. 不 build
5. resolve package plan
   - flavor 默认 release
   - products 默认 project.products

6. 检查已有 artifacts
   - native artifact 是否存在
   - ui dist 是否存在或是否允许缺失，这个要定

7. 复制到 artifacts/
   - standalone 布局
   - vst3 布局
   - mac app bundle 布局

8. 打印清晰报告
```

package 的核心是：**只整理已有产物，不构建。**

# 暂不加入的命令

我暂时不建议马上加：

```bash
arrange doctor
arrange status
arrange clean
arrange inspect
```

这些以后可能有价值，但第三期第一步不应该扩命令面。  
先把 create / adopt / sync / dev / build / package 的语义钉死。
