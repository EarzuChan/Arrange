# M2.2 命令定义与执行流程

本文是 CLI 重写期间的命令执行规格。命令与工程形态见 [Arrange CLI 与工程模式](../../../arch/31-ArrangeCLI与工程模式.md)；定义、扫描矩阵与 LSRA 语义见 [托管与同步母文档](../../../arch/32-ArrangeCLI托管与同步模型.md)。本文用 Mermaid 明确命令顺序、交互位置和退出分支，不重复矩阵定义。

## 命令入口

命令和参数定义见 [CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#命令)。本期交互使用 Clack，配置校验使用 Zod，YAML 使用 `yaml` 库。

## `arrange create`

### 目标与交互输入

创建标准 Arrange 工程，写入共享配置和初始 UI/native 文件。向导收集：

- 创建位置：当前目录或项目名子目录。
- project name、project version、Arrange framework version。
- vendor name、vendor code、plugin code。
- plugin type：`effect` 或 `instrument`。
- UI package manager：`pnpm` 或 `npm`。
- products：`standalone`、`vst3`。
- UI、native、artifacts 目录。
- 各 ManagedItem 是否启用。
- 可选 framework registry 和 CMake FetchContent URL。

生成接口见[托管模型](../../../arch/32-ArrangeCLI托管与同步模型.md#物理定义接口)。

### 流程

```mermaid
flowchart TD
    A["arrange create"] --> B["启动交互向导，选择工程根和目录"]
    B --> C["填写项目、framework、UI、native 信息"]
    C --> D["选择 products 与 ManagedItem"]
    D --> E["校验输入并展示完整摘要"]
    E --> F{"用户确认？"}
    F -->|否或取消| AB["结束，不写工程"]
    F -->|是| G["构造 ProjectState，解析生成所需拓扑"]
    G --> H["调用各 File.make(state)"]
    H --> I{"文件种类"}
    I -->|文本| J["File 委派 Cluster.make(state)"]
    J --> K["Cluster 生成外壳并委派 Region.make(state)"]
    I -->|JSON| L["File 汇合 JsonRegion.make(state) 的字段结果"]
    K --> M["汇合各文件生成结果"]
    L --> M
    M --> N["写 arrange.project.yaml、初始文件与 .gitignore"]
    N --> O{"立即 sync？"}
    O -->|否| DONE["报告创建完成"]
    O -->|是| P["运行完整 arrange sync"]
    P --> Q{"sync 成功？"}
    Q -->|是| DONE
    Q -->|否| FAIL["报告工程已创建及同步失败原因"]
```

### 完成条件

- 工程根有合法 `arrange.project.yaml`，按配置生成所需 UI/native 初始文件。
- create 的生成结果与后续 CONFIG 使用同一套定义。
- local 尚未准备时由后续 SETUP 负责；选择立即 sync 不意味着同步必然成功。

## `arrange adopt`

### 目标与输入

收编已有 UI/native 工程。保持选择新建或复用、复制或原位引用的交互；项目已在 CWD 对应位置时不重复复制，目录名不同于默认值时可询问是否改名。

native 由用户明确目录、目标和项目配置，不分析 CMake 正文来反推字段或定位区块。UI 可读取 package.json 等结构化文件展示现状，由用户提供并确认工程配置。选择托管的文本内容通过同一套 Wrapper/Marker 交互接入，不恢复旧的智能文本候选或反哺配置流程。

### 流程

```mermaid
flowchart TD
    A["arrange adopt"] --> B["选择新建或复用 native"]
    B --> C["复用时选择复制或原位引用，必要时确认目录名"]
    C --> D["用户填写 native 项目信息"]
    D --> E["选择新建或复用 UI"]
    E --> F["复用时选择复制或原位引用"]
    F --> G["读取可用 JSON 信息，用户确认 UI 配置"]
    G --> H["选择 ManagedItem，汇总 ProjectState 草案"]
    H --> I["补齐输入、校验配置、展示将修改的文件"]
    I --> J{"用户确认？"}
    J -->|否或取消| AB["结束，不接管"]
    J -->|是| K["按选择接入目录；新文件由统一定义生成"]
    K --> L["保存共享配置，运行 CONFIG LSRA 接入托管"]
    L --> M{"CONFIG 成功？"}
    M -->|否| FAIL["报告接入未完成，结束"]
    M -->|是| N{"立即准备环境？"}
    N -->|否| DONE["报告 adopt 完成"]
    N -->|是| O["重新加载 State，运行 SETUP LSRA"]
    O --> P{"SETUP 成功？"}
    P -->|是| DONE
    P -->|否| SF["报告托管已接入及环境准备失败原因"]
```

### 完成条件

- 配置完整并经用户确认，所选托管通过 CONFIG 接入。
- 既有文本区块通过用户指定的 Wrapper 建立定位，未托管内容不被接管。
- 后续 sync 从保存的 State 推导拓扑，不依赖 adopt 的一次性内存坐标。

## `arrange sync`

参数选择见 [CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#命令)。

### 完整同步编排

```mermaid
flowchart TD
    A["arrange sync"] --> B["解析部分、范围与 scan 参数"]
    B --> C{"仅扫描？"}
    C -->|是| SO["进入扫描模式，输出所选部分报告后结束"]
    C -->|否| D{"包含 CONFIG？"}
    D -->|是| E["运行 CONFIG LSRA"]
    E --> F{"CONFIG 成功？"}
    F -->|否或放弃| AB["失败退出 sync"]
    F -->|是| G{"包含 SETUP？"}
    D -->|否| G
    G -->|否| DONE["sync 完成"]
    G -->|是| H["重新加载 ProjectState"]
    H --> I["运行独立的 SETUP LSRA"]
    I --> J{"SETUP 成功？"}
    J -->|是| DONE
    J -->|否或放弃| AB
```

### CONFIG LSRA

```mermaid
flowchart TD
    S["SCAN：重新加载 State，推导拓扑，尽可能扫描"] --> R["产出完整 ConfigScanReport"]
    R --> F{"RESOLVE：报告中有 Fatal？"}
    F -->|有| AB["展示报告，失败退出；不修复其他 Issue"]
    F -->|无| Q{"有 Resolvable？"}
    Q -->|有| ONE["取一个 Issue，进入对应交互"]
    ONE --> O{"处理结果"}
    O -->|取消| AB
    O -->|继续：写入或用户编辑后| S
    Q -->|无| READY["RESOLVE 完成"]
    READY --> A["APPLY：执行最后一轮报告的 Applicable"]
    A --> OK{"写入成功？"}
    OK -->|是| END["CONFIG 完成；不追加复检"]
    OK -->|否| ERR["保留事务信息，报告失败并退出"]
```

### CONFIG SCAN 的遍历

父级门控与四类结果使用[母文档的扫描矩阵](../../../arch/32-ArrangeCLI托管与同步模型.md)，下图展开当前扫描器的遍历顺序。

```mermaid
flowchart TD
    A["读取 State，收集配置诊断"] --> B{"有可信输入可推导拓扑？"}
    B -->|无| C["记录 Fatal 及无法展开的范围"]
    C --> C2["完成不依赖该输入的可用检查"]
    C2 --> Z["汇总四类结果"]
    B -->|有| D["按启用 ManagedItem 和范围取得 Region 及物理祖先"]
    D --> EX["委派期望值计算；非法期望记录 Fatal"]
    EX --> FILE{"还有可扫描 File？"}
    FILE -->|无| Z
    FILE -->|有| READ["委派下一 File.check 读取并检查"]
    READ --> FS{"文件状态"}
    FS -->|缺失| FM["记录 Resolvable；后代不进入扫描"]
    FS -->|读取失败| FF["记录 Fatal；后代不进入扫描"]
    FM --> FILE
    FF --> FILE
    FS -->|可读| KIND{"文本还是 JSON？"}
    KIND -->|JSON| JP{"JSON 可解析？"}
    JP -->|否| JF["记录 Fatal；JsonRegion 不进入扫描"]
    JF --> FILE
    JP -->|是| JR["逐个委派参与 JsonRegion 的 check，汇总结果"]
    JR --> FILE
    KIND -->|文本| CL{"还有可扫描 Cluster？"}
    CL -->|无| FILE
    CL -->|有| CW["委派下一 Cluster.check，复用 locate"]
    CW --> CS{"定位结果"}
    CS -->|missing 或 damaged| CF["记录 Resolvable；其参与 Region 不进入扫描"]
    CF --> CL
    CS -->|located| TR["以 Cluster inner 委派参与 TextRegion.check"]
    TR --> COL["收集四类结果；受损坏波及的区域不进入扫描"]
    COL --> CL
```

期望非法和父级失败都只阻断依赖该输入的判定；其他具有可信输入的对象继续扫描。报告引用与验收示例见 [SCAN 结果各项与对策](SCAN结果各项+对策.md)。

### CONFIG RESOLVE 的一次交互

此处的入口已经通过 Fatal 检查。每次只处理一个 Resolvable；所有编辑返回完整 SCAN，不继续消费旧报告。

```mermaid
flowchart TD
    A["接收一个 Resolvable Issue"] --> K{"对象与判定"}
    K -->|File missing| FC{"确认创建文件？"}
    FC -->|是| FW["调用 File.make 并写入"]
    FC -->|否| AB["Abort sync"]
    K -->|Cluster 或 TextRegion missing| M{"已有内容还是新建？"}
    M -->|已有| W["用户给已有区块补长期 Wrapper"]
    W --> V{"locate 验证 Wrapper 是否有效？"}
    V -->|无效| RETRY{"继续编辑？"}
    RETRY -->|是| W
    RETRY -->|否| AB
    V -->|有效| S["结束本次交互，reload 并全量 SCAN"]
    M -->|新建| MARK["用户在父级范围内放一次性 Marker"]
    MARK --> MV{"Marker 位置是否有效？"}
    MV -->|无效| MR{"继续编辑？"}
    MR -->|是| MARK
    MR -->|否| AB
    MV -->|有效| GEN["调用对应定义 make，替换 Marker"]
    GEN --> S
    M -->|取消| AB
    K -->|Cluster 或 TextRegion damaged| FIX["展示标记错误，要求用户修复"]
    K -->|JsonRegion damaged| JFIX["展示文件、路径与实际类型，要求用户编辑"]
    FIX --> CONT{"用户继续还是取消？"}
    JFIX --> CONT
    CONT -->|继续| S
    CONT -->|取消| AB
    K -->|JsonRegion missing| JC{"确认补入字段？"}
    JC -->|是| JW["按 JsonRegion.locate 路径写入 make 结果"]
    JC -->|否| AB
    JW --> S
    FW --> S
```

若发现用户在交互期间同时修改了 YAML，结束当前 Issue 的交互并回到完整 SCAN，不再依据旧 expect 或旧托管开关写入。位置验证不通过时不写入，用户可修复或取消。对应处理的语义边界以母文档为准。

### CONFIG APPLY

```mermaid
flowchart TD
    A["接收最后一轮无阻塞报告"] --> B{"Applicable 为空？"}
    B -->|是| DONE["CONFIG 完成"]
    B -->|否| C["按报告的定位与期望内容，按 File 组合更新"]
    C --> D{"文件快照与写入范围仍有效？"}
    D -->|否| FAIL["报告失败，保留已有恢复信息"]
    D -->|是| E["创建 .arrange/ journal"]
    E --> F["写目标旁临时文件，逐个替换并记录进度"]
    F --> G{"全部成功？"}
    G -->|否| FAIL
    G -->|是| H["标记事务完成，报告更新清单"]
    H --> DONE
```

区间换算与替换规则见[恢复与应用](../../../arch/32-ArrangeCLI托管与同步模型.md#config-的恢复与应用)，写入保护见[事务约定](../../../arch/32-ArrangeCLI托管与同步模型.md#arrange-与写入失败)。

### 扫描模式

```mermaid
flowchart TD
    A["sync --scan"] --> B["按选择取得部分与范围"]
    B --> C{"包含 CONFIG？"}
    C -->|是| D["运行 CONFIG SCAN，保存完整报告"]
    C -->|否| E{"包含 SETUP？"}
    D --> E
    E -->|是| F["按当前可信输入执行 SETUP 的只读扫描入口"]
    E -->|否| G["输出已选部分的报告与受阻范围"]
    F --> G
    G --> H{"存在 Fatal 或 Resolvable？"}
    H -->|是| FAIL["非零状态结束"]
    H -->|否| END["正常结束，Applicable 只展示不执行"]
```

SETUP 在扫描模式中观察当前实际状态，不假定 CONFIG 的 Applicable 已被执行；无法开展的范围必须说明。其具体扫描项目与分类仍待后续设计。

### SETUP 的已定边界

SETUP 管环境和设施准备状态，使用项目需求与本机设置，运行独立 LSRA。完整 sync 中，它在 CONFIG 成功并重新加载 State 后开始。

本轮不规定工具探测、依赖安装、CMake configure 等动作分别属于哪个阶段，也不保留旧稿中未经确定的详细对策图。后续设计应补充 SETUP 自己的扫描矩阵和交互流程，再实现该部分。

## `arrange dev`

### 目标

拉起开发环境和测试程序。dev 可以为缺失的开发版 native artifact 执行正式构建，但不静默修改工程托管配置。

### 流程

```mermaid
flowchart TD
    A[arrange dev] --> B[加载 ProjectState]
    B --> C[执行 sync --scan]
    C --> D{CONFIG 或 SETUP 有阻塞？}
    D -->|是| E[报告问题并提示 arrange sync]
    D -->|否| F[解析 ui-only/native-only 与 flavor]
    F --> G{默认模式需要 Standalone？}
    G -->|是| H{Standalone 在 products 中？}
    H -->|否| I[提示使用 --ui-only 或修改 project 后 sync]
    H -->|是| J{开发版 artifact 存在？}
    J -->|否| K[调用 native build 生成开发版 artifact]
    J -->|是| L[准备 Vite 与 native 进程]
    K --> L
    G -->|否：ui-only| L
    F --> M{native-only？}
    M -->|是| N[只准备 native 进程]
    M -->|否| L
    L --> O[DevSupervisor 启动并监管进程]
    N --> O
    O --> P{进程退出或收到信号？}
    P -->|native 退出| Q[停止关联 Vite]
    P -->|Ctrl+C| R[停止全部子进程并正常结束]
    P -->|异常退出| S[报告进程错误并停止全部]
```

默认 dev 启动 Vite 与 Standalone；`--ui-only` 只启动 Vite；`--native-only` 只启动 native 开发程序。Ctrl+C 是正常结束，不应渲染为错误。

## `arrange build`

### 目标

构建可用的 UI/native 产物。默认 flavor 为 `release`，默认 products 来自 ProjectState；完整构建默认继续进入 package，`--no-package` 可关闭。

### 流程

```mermaid
flowchart TD
    A[arrange build] --> B[加载 ProjectState]
    B --> C[解析 flavor、范围、products、clean]
    C --> D[检查 sync 与工具链状态]
    D --> E{工程或工具链未 ready？}
    E -->|是| F[报告 arrange sync 或 SETUP]
    E -->|否| G{需要 UI？}
    G -->|是| H[执行 UI package manager build]
    G -->|否| I[跳过 UI]
    H --> J{需要 native？}
    I --> J
    J -->|是| K[执行 CMake configure]
    J -->|否| L[跳过 native]
    K --> M[按 products 构建 native targets]
    L --> N{允许 package？}
    M --> N
    N -->|是| O[调用 package 整理 artifacts]
    N -->|否| P[报告构建完成]
    O --> P
```

`--ui-only` 不执行 native，也不 package；`--native-only` 不执行 UI，也不 package；`--no-package` 只跳过 package。`--clean` 清理行为只作用于本次明确选择的构建范围。

## `arrange package`

### 目标

只整理已有的 UI/native 构建产物，不 install、不 configure、不 build。

### 流程

```mermaid
flowchart TD
    A[arrange package] --> B[加载 ProjectState]
    B --> C[解析 flavor、products、clean]
    C --> D[定位已有 UI dist 与 native artifacts]
    D --> E{所选产物是否齐全？}
    E -->|否| F[报告缺失项并结束失败]
    E -->|是| G{clean？}
    G -->|是| H[清理所选 artifacts 输出范围]
    G -->|否| I[保留其它输出]
    H --> J[复制并整理 Standalone 布局]
    I --> J
    J --> K[复制并整理 VST3 布局]
    K --> L[按 flavor、version、platform、product 写入 artifacts]
    L --> M[打印复制清单并结束]
```

默认布局为 `artifacts/<flavor>/<version?>/<platform>-<arch>/<product>/`。VST3 的 UI 资源放入对应 bundle 的约定资源目录；具体路径由 ArtifactLocator 根据平台和实际产物确认。

## 完成判据

- 命令实现与对应 Mermaid 流程一致，失败、取消与扫描模式有明确出口。
- CONFIG 满足[报告验收案例](SCAN结果各项+对策.md)，特别是完整收集四类结果、父级阻断后不扫描子项、每轮只修一个 Issue 和重扫。
- create/adopt 复用统一定义，受管文本以 Wrapper 定位，不引入正文反向解析。
- SETUP 在自己的后续规格确定后单独验收，不把 CONFIG 的矩阵直接当作其实现。
