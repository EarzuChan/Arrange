# CLI 进程树清理整改验收

状态：Windows 机械测试通过，Windows 手测与 macOS 机械、手测待验。设定见 [资源占用与进程生命周期](../../arch/36-ArrangeCLI资源占用与进程生命周期.md#进程树归属与清理结论)。

## 起因

虚拟机中用 CLI 创建工程并 sync，`pnpm install`、debug 配置均成功，release 配置的 CMake 已写出构建文件，随后报“Windows 子进程树清理超时”，任务整体失败。主工具成功，失败只来自收尾。

原因：主进程退出后，工作进程用冷启动的 PowerShell 枚举全机进程来找后代，超时仅 4 秒，慢机器上不够；超时被当作任务失败，并且永久阻止该工作进程释放资源。

## 整改

- 进程归属改由 Windows 工具专属 Job、macOS 进程组回答，删除对 PowerShell 的主路径依赖；Job 不可用时保留扫描兜底，独立 30 秒超时。
- 清理结论分 `clean`、`reaped`、`unknown`，与任务结果分离；`unknown` 可重试，不再永久污染工作进程。
- 清理账本抽为 `ManagedProcesses`，可脱离真实进程测试。

## Windows 本机结果

- 类型检查通过；CLI 全量测试 502 项，491 通过，0 失败，11 项为对方平台不适用。改动后连续 8 轮全量均无失败；改动前基线 6 轮全量同样无失败。
- 调试中曾见一次 `operations.test.ts` 的“客户端被强杀后”失败，当时 Job 排空窗口尚未加入；之后 24 次并行压力与 8 轮全量均未复现，原因未能确认，Windows 手测时留意。
- 新增用例覆盖：无后代为 `clean`；脱离父进程的长驻后代被结束；`unknown` 可重试并在确认后固定；清理动作出错可重试；成功任务不因清理未确认而改变结果；账本只在确认后撤销登记；Windows 扫描兜底能结束已退出父进程的后代。
- 探测发现的实现要点：首次加载 kernel32 绑定耗时数百毫秒，若放在进程创建之后，后代会在加入 Job 前逃逸，已改为 Executor 创建时加载。
- `format:check` 依赖本机未安装的 `rg`，改动前后同样无法运行，未得到格式检查结果。

### CLI 在 macOS 上要测什么

对应版本 CLI 1.2.0。本次只重写了外部工具的进程树清理，macOS 走进程组分支，行为应与旧版一致，要确认的是“没改坏”和新增的清理结论。背景与 Windows 结果见上文，设定见 [进程生命周期](../../arch/36-ArrangeCLI资源占用与进程生命周期.md#进程树归属与清理结论)。

#### 机械测试：已完成

在 `cli/` 下执行 `npm test`，预期无失败，Windows 专属用例显示“不适用”。重点看 `platform-process.test.ts` 与 `operations.test.ts`。

#### 手测：已完成

1. 新建工程并 sync 走完整流程，debug、release 两个配置都要成功。
2. configure 或 build 进行中按 Ctrl+C，用 `pgrep -fl "cmake|ninja|clang"` 确认没有残留，随后立刻再跑命令，不应提示资源被占用。
3. dev 模式启动，等就绪后按键正常结束，再 Ctrl+C 取消一次，确认 Vite 与 Standalone 都已退出、端口已释放。
4. 全程留意是否出现“未能确认后代进程已结束”的警告；出现即记录当时的命令，它在正常流程中不该出现。
