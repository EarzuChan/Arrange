# M5-EX：字体与文字样式

状态：Windows 与 macOS 原型均已验证；Windows 侧施工完成并通过验证，macOS 侧代码已写，待在 macOS 上验证（见「macOS 待验」）。M5 的追加篇，主题是字体样式 API 与相关的文字排版修正；本文记录需求、范围、验收、原型结论与施工状态，定稿后的长期设定迁入 arch 与新 ADR。

## 目标

文字能指定字体族、字重与字形，系统字体与随 App 打包的字体都可用，Windows 与 macOS 上选中同一字面、伪造行为一致；字体环境变化后，Text、Canvas 与绘制修饰器中的文字都重新排版。

## 老现状

- `TextStyle` 只有字号与行高，所有文字都用 JUCE 默认无衬线字体：Windows 为 Verdana，macOS 为 Lucida Grande（[基础类型](../../arch/10-基础类型.md)中字体族、字重、字形列为尚未实现）。
- Windows 上 JUCE 8 的窗口绘制走 Direct2D 加 DirectWrite，字形是原生渲染；离屏位图（模糊、阴影等缓存）中的文字走 JUCE 软件渲染。
- 字体环境代际（[文本输入与绘制](../../arch/18-文本输入与绘制.md)）已有，但没有任何生产代码推进它；推进后 Text 会重新测量，Canvas 与绘制修饰器中的 `drawText` 排版结果缓存在绘制片段里，不会重建。

### JUCE 8.0.12 字体行为（源码调研）

- 没有数值字重。字体由「族名 + 样式名字符串」确定；粗体、斜体只看样式名里是否有完整单词 `Bold`、`Italic` 或 `Oblique`，因此 `SemiBold` 不算粗体，`Semi Bold` 算。
- Windows 选字面：先按英文字面名在族内精确匹配（忽略大小写）；失败时交给 DirectWrite 按 700 或 400 两档加斜与不斜找最接近的字面，请求的 Medium、SemiBold 缺失时落到 400。
- macOS 选字面：先查内存加载的字体，再在族内精确匹配样式名（区分大小写）；失败时取族内列出的第一个样式，不保证是 Regular。
- 伪造：请求的样式名不在族的样式列表中、且含 Bold 或 Italic 时，在 HarfBuzz 上合成粗体（0.04 em，不改字距）与斜体（倾斜 0.1）。Windows 原生绘制靠 DirectWrite 自己的模拟；macOS 纯色文字经 CoreText 绘制时只套用了倾斜，合成粗体不生效，渐变填充走轮廓时又生效；离屏软件渲染走 HarfBuzz 轮廓，两者都生效。
- 内存字体：`Typeface::createSystemTypefaceFor(bytes)`。Windows 上字体对象存活期间加入进程级字体集合，可按名字找到；macOS 登记在 JUCE 自己的表里。`FontOptions::withTypeface` 直接使用给定字面，不经名字匹配，也不触发 JUCE 的合成。
- 可变字体：原生绘制按命名实例，轮廓路径（离屏软件渲染）按默认实例，两者错位。排版宽度两个平台不同：Windows 上 HarfBuzz 不带调节轴取值，按默认实例；macOS 上 HarfBuzz 随命名实例（见 macOS 原型结论）。
- JUCE 内置的 HarfBuzz 含 `hb_style_get_value`，但 JUCE 的原生字体句柄是内部类型，公开 API 拿不到 `hb_font_t`；字面的字重与斜体需各平台原生读取（Windows 用 DirectWrite，macOS 用 CoreText）。

### 原型结论：Windows

原型为独立控制台程序（JUCE 8.0.12 + DirectWrite），同一组文字分别画到 Direct2D 原生图像与软件图像上对照。

- 字重读取：DirectWrite `IDWriteFont::GetWeight` 给出真实字重（Segoe UI 为 300/350/400/600/700/900 及各自斜体，Microsoft YaHei UI 为 290/400/700）。OS/2 表的 `usWeightClass` 对可变字体的命名实例一律是 400（Bahnschrift、Segoe UI Variable），不可用。枚举时跳过 DirectWrite 模拟出来的字面与非常规宽度的字面（如 Arial Narrow）。
- JUCE 名字匹配实测：`SemiBold` 忽略大小写命中 `Semibold`；`Semi Bold` 落到 Bold；`Medium` 落到 Regular；Arial 请求 `SemiBold` 落到 Regular；Gabriola 请求 `Bold` 得到 DirectWrite 模拟粗体；Gabriola 与 YaHei 请求 `Italic` 得到 `Oblique` 模拟；未知族名落到 Arial。印证了不能依赖名字匹配。
- 自定匹配：按 CSS 规则选字面结果确定（Segoe UI 500→Regular、800→Black；Arial 600→Bold、800 斜体→Bold Italic；YaHei UI 600→Bold，斜体回落到正体并需伪造）。经 `withTypeface` 绘制正常。
- 自带字体：字节经 `createSystemTypefaceFor` 加载、`withTypeface` 使用，中日文字自动回落到 Microsoft YaHei UI 与 Yu Gothic UI，分段与绘制正常。
- 可变字体：Bahnschrift 各命名实例的 HarfBuzz 排版宽度完全相同，软件图像全部按默认字重绘制，Direct2D 则画出各实例的真实字重，确认错位，只支持静态字面。
- 伪造：原生字形加约 0.045 em 的轮廓描边，观感接近 DirectWrite 自己的模拟粗体；16px Segoe UI 下比真 Bold 略重。错切 0.2 至 0.25 的斜体观感合理。JUCE 自带的伪斜体（YaHei 请求 `Italic`）在 Direct2D 上是倾斜的、在软件图像上是正体，两条路径不一致，确认伪造由 Arrange 自己绘制。
- 默认字体候选：Segoe UI 加 Microsoft YaHei UI（中文回落）在 15px 下清晰，均为静态字面，优于当前的 Verdana。

### 原型结论：macOS

原型为独立控制台程序（JUCE 8.0.12 + CoreText，macOS 27.2、Apple Silicon）。排版与重放走和 Arrange 相同的路径：`detail::ShapedText` 取字形，再用 `drawGlyphs` 重放。同一组文字分别画到 `NativeImageType`（CoreGraphics）与 `SoftwareImageType` 上对照，覆盖率（透明底上的平均 alpha）用来量化粗细。原型源码与截图在会话临时目录，未入库。

- 字重读取（静态字面）：CoreText `kCTFontWeightTrait` 对 Apple 自带字体只取离散值（-0.8、-0.6、-0.4、0、0.23、0.3、0.4、0.56、0.62），按 Apple 刻度映射并取整到百位，即得 UltraLight 100、Thin 200、Light 300、Regular 400、Medium 500、Semibold 600、Bold 700、Heavy 800、Black 900。对 273 个系统族里样式名带明确字重词的 584 个静态字面做核对：CT 读法正确 556 个（95%），OS/2 `usWeightClass` 正确 516 个（88%）。OS/2 的典型偏差：Avenir Next Heavy 为 900（CT 为 800，Apple 的定义是 800）、Hiragino Sans 的 W3 为 300（实为常规）、Lucida Grande 的 Regular 与 Bold 为 500 与 600、一批旧版中日文字体的 Bold 写成 400。CT 的偏差集中在旧版 CJK 与装饰字体（Heiti、STHeiti、Impact 等），无法两全。
- 第三方静态字体的 CT 值不在 Apple 刻度上（Source Code Pro 的 Light 为 -0.23、Medium 为 0.2，另一条由 OS/2 换算的连续曲线）。线性插值后取整，Light、Medium 正确，ExtraLight（OS/2 为 200）会读成 300。因此自带字体不要读 CT：直接解析字节里的 OS/2 表（`usWeightClass`、`fsSelection`），两个平台一致；`defineFontFamily` 的覆盖项保留给个别写错 OS/2 的字体。
- 可变字体的命名实例（SF Pro、SF Compact、Noto Sans CJK VF）：OS/2 一律无用（SF Pro 全是 400，SF Compact 全是 1000，Noto 全是 100）。`wght` 轴取值只对第三方字体可用（Noto 实例为 300、350、400、500、700、900），SF 的取值不在 CSS 刻度上（SF Pro 的 Ultralight 30.9、Medium 510、Semibold 590，SF Compact 的 Regular 457.9），且默认实例没有取值条目。145 个带字重词的命名实例上，CT 读法正确 135 个，轴取值正确 102 个。结论：系统 SF 字体读 CT；第三方可变字体 CT 值是连续插值（Noto Light 为 -0.23、Medium 为 0.2）、默认实例 Thin 会读成 200，只可靠地知道默认实例的字重是 `wght` 轴默认值（Noto 为 100）。本期只支持静态字面，这一点只在“误选了可变字体族”时才用到。
- 枚举要排除的字面：宽度特征 `kCTFontWidthTrait` 不为 0 的（Helvetica Neue 的 Condensed Bold、Condensed Black 为 -0.2；SF Pro 的 Expanded 为 0.2，Condensed 为 -0.2，Compressed 为 -0.3）。用户安装的字体可能在多个目录各有一份，枚举结果会重复，按 PostScript 名去重。枚举要用族名属性查询；`SF Pro`（可变，45 个实例）与 `SF Pro Text`、`SF Pro Display`（静态，需用户另装）是不同的族，系统自带的系统 UI 字体 `.AppleSystemUIFont` 也是可变的，可经 JUCE 按名字取到。
- JUCE 名字匹配实测（Helvetica Neue、PingFang SC、Avenir Next、Menlo、Arial、Apple Chancery、Source Code Pro 与一个不存在的族）：
  - 样式名区分大小写：`SemiBold` 命不中 PingFang 的 `Semibold`，也命不中 Avenir 的 `Demi Bold`，都落到族内第一个样式；该样式在系统自带的族里是 Regular，在没有 Regular 的 Source Code Pro 里是 ExtraLight。与 Windows 不同，Windows 上 `SemiBold` 忽略大小写命中 `Semibold`。
  - `Medium`、`Bold`、`Italic` 在族里有同名样式时精确命中；Windows 上 `Medium` 落到 Regular，macOS 上命中真 Medium。
  - `Semi Bold` 与不存在的 `Bold`：样式名含完整单词 Bold，取第一个样式（Regular），再叠 JUCE 的合成粗体，Arial、Menlo、PingFang、Apple Chancery 上的前进量与 Regular 相同。`Italic` 不存在时同理叠合成斜体（倾斜 0.1）。
  - 不存在的族名：CoreText 替换为 Helvetica（Windows 上是 Arial），JUCE 报告的名字仍是请求的名字，不可据此判断。
  - 以 JUCE 高度（`FontOptions(name, style, height)`）建出的合成字面，前进量与 Regular 不一致（Arial 的 `Semi Bold` 比 Regular 小约 3.5%），以点高度建出的则一致；原因没有深究，也是不依赖合成的理由。
- 自定匹配：按 CSS 规则选字面，结果确定（重复选择一致；Menlo 500→Regular、600→Bold；Helvetica Neue 300→Light、500→Medium、600→Bold、800→Bold；PingFang SC 600、700→Semibold、斜体缺失→回落到正体并需伪造斜体；Apple Chancery 单字面，600 以上伪造粗体；Lato 600 斜体→Italic 加伪造粗体）。选中的字面经 `createSystemTypefaceFor(Font(族, CT 样式名))` 取得、再交给 `FontOptions(typeface)` 使用，没有触发 JUCE 的合成。用 CoreText 直接度量该字面的前进量与 JUCE 排版结果对照，Menlo、Helvetica Neue、PingFang SC 共 27 组全部一致；Apple Chancery 差 3.4%，是脚本字体上 CoreText 与 HarfBuzz 的整形差异，字面选择没有错。`FontOptions::withTypeface` 要求先前没有设过名字和样式，直接用 `FontOptions(Typeface::Ptr)` 构造更稳。
- 自带字体：字节经 `createSystemTypefaceFor` 加载，族名与样式名取自字体的 name 表（Lato 的 Regular、Bold、Italic）。字体对象存活期间登记在 JUCE 自己的表里：`findAllTypefaceNames` 能找到，按名字取到的面与 `withTypeface` 的是同一个面；CoreText 字体管理器不知道它。对象全部释放后仍要调用 `Typeface::clearTypefaceCache()`（JUCE 缓存最近 10 个）才会注销。与中日文、emoji 混排与自动回落正常，原生与软件图像都画出彩色 emoji。回落到的字体：中文与日文为 PingFang SC，韩文为 Apple SD Gothic Neo，emoji 为 Apple Color Emoji，`❤` 为 Zapf Dingbats，阿拉伯文为 Geeza Pro；`∑` 自带字体里有，不回落。回落字体跟随请求的字重（Lato Bold 的中日文落到 PingFang SC Semibold，因为 PingFang 没有 Bold），斜体不跟随（落到正体）。
- JUCE 自带合成：粗体在 CoreText 纯色路径上不生效（覆盖率与 Regular 相同），渐变填充与软件图像上生效（覆盖率约 +55%），确认不一致；斜体在所有组合下都生效，纯色走文字矩阵、其余走轮廓，观感一致。
- 自绘伪造：
  - 伪斜体：错切系数 0.2 至 0.25 观感合理，纯色与渐变、原生与软件一致。
  - 伪粗体（字形原样绘制，再对轮廓描边）：描边 0.045 em 时，纯色、渐变与软件三条路径的覆盖率几乎相同（161.7、161.1、160.7，Helvetica Neue 28px），所以伪造的粗细不随填充方式改变。但与真 Bold 的比值不同：CoreText 纯色路径下 Regular 本身比轮廓路径浓约 16%（CoreText 的字体平滑），0.045 em 与真 Bold 几乎相等（163.7 对 161.7）；轮廓路径下真 Bold 为 147.7，0.045 em 比它重约 9%，约 0.035 em 才相当。13 至 15px 下 0.045 em 读起来是明显的粗体、略挤，0.036 偏中等，默认值取 0.04 em 是折中。字距不变，字号大时（0.06 em）笔画会黏连。
  - CoreText 与轮廓两条路径画同一个 Regular，粗细本来就差约 16%（真 Bold 差约 10%），这是 JUCE 在 macOS 上的固有差异，与伪造无关，不做补偿。
- 可变字体错位（SF Pro、Noto Sans CJK SC VF、SF Compact）：与 Windows 不同。HarfBuzz 排版宽度随命名实例（SF Pro 从 Ultralight 的 248.7 增大到 Black 的 309.9，与 CoreText 的 243.9 至 306.7 接近，差 1% 至 2%）；CoreText 纯色路径画出真实实例（覆盖率 46.5 至 213.8）；渐变填充与软件图像的轮廓固定是默认实例（覆盖率恒为 92.5 与 92.1），字形不随实例变粗，排版却按实例加宽，出现“字稀、间距大”。SF Compact 与 Noto 同样。静态对照族 SF Pro Text 四条路径一致。只有默认实例在所有路径上一致（SF Pro 的默认实例是 Regular，Noto 是 Thin，SF Compact 的默认实例接近 Black），因此仍只支持静态字面，可变字体不选命名实例。
- 默认字体候选：Helvetica Neue 加 PingFang SC（中文回落，也是系统自带的静态字面，Helvetica Neue 有 100、200、300、400、500、700 及各自斜体，没有 600、800、900）在 13 至 15px、1x 与 2x 下都清晰，与同样静态的 Arial 相比更接近 Windows 上的 Segoe UI。系统 UI 字体 `.AppleSystemUIFont` 是可变字体，只有 Regular 在各路径上一致，选它等于放弃 600 以上的真字面，而且中文回落到隐藏的 `.PingFang UI SC`；SF Pro Text 不是系统预装；Avenir Next 偏细偏宽。选 Helvetica Neue。
- 字号语义（原型中发现，不属于字体匹配）：Arrange 现在以 `FontOptions(fontSize)` 建字体，数值是 JUCE 高度（上下行之和），换算到 em 的系数因字体而异：Lucida Grande 0.849、Helvetica Neue 0.858、Arial 0.895、SF Pro Text 0.838、Avenir Next 0.732、PingFang SC 0.714；`fontSize` 14 对应的 em 是 10 至 12.5。中文回落字体沿用同一个高度，PingFang 的系数比拉丁字体小，中文因此比拉丁字母小约 16%（默认字体 Lucida Grande 下肉眼可见）。以 `withPointHeight` 建字体（数值即 em）则中英一致。只换默认字体时，Helvetica Neue 的 em 与 Lucida Grande 相差 1%，现有布局基本不变；一旦开放 `fontFamily`，同一个 `fontSize` 在不同字体族下大小最多差 25%（Arial 对 PingFang SC）。
- 字号与行高改按 em 的验证（macOS）：以 `withPointHeight(14)` 建字体，Helvetica Neue、Arial、Avenir Next、Menlo、PingFang SC 五个族的拉丁 run 与中日文回落 run 的 em 全是 14.00，旧写法下回落 run 为 10.00、拉丁 run 为 10.25 至 12.53，约 16% 的缩小消失，同一 `fontSize` 换族 em 不变。行盒：JUCE 一行的高度是该行各 run 的“上下行之和”取最大再加上统一的加性行距，Helvetica Neue 的上下行之和是 1.165 em，PingFang SC 是 1.4 em。因此按现在的做法（以主字体算一个加性行距）喂入 `lineHeight` 时，同一段文字里含中文的行比纯拉丁的行高（`lineHeight` 取 1.5 em 即 21 时，拉丁行 21.00，含中文的行 24.29），`lineHeight` 小于上下行之和时则被 `max(0, …)` 截成上下行之和而不生效。加性行距允许负值，行距本身可以做到小于上下行之和（PingFang 的 -2.8 得到 16.8）。

## 范围

### 1. 文字样式 API

- `fontFamily`：字体族名列表，按顺序回落；末尾隐含平台默认字体。
- `fontWeight`：100 至 900 的数值，规则同 CSS；另给 `FontWeight.Thin` 至 `FontWeight.Black` 常量，只是数值的写法便利，样式名不向下传递。
- `fontStyle`：`'normal'` 或 `'italic'`。
- 用于 Text 的 `style`、Input 的 `textStyle` 与 `DrawScope.drawText`；进入排版缓存键与原生 schema。
- `fontSize` 与 `lineHeight` 都是 SP，SP 的定义是 em：名字沿用，数值就是字体的 em 大小（对齐 CSS 的 `font-size` 与 Compose 的 `sp`），经 Density 的 `spScale` 缩放，不再是 JUCE 高度（上下行之和）。JUCE 侧用 `FontOptions::withPointHeight` 建字体，其点高度即 CoreText 与 DirectWrite 的字体大小，拉丁与回落字体的 em 一致已在 macOS 原型与两个平台的原生测试中验证。这是破坏性变更：现有数值不按旧高度换算兼容，框架默认字号、Demo 与测试基线中的字号按 em 语义一次重新取值，在 ADR 中记为破坏性变更。
- `lineHeight` 是 em 语义下的绝对行距（对齐 CSS 的 `line-height: <length>`），与字体上下行之和无关：未设置时取 1.2 倍字号，设置值小于 1 倍字号时按 1 倍字号处理（core 已有此规则），允许小于字体的上下行之和（半行距为负）。一行的位置不再由 JUCE 的行盒决定：每行行距都是 `lineHeight`，基线取主字体（`fontFamily` 的首个可用字体）的半行距加上行，中日文与 emoji 回落字形画在同一条基线上，可以略高于或低于行盒，与 CSS 的固定行高一致。排版结果中的行高、基线、总高、光标与选区矩形都按这一规则出，不读 JUCE 的行盒。

### 2. 字面解析由 Arrange 完成

- 枚举族内全部字面，经平台原生接口读出每个字面的真实字重与斜体，按族缓存。系统字体：Windows 为 DirectWrite `GetWeight`，macOS 为 CoreText `kCTFontWeightTrait`（按 Apple 刻度映射并取整到百位）；枚举时排除非常规宽度的字面，按 PostScript 名去重。自带字体：两个平台都直接解析字节里的 OS/2 表（字重、`fsSelection`），不经平台接口，`faces` 的覆盖项优先。
- 按 CSS 字体匹配算法选字面：请求 400 至 500 时先找 500 以内，再往下，再往上；小于 400 先往下；大于 500 先往上；斜体依次找斜体、倾斜体、正体。
- 选中的字面经 `withTypeface` 交给 JUCE（macOS 上以 CoreText 样式名取字面，Windows 上以英文字面名取字面），不依赖 JUCE 的名字匹配与触发式合成，两个平台结果一致。
- 只支持静态字面；可变字体只按默认实例使用，不暴露调节轴，枚举时不把命名实例当作可选字面。两个平台上的错位形态不同（见两节原型结论），但只有默认实例在所有绘制路径上一致。

### 3. 伪粗体与伪斜体

- 有真字面就用真字面，没有时才伪造，默认规则同 CSS `font-synthesis`：请求 600 及以上而选中字面低于 600 时伪造粗体；请求斜体而族内没有斜体与倾斜体时伪造斜体。
- 可关闭伪造，关闭后严格使用选中的字面。
- 伪造由 Arrange 自己绘制：斜体为绘制时的错切变换；粗体为字形轮廓加描边（默认约 0.04 em），字距不变。窗口、离屏与纯色、渐变各路径上伪造部分的粗细一致；macOS 上 CoreText 纯色路径画出的正体本身比轮廓路径浓约 16%，是 JUCE 的固有差异，不补偿。

### 4. 系统字体与自带字体

- 系统字体按族名使用。
- 自带字体经 Vite import 或 `public/` 取得地址，以 `defineFontFamily(name, faces)` 声明，faces 给出地址与可选的字重、字形覆盖；字节走现有资源获取层（live 与 dist 同一条链路），加载后由运行时持有字面。
- 加载完成前用回落字体排版，到达后推进字体环境代际重排；可声明预加载，首帧等声明的字体到齐。
- 默认字体改为各平台的静态 UI 字体（避开 Segoe UI Variable、SF Pro 等可变字体）：Windows 为 Segoe UI，中文回落 Microsoft YaHei UI；macOS 为 Helvetica Neue，中文回落 PingFang SC。
- 缺字回落继续交给平台：中日韩文字与 emoji。

### 5. 字体环境代际与文字重排

- 字体注册表变化、自带字体到达或默认字体变化时推进代际。
- 代际推进后 Text 与 Input 重新测量；Canvas 与绘制修饰器中含文字的绘制片段重建并重绘，不重新布局。

## 本期不做

- 富文本与一段文字内的多种样式。
- 字距、OpenType 特性（等宽数字等）、下划线等装饰线。
- 可变字体调节轴。
