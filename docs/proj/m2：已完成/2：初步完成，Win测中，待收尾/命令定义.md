# M2.2 命令定义与执行流程

本文是 CLI 重写期间的命令执行规格。命令与工程形态见 [Arrange CLI 与工程模式](../../../arch/31-ArrangeCLI与工程模式.md)；定义、扫描矩阵与 LSRA 语义见 [托管与同步母文档](../../../arch/32-ArrangeCLI托管与同步模型.md)。本文用 Mermaid 明确命令顺序、交互位置和退出分支，不重复矩阵定义。

## 命令入口

命令和参数定义见 [CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#命令)。本期交互使用 Clack，配置校验使用 Zod，YAML 使用 `yaml` 库。

## `arrange create`

### 目标与交互输入

创建标准 Arrange 工程，写入共享配置和初始 UI/native 文件。向导收集：

- 创建位置：当前目录或项目名子目录。
- project name、project version、Arrange framework version。
- vendor name、vendor code、plugin code。
- plugin type：`effect` 或 `instrument`。
- UI package manager：`pnpm` 或 `npm`。
- products：`standalone`、`vst3`。
- UI、native、artifacts 目录。
- 各 ManagedItem 是否启用。
- 可选 framework registry 和 CMake FetchContent URL。

生成接口见[托管模型](../../../arch/32-ArrangeCLI托管与同步模型.md#物理定义接口)。

### 流程

```mermaid
flowchart TD
    A["arrange create"] --> B["启动交互向导，选择工程根和目录"]
    B --> C["填写项目、framework、UI、native 信息"]
    C --> D["选择 products 与 ManagedItem"]
    D --> E["校验输入并展示完整摘要"]
    E --> F{"用户确认？"}
    F -->|否或取消| AB["结束，不写工程"]
    F -->|是| G["构造 ProjectState，解析生成所需拓扑"]
    G --> H["调用各 File.make(state)"]
    H --> I{"文件种类"}
    I -->|文本| J["File 委派 Cluster.make(state)"]
    J --> K["Cluster 生成外壳并委派 Region.make(state)"]
    I -->|JSON| L["File 汇合 JsonRegion.make(state) 的字段结果"]
    K --> M["汇合各文件生成结果"]
    L --> M
    M --> N["展示并确认写入计划；写共享配置、初始源文件与 .gitignore"]
    N --> O{"立即 sync？"}
    O -->|否| DONE["报告创建完成"]
    O -->|是| P["运行完整 arrange sync"]
    P --> Q{"sync 成功？"}
    Q -->|是| DONE
    Q -->|否| FAIL["报告工程已创建及同步失败原因"]
```

### 完成条件

- 工程根有合法 `arrange.project.yaml`，按配置生成所需 UI/native 初始文件和最小源文件。
- create 的生成结果与后续 CONFIG 使用同一套定义。
- local 尚未准备时由后续 SETUP 负责；选择立即 sync 不意味着同步必然成功。

## `arrange adopt`

### 目标与输入

收编已有 UI/native 工程。保持选择新建或复用、复制或原位引用的交互；项目已在 CWD 对应位置时不重复复制，目录名不同于默认值时可询问是否改名。

native 由用户明确目录、`native.target` 和项目配置，不分析 CMake 正文来反推字段或定位区块。UI 可读取 package.json 等结构化文件展示现状，由用户提供并确认工程配置。选择托管的文本内容通过同一套 Wrapper/Marker 交互接入，不恢复旧的智能文本候选或反哺配置流程。

### 流程

```mermaid
flowchart TD
    A["arrange adopt"] --> B["选择新建或复用 native"]
    B --> C["复用时选择复制或原位引用，必要时确认目录名"]
    C --> D["用户填写 native 项目信息"]
    D --> E["选择新建或复用 UI"]
    E --> F["复用时选择复制或原位引用"]
    F --> G["读取可用 JSON 信息，用户确认 UI 配置"]
    G --> H["选择 ManagedItem，汇总 ProjectState 草案"]
    H --> I["补齐输入、校验配置、展示将修改的文件"]
    I --> J{"用户确认？"}
    J -->|否或取消| AB["结束，不接管"]
    J -->|是| K["按选择接入目录；新文件由统一定义生成"]
    K --> L["保存共享配置，运行 CONFIG LSRA 接入托管"]
    L --> M{"CONFIG 成功？"}
    M -->|否| FAIL["报告接入未完成，结束"]
    M -->|是| N{"立即准备环境？"}
    N -->|否| DONE["报告 adopt 完成"]
    N -->|是| O["重新加载 State，运行 SETUP LSRA"]
    O --> P{"SETUP 成功？"}
    P -->|是| DONE
    P -->|否| SF["报告托管已接入及环境准备失败原因"]
```

### 完成条件

- 配置完整并经用户确认，所选托管通过 CONFIG 接入。
- 既有文本区块通过用户指定的 Wrapper 建立定位，未托管内容不被接管。
- 后续 sync 从保存的 State 推导拓扑，不依赖 adopt 的一次性内存坐标。

## `arrange sync`

参数选择见 [CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#命令)。

### 完整同步编排

```mermaid
flowchart TD
    A["arrange sync"] --> B["解析部分、范围与 scan 参数"]
    B --> C{"仅扫描？"}
    C -->|是| SO["进入扫描模式，输出所选部分报告后结束"]
    C -->|否| D{"包含 CONFIG？"}
    D -->|是| E["运行 CONFIG LSRA"]
    E --> F{"CONFIG 成功？"}
    F -->|否或放弃| AB["失败退出 sync"]
    F -->|是| G{"包含 SETUP？"}
    D -->|否| G
    G -->|否| DONE["sync 完成"]
    G -->|是| H["重新加载 ProjectState"]
    H --> I["运行独立的 SETUP LSRA"]
    I --> J{"SETUP 成功？"}
    J -->|是| DONE
    J -->|否或放弃| AB
```

### CONFIG LSRA

```mermaid
flowchart TD
    S["SCAN：重新加载 State，推导拓扑，尽可能扫描"] --> R["产出完整 ConfigScanReport"]
    R --> F{"RESOLVE：报告中有 Fatal？"}
    F -->|有| AB["展示报告，失败退出；不修复其他 Issue"]
    F -->|无| Q{"有 Resolvable？"}
    Q -->|有| ONE["取一个 Issue，进入对应交互"]
    ONE --> O{"处理结果"}
    O -->|取消| AB
    O -->|继续：写入或用户编辑后| S
    Q -->|无| READY["RESOLVE 完成"]
    READY --> A["APPLY：执行最后一轮报告的 Applicable"]
    A --> OK{"写入成功？"}
    OK -->|是| END["CONFIG 完成；不追加复检"]
    OK -->|否| ERR["保留事务信息，报告失败并退出"]
```

### CONFIG SCAN 的遍历

父级门控与四类结果使用[母文档的扫描矩阵](../../../arch/32-ArrangeCLI托管与同步模型.md)，下图展开当前扫描器的遍历顺序。

```mermaid
flowchart TD
    A["读取 State，收集配置诊断"] --> B{"有可信输入可推导拓扑？"}
    B -->|无| C["记录 Fatal 及无法展开的范围"]
    C --> C2["完成不依赖该输入的可用检查"]
    C2 --> Z["汇总四类结果"]
    B -->|有| D["按启用 ManagedItem 和范围取得 Region 及物理祖先"]
    D --> EX["委派期望值计算；非法期望记录 Fatal"]
    EX --> FILE{"还有可扫描 File？"}
    FILE -->|无| Z
    FILE -->|有| READ["委派下一 File.check 读取并检查"]
    READ --> FS{"文件状态"}
    FS -->|缺失| FM["记录 Resolvable；后代不进入扫描"]
    FS -->|读取失败| FF["记录 Fatal；后代不进入扫描"]
    FM --> FILE
    FF --> FILE
    FS -->|可读| KIND{"文本还是 JSON？"}
    KIND -->|JSON| JP{"JSON 可解析？"}
    JP -->|否| JF["记录 Fatal；JsonRegion 不进入扫描"]
    JF --> FILE
    JP -->|是| JR["逐个委派参与 JsonRegion 的 check，汇总结果"]
    JR --> FILE
    KIND -->|文本| CL{"还有可扫描 Cluster？"}
    CL -->|无| FILE
    CL -->|有| CW["委派下一 Cluster.check，复用 locate"]
    CW --> CS{"定位结果"}
    CS -->|missing 或 damaged| CF["记录 Resolvable；其参与 Region 不进入扫描"]
    CF --> CL
    CS -->|located| TR["以 Cluster inner 委派参与 TextRegion.check"]
    TR --> COL["收集四类结果；受损坏波及的区域不进入扫描"]
    COL --> CL
```

期望非法和父级失败都只阻断依赖该输入的判定；其他具有可信输入的对象继续扫描。报告引用与验收示例见 [SCAN 结果各项与对策](SCAN结果各项+对策.md)。

### CONFIG RESOLVE 的一次交互

此处的入口已经通过 Fatal 检查。每次只处理一个 Resolvable；所有编辑返回完整 SCAN，不继续消费旧报告。

```mermaid
flowchart TD
    A["接收一个 Resolvable Issue"] --> K{"对象与判定"}
    K -->|File missing| FC{"确认创建文件？"}
    FC -->|是| FW["调用 File.make 并写入"]
    FC -->|否| AB["Abort sync"]
    K -->|Cluster 或 TextRegion missing| M{"已有内容还是新建？"}
    M -->|已有| W["用户给已有区块补长期 Wrapper"]
    W --> V{"locate 验证 Wrapper 是否有效？"}
    V -->|无效| RETRY{"继续编辑？"}
    RETRY -->|是| W
    RETRY -->|否| AB
    V -->|有效| S["结束本次交互，reload 并全量 SCAN"]
    M -->|新建| MARK["用户在父级范围内放一次性 Marker"]
    MARK --> MV{"Marker 位置是否有效？"}
    MV -->|无效| MR{"继续编辑？"}
    MR -->|是| MARK
    MR -->|否| AB
    MV -->|有效| GEN["调用对应定义 make，替换 Marker"]
    GEN --> S
    M -->|取消| AB
    K -->|Cluster 或 TextRegion damaged| FIX["展示标记错误，要求用户修复"]
    K -->|JsonRegion damaged| JFIX["展示文件、路径与实际类型，要求用户编辑"]
    FIX --> CONT{"用户继续还是取消？"}
    JFIX --> CONT
    CONT -->|继续| S
    CONT -->|取消| AB
    K -->|JsonRegion missing| JC{"确认补入字段？"}
    JC -->|是| JW["按 JsonRegion.locate 路径写入 make 结果"]
    JC -->|否| AB
    JW --> S
    FW --> S
```

若发现用户在交互期间同时修改了 YAML，结束当前 Issue 的交互并回到完整 SCAN，不再依据旧 expect 或旧托管开关写入。位置验证不通过时不写入，用户可修复或取消。对应处理的语义边界以母文档为准。

### CONFIG APPLY

```mermaid
flowchart TD
    A["接收最后一轮无阻塞报告"] --> B{"Applicable 为空？"}
    B -->|是| DONE["CONFIG 完成"]
    B -->|否| C["按报告的定位与期望内容，按 File 组合更新"]
    C --> D{"文件快照与写入范围仍有效？"}
    D -->|否| FAIL["报告失败，保留已有恢复信息"]
    D -->|是| E["创建 .arrange/ journal"]
    E --> F["写目标旁临时文件，逐个替换并记录进度"]
    F --> G{"全部成功？"}
    G -->|否| FAIL
    G -->|是| H["标记完成，清理恢复记录并报告更新清单"]

```

区间换算与替换规则见[恢复与应用](../../../arch/32-ArrangeCLI托管与同步模型.md#config-的恢复与应用)，写入保护见[事务约定](../../../arch/32-ArrangeCLI托管与同步模型.md#arrange-与写入失败)。

### 扫描模式

```mermaid
flowchart TD
    A["sync --scan"] --> B["按选择取得部分与范围"]
    B --> C{"包含 CONFIG？"}
    C -->|是| D["运行 CONFIG SCAN，保存完整报告"]
    C -->|否| E{"包含 SETUP？"}
    D --> E
    E -->|是| F["按当前可信输入执行 SETUP 的只读扫描入口"]
    E -->|否| G["输出已选部分的报告与受阻范围"]
    F --> G
    G --> H{"存在 Fatal 或 Resolvable？"}
    H -->|是| FAIL["非零状态结束"]
    H -->|否| END["正常结束，Applicable 只展示不执行"]
```

SETUP 在扫描模式中观察当前实际状态，不假定 CONFIG 的 Applicable 已被执行；无法开展的范围必须说明。扫描对象与分类以[托管母文档](../../../arch/32-ArrangeCLI托管与同步模型.md)为准。

### SETUP LSRA

SETUP 管环境和设施准备状态，使用项目需求与本机设置，运行独立 LSRA。完整 sync 中，它在 CONFIG 成功并重新加载 State 后开始。

```mermaid
flowchart TD
    A["加载 State 与快照，按范围探测工具和实际准备状态"] --> B["输出独立 SetupScanReport"]
    B --> C{"有 Fatal？"}
    C -->|是| FAIL["报告阻塞，结束"]
    C -->|否| SC{"仅 scan？"}
    SC -->|是| RESULT["报告缺失、待执行动作和可用状态，不写入"]
    SC -->|否| D{"有 Resolvable？"}
    D -->|是| E["确认检测到的本机配置，或提示用户编辑工具配置"]
    E --> F{"取消？"}
    F -->|是| AB["结束，不执行后续准备"]
    F -->|否| A
    D -->|否| G["核对快照，执行所选 Applicable"]
    G --> H["UI install 或 native Debug/Release configure"]
    H --> I{"工具执行及产物模型验证成功？"}
    I -->|否| ERR["报告失败，不宣告 ready"]
    I -->|是| DONE["保存成功准备记录，SETUP 完成"]
```

SETUP 的具体检查和准备记录归属见[托管母文档](../../../arch/32-ArrangeCLI托管与同步模型.md)；平台与工具契约见[CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#版本与工具链)。

## `arrange dev`

### 目标

拉起开发环境和测试程序。包含 native 时，每次都执行正式 Standalone 增量构建，再定位产物；不静默修改工程托管配置。各 flavor/范围的资源来源以[CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#dev)为准。

### 流程

```mermaid
flowchart TD
    A[arrange dev] --> B[加载 ProjectState]
    B --> C[只读检查 CONFIG、所选工具链与准备状态]
    C --> D{配置待同步或工具/准备缺失？}
    D -->|是| E[报告问题并提示 arrange sync]
    D -->|否| F[解析 ui-only/native-only 与 flavor]
    F --> G{ui-only？}
    G -->|否| H{Standalone 在 products 中？}
    H -->|否| I[提示使用 --ui-only 或修改 project 后 sync]
    H -->|是| K[正式增量构建所选 flavor 的 Standalone，再用共享定位器]
    K --> M{Debug 完整模式？}
    G -->|是| U[准备 UI dev server]
    M -->|是| L[准备 Live UI 服务和 Standalone，不要求 UI dist]
    M -->|否| MODE{Release 完整模式？}
    MODE -->|是| UB[构建 UI]
    MODE -->|否：native-only| DIST[使用现有 UI dist；缺少则提示先 UI build]
    UB --> PACK[package Standalone，准备 packed binary]
    DIST --> PACK
    L --> O[DevSupervisor 检查地址占用，等待 UI 就绪后启动 native]
    U --> O
    PACK --> O
    O --> P{进程退出或收到信号？}
    P -->|任一进程退出| Q[停止关联子进程并返回结果]
    P -->|Ctrl+C| R[停止全部子进程并正常结束]
    P -->|异常退出| S[报告进程错误并停止全部]
```

地址占用、准备超时、启动失败和提前退出均结束监管并释放资源。Ctrl+C 是正常结束，不应渲染为错误。Release 和 native-only 不由 CLI 启动 UI 服务，但不覆盖 native 的 App source 选择；具体边界见[CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#dev)。

## `arrange build`

### 目标

构建可用的 UI/native 产物。默认 flavor 为 `release`，默认 products 来自 ProjectState；完整构建默认继续进入 pack，`--no-pack` 可关闭。

### 流程

```mermaid
flowchart TD
    A[arrange build] --> B[加载 ProjectState]
    B --> C[解析 flavor、范围、products、clean]
    C --> D[检查 sync 与工具链状态]
    D --> E{工程或工具链未 ready？}
    E -->|是| F[报告 arrange sync 或 SETUP]
    E -->|否| G{需要 UI？}
    G -->|是| H[标记 UI 构建开始，执行 package manager build，验证入口并记录结果]
    G -->|否| I[跳过 UI]
    H --> J{需要 native？}
    I --> J
    J -->|是| K[标记 native 构建开始，执行 CMake configure]
    J -->|否| L[跳过 native]
    K --> M[按 products 构建 native targets，记录成功或失败]
    L --> N{允许 package？}
    M --> N
    N -->|是| O[调用 package 整理 artifacts]
    N -->|否| P[报告构建完成]
    O --> P
```

`--ui-only` 不执行 native，也不 pack；`--native-only` 不执行 UI，也不 pack；`--no-pack` 只跳过 pack。任何构建失败均不进入后续 pack。build 结尾说明打包去向（打包完成、已跳过、或因范围未打包），pack 完成时列出交付目录、产品位置、二进制大小与清单。`--clean` 范围和构建记录语义见[CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#build)。

## `arrange pack`

### 目标

只整理已有的 UI/native 构建产物，不 install、不 configure、不 build。

### 流程

```mermaid
flowchart TD
    A[arrange pack] --> B[加载 ProjectState]
    B --> C[解析 flavor、products、clean]
    C --> D[读取已有 CMake 模型，定位完整产品与 UI dist]
    D --> E{配置/架构/目标/入口/构建记录与路径安全检查通过？}
    E -->|否| F[报告失败；旧交付物保留]
    E -->|是| G[在同文件系统 staging 中整理所选产品]
    G --> H[整体复制 UI；按 clean 范围保留或重建所选目录]
    H --> I[验证完整 bundle、资源、Mac 签名和轻量清单]
    I --> J{全部 staging 验证成功？}
    J -->|否| F
    J -->|是| K[备份所选旧输出，逐项替换并提交清单]
    K --> L{提交成功？}
    L -->|是| M[清理临时目录，打印交付路径]
    L -->|否| R[逆序回退；无法恢复时保留并报告备份位置]
```

产物布局、构建记录缺失时的手工产物边界、clean/回退与 Mac 签名策略见[CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#交付物布局与提交)。package 不以模拟测试通过代替宿主运行验收。

## 完成判据

- 命令实现与对应 Mermaid 流程一致，失败、取消与扫描模式有明确出口。
- CONFIG 满足[报告验收案例](SCAN结果各项+对策.md)，特别是完整收集四类结果、父级阻断后不扫描子项、每轮只修一个 Issue 和重扫。
- create/adopt 复用统一定义，受管文本以 Wrapper 定位，不引入正文反向解析。
- SETUP 独立验收工具、安装结果、configure 模型与准备记录，不把 CONFIG 的矩阵直接当作其实现。
- build/pack 的失败不得宣告成功或先破坏旧交付；dev 结束后没有关联长进程残留。
- clean/storage/recover 的确认后重查、资源占用、归属核验和中断恢复均有真实执行验证；扫描与取消预览不执行清理、修复或恢复。
- Windows/Mac 的真实执行记录分别保存；本轮 Windows 结果与 Mac 待验收项见[存储维护与验收优化记录](20261013-CLI存储维护与验收优化.md)。

## 维护命令执行规格

以下逐项规定维护命令的执行与交互。参数契约见[CLI 母文档](../../../arch/31-ArrangeCLI与工程模式.md#工程与用户级维护命令)，目录归属与缓存引用见[用户目录母文档](../../../arch/35-Arrange用户目录与源码缓存.md)，资源取得与等待见[资源协议](../../../arch/36-ArrangeCLI资源占用与进程生命周期.md)，事务格式与恢复边界见[托管模型](../../../arch/32-ArrangeCLI托管与同步模型.md#持久事务与独立恢复)。

修改命令必须先展示计划并交互确认；非交互环境不能代替用户确认，可使用 `--scan`。预览、未选择内容或确认前取消均不执行修改；执行中断按持久事务报告恢复入口。参数错误、占用失败、计划变化及执行错误报告失败，不宣告完成。

### `arrange clean`

#### 目标与参数

清理当前工程生成结果，独立于 `build --clean` 的清理后构建行为。

```text
arrange clean [--ui-only | --native-only | --artifacts-only]
              [--artifacts] [--flavor debug|release] [--scan]
```

| 参数 | 本次计划范围 |
|---|---|
| 默认 | UI 输出与本平台当前架构的 Debug、Release 构建树，保留交付物 |
| `--ui-only` | 仅 UI 输出及其构建记录 |
| `--native-only` | 仅 native 构建树及其构建记录 |
| `--artifacts-only` | 仅清单确认归属的交付物 |
| `--artifacts` | 在默认范围中加入受管交付物 |
| `--flavor debug\|release` | 仅缩小 native 范围；默认范围中的 UI 仍清理 |
| `--scan` | 取得所选范围只读占用，展示计划后退出 |

三个单范围参数互斥，也不能与 `--artifacts` 混用；`--flavor` 不用于 `--ui-only` 或 `--artifacts-only`。

#### 流程

```mermaid
flowchart TD
    A["arrange clean"] --> B["校验参数，加载工程并核验归属、路径与未完成事务"]
    B --> C["展示具体清理路径与原因"]
    C --> D{"无内容或仅 scan？"}
    D -->|是| VIEW["报告无内容或预览完成，结束"]
    D -->|否| E["记录目标内容身份，询问确认"]
    E --> F{"用户确认？"}
    F -->|否或取消| CANCEL["报告取消，不执行清理"]
    F -->|是| G["整组取得工程配置与所选范围写占用"]
    G --> H["重新加载工程，重算计划并比较内容身份"]
    H --> I{"计划与内容保持一致？"}
    I -->|否| FAIL["报告变化，要求重新运行并确认"]
    I -->|是| J["记录删除事务，移入隔离目录并清除"]
    J --> K{"执行及收尾成功？"}
    K -->|是| DONE["报告工程清理完成"]
    K -->|失败或中断| RECOVER["报告原因与 arrange recover 入口"]
```

#### 完成与退出条件

- 仅移除计划内生成结果和相应构建记录；保留源码、依赖、配置、日志、恢复材料及用户额外交付文件。
- 无有效归属清单的手工交付物不猜测删除；损坏清单、路径重叠、危险链接或未完成事务阻止执行。
- `--scan` 遇到资源忙立即报告，不能以不稳定视图宣告扫描成功。正常执行按资源协议等待，可取消。
- 清理执行失败或中断时保留恢复所需记录；删除事务只提供继续完成，不提供撤销删除。

### `arrange storage inspect`

#### 目标与输入

查看本用户工程登记及受管资源，可在工程外运行，无范围参数。

```text
arrange storage inspect
```

#### 流程

```mermaid
flowchart TD
    A["arrange storage inspect"] --> B["读取工程登记，发现构建树、源码与获取临时内容"]
    B --> C["核验可访问性、归属和引用，统计逻辑字节数"]
    C --> D["对非工程条目尝试取得只读占用"]
    D --> E{"资源忙或无法稳定查看？"}
    E -->|是| WARN["附注无法稳定查看及原因"]
    E -->|否| OK["保留本轮检查结果"]
    WARN --> OUT["逐项输出 ID、状态、路径、引用与大小，结束"]
    OK --> OUT
```

#### 完成与退出条件

- 逐项展示记录、内容、归属、工程、准备与引用事实，并输出具体原因、阻断路径及清理结论；状态与判定依据见[存储检查母文档](../../../arch/35-Arrange用户目录与源码缓存.md#存储检查事实与清理判定)。
- 工程登记不统计大小；资源统计不完整时标明“至少”。结果是本轮快照，占用检查失败时明确附注。
- 不登记工程，不执行删除、修复或事务恢复；归属和引用未知时报告不确定性。

### `arrange storage clean`

#### 目标与参数

选择释放本用户可确认安全清理的资源，可在工程外运行。

```text
arrange storage clean [--scan]
```

候选包括归属明确的孤儿构建树、引用已完整核验的无引用依赖源码及可识别的获取临时内容。扫描同时列出排除原因；没有候选不等于没有库存。外部目录、运行时数据和归属或引用未知的资源不进入候选；不提供强制删除参数。

#### 流程

```mermaid
flowchart TD
    A["arrange storage clean"] --> B["扫描库存，展示可清理条目的 ID、大小与路径"]
    B --> C{"无候选或仅 scan？"}
    C -->|是| VIEW["报告库存为空或候选及排除原因，结束"]
    C -->|否| D["交互多选资源，记录所选内容身份"]
    D --> E{"已选择且确认？"}
    E -->|否或取消| CANCEL["报告取消，不执行清理"]
    E -->|是| F["整组尝试取得共享依赖源码维护与目标目录写占用"]
    F --> G{"取得成功？"}
    G -->|否| BUSY["报告占用失败，结束"]
    G -->|是| H["比较内容身份，重扫归属、引用及未完成用户事务"]
    H --> I{"所选条目仍可清理？"}
    I -->|否| FAIL["报告变化或恢复要求，不执行删除"]
    I -->|是| J["记录删除事务，清理所选资源及对应源码请求索引"]
    J --> K{"执行成功？"}
    K -->|否或中断| RECOVER["报告原因与 arrange storage recover 入口"]
    K -->|是| L["仅在已无已知构建时移除失效工程登记"]
    L --> DONE["报告用户级清理完成"]
```

#### 完成与退出条件

- 只处理用户所选条目；确认后有内容、归属或引用变化必须重新查看，不能沿用旧计划。
- 资源忙立即失败；有未完成用户事务时先要求 `storage recover`。不会主动停止其它命令或跳过占用检查。
- 正常工程登记保留；失联或失效登记仍有已知构建时保留，以便继续追踪。
- 执行失败或中断保留事务；清理事务只可继续完成。

### `arrange storage repair <id>`

#### 目标与参数

按缓存记录的确切 commit 重新获取共享依赖源码，不升级依赖版本。

```text
arrange storage repair <id> [--scan]
```

`id` 使用 inspect 输出的 `deps-src:<16位十六进制键>`，也接受省略 `deps-src:` 的键；旧 ID 不作别名。`--scan` 仅展示源码路径与受影响构建，不发起修复网络请求。

#### 流程

```mermaid
flowchart TD
    A["arrange storage repair"] --> B["查找源码条目，展示路径与引用它的构建树"]
    B --> C{"仅 scan？"}
    C -->|是| VIEW["预览结束"]
    C -->|否| D["确认重新获取并使相关准备状态失效"]
    D --> E{"用户确认？"}
    E -->|否或取消| CANCEL["报告取消，不执行修复"]
    E -->|是| F["整组取得共享依赖源码维护及受影响构建写占用"]
    F --> G["重查记录、完整引用与未完成用户事务"]
    G --> H["创建替换事务，临时获取确切 commit 及子模块并核验"]
    H --> I{"获取与核验成功？"}
    I -->|否或中断| FAILED["保留失败事务，报告 storage recover 入口"]
    I -->|是| J["失效受影响构建的准备记录，记录替换步骤"]
    J --> K["备份旧源码，发布新快照，清理备份与事务"]
    K --> L{"提交及收尾成功？"}
    L -->|否或中断| FAILED
    L -->|是| DONE["报告修复完成，提示重新运行 native SETUP"]
```

#### 完成与退出条件

- 条目不存在、记录损坏、引用不完整或存在未完成用户事务时报告失败；不能猜测来源或迁移旧格式记录。
- 按资源协议等待占用，允许取消；获取失败不得发布半成品源码。
- 成功只表示源码修复完成；受影响工程须重新运行 `arrange sync --setup --native` 才能恢复准备状态。
- 暂存未完成的替换事务仅可回退清理；进入替换阶段后由实际文件状态决定可继续或可回退。

### `arrange recover [id]`

#### 目标与参数

恢复当前工程 `.arrange/transactions` 内的持久事务，可用于初始化尚未完成、工程配置尚未齐全的目录。无需先安装 Framework 或完成 SETUP。

```text
arrange recover [id] [--scan]
```

无 `id` 时只列事务；有 `id` 时展示目标路径、冲突和当前实际可用动作。`--scan` 展示后退出；继续、回退通过交互选择，不提供强制覆盖或强制解锁参数。

#### 流程

```mermaid
flowchart TD
    A["arrange recover 或 arrange storage recover"] --> B["按入口选择事务根，读取记录"]
    B --> C["列出事务 ID、类型、状态或读取错误"]
    C --> D{"给定事务 ID？"}
    D -->|否| LIST["仅列出，结束"]
    D -->|是| E["校验记录与路径，展示目标、冲突及可用动作"]
    E --> F{"仅 scan 或无可用动作？"}
    F -->|是| VIEW["预览结束；无动作时提示人工处理"]
    F -->|否| G["选择继续或回退，再确认执行"]
    G --> H{"用户确认？"}
    H -->|否或取消| CANCEL["报告取消，不执行恢复"]
    H -->|是| I["整组取得恢复所需资源占用"]
    I --> J["重读记录，核验路径与内容，再生成恢复计划"]
    J --> K{"记录一致且所选动作仍可执行？"}
    K -->|否| FAIL["报告冲突，保留记录与材料"]
    K -->|是| L["执行所选动作并完成事务收尾"]
    L --> M{"成功？"}
    M -->|是| DONE["移除事务记录，报告事务恢复完成"]
    M -->|否或中断| RETAIN["报告原因，保留未完成事务"]
```

#### 完成与退出条件

- 可用动作按当前文件事实计算：文件写入、初始化和替换可在满足条件时继续或回退；删除只有继续。
- 用户新增或修改的内容不能被强行覆盖或删除；源内容消失、备份缺失等情况可能使动作不可用。
- 损坏或不认识的记录须报告人工处理；没有可用动作不输出“事务恢复完成”。
- 恢复成功完成事务收尾；失败或执行取消继续保留恢复材料。外部包管理器或编译器副作用不属于文件事务回退范围。

### `arrange storage recover [id]`

#### 目标与参数

恢复 `~/.arrange/transactions` 内的用户级清理、源码修复等事务，可在工程外或原工程已不存在时执行。

```text
arrange storage recover [id] [--scan]
```

#### 流程与完成条件

使用上一节恢复流程，但从用户目录读取事务，按受管用户资源与登记构建路径核验恢复范围；不读取当前目录的工程事务。无 ID 列出、有 ID 展示与选择、scan、取消、冲突及完成出口均与工程级恢复一致。

用户级清理失败提示此入口；源码修复事务完成后，若相关准备记录已失效，仍须在受影响工程重新运行 native SETUP。不能用用户级恢复入口代替工程级事务恢复。
