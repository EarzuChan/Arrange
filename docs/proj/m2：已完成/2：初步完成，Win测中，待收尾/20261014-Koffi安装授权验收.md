# Koffi 安装授权验收

本轮仅完成主人批准的 Koffi/pnpm 安装策略整改，QuickJS/Lazy 执行预算未改。

## 修改

根 pnpm-workspace.yaml 的 allowBuilds 增加 `koffi: true`，只授权该依赖的安装脚本；没有开放全部脚本，没有关闭自动依赖检查。CLI 继续直接依赖锁定的 koffi 2.14.1，package.json 与 pnpm-lock.yaml 未改，不新增锁实现或原生 helper。

Koffi 的 `--prebuild` 安装脚本先检验预构建模块是否可加载，可加载则直接完成；否则按上游实现尝试源码构建。当前 darwin arm64 的 Node 24/26 均使用包内预构建模块，不宣称已实测源码构建回退。锁和工作进程语义见[资源占用与进程生命周期](../../../arch/36-ArrangeCLI资源占用与进程生命周期.md#内核锁与工具工作进程)。

## 验证

环境：macOS arm64，pnpm 11.15.0；Node 26.5.0 与 24.18.0。两个独立工作区复制当前源码及锁文件，初始没有 node_modules，各用独立空 pnpm store，从 registry 下载依赖；不复制现有安装或其构建结果。安装均使用 `pnpm install --frozen-lockfile`。

首次独立包消费者安装遭 registry tarball 下载超时，日志保留；随后使用已核验缓存、prefer-offline 和单下载并发完成安装，不把首次失败计为通过。该消费者使用自身明确的安装授权：根仓库 pnpm-workspace.yaml 不会替代下游工程的脚本审批策略，也没有设置用户全局策略。

安装包探针首次显式 createRequire 使用 pnpm 的逻辑链接位置，导致探针附加的版本读取找不到 koffi；改为以安装包物理路径建立 require 后通过。生产 KernelLock 的导入和安装包代码未改；探针失败记录与修正后记录分别保留。

## 证据与范围

忽略材料位于仓库 `build/mac-cli-acceptance-20261014/`：

- `koffi-clean-install`、`koffi-node24-install`：两套干净安装日志与 result.json。
- `koffi-clean-cli`、`koffi-node24-cli`：两套完整 CLI 回归。
- `koffi-clean-build`、`koffi-node24-build`、`koffi-clean-types`：构建与类型检查。
- `koffi-workspace-install`、`koffi-workspace-operations`：当前工作区安装及定点回归。
- `koffi-clean-pack`、`koffi-consumer-install`、`koffi-consumer-install-retry`：本次 CLI 包及独立消费者安装。
- `koffi-consumer-probe`、`koffi-consumer-probe-corrected`、`koffi-consumer-probe-node24`：安装包探针原始和最终结果；消费者目录下 probe.mjs 为可复核源码。
- `koffi-clean-context.json`、`koffi-integrity.json`：隔离工作区与锁文件一致性。

Windows x64 和 macOS x64 本轮未运行。包内包含这些平台的预构建模块只证明文件存在，不证明其可加载或锁/Job Object 行为；等待真实设备安装、测试与回归。Windows 与 macOS 锁/进程实现未改，Framework 运行时未改，QuickJS 预算调查保持待办。
