# M5-EX2：微软 D2D1 真实窗口渲染归因测试

历史实验日期：2026-11-14。以下六组数据来自 0.10.1 基线加临时诊断，不是 0.10.2 的复测结果。当前数据口径见[开发期诊断表层](../../arch/25-开发期诊断表层.md#渲染归因采集)。

## 结论

在本轮首页快速往返滚动和动画页反复「全部播放」的真实窗口测试中，关闭滚动图块稳定减少 CPU 绘制开销。SVG 蒙版缓存保留了独立收益；普通位图缓存的 native 转换没有解释动画页的大幅回退。此前合成列表对图块有利的结果不能用于推断这两个真实页面。

这轮只添加可拆分的开关、计数、自动化夹具和报告，不继续修改降级或绘制策略。

## 环境和方法

- 基点：本地 `636926b`（0.10.1），加本轮诊断改动；没有重新测 0.9.x，也没有使用特制 D2D1
- Windows 11 10.0.26300，RTX 5070 Ti，驱动 621.01；Release、JUCE 8.0.12
- 真正创建 DocumentWindow + ArrangeEditor，选取 Direct2D 引擎；每次运行通过 GetModuleFileName 验证实际加载 `C:\WINDOWS\SYSTEM32\d2d1.dll`
- 完整画廊 UI 从 Demo 源码与素材编译到独立 gallery 夹具，不读正式 Demo 的 dist、构建或安装目录；未启动音频设备，因此这是借用 Demo UI 的真实窗口夹具，不是正式 Standalone 产品的端到端验收
- 窗口逻辑尺寸 900×780，实际客户区截图 1350×1170，系统缩放 150%（DPI 144）
- 首页：8 秒，每 40 ms 发送一次 ±360 滚轮，每 700 ms 反向，共 200 次；鼠标停在页面内容上，悬停按正常链路处理
- 动画：通过只读诊断定位可见「动画」卡并用系统点击进入，8 秒内每 450 ms 点击「全部播放」，共 18 次
- 测量输入由独立线程按固定截止时刻 SendInput，不因 UI 卡顿而少发；导航、等待就绪、截图和写文件在测量阶段外
- 每组独立进程，六组、三轮共 18 个有效运行；第二轮反向顺序。每轮输入次数相同；动画记录的节点数实际在 53 至 59 间变化，验证点击确实生效
- 截图直接从屏幕客户区 BitBlt，不用离屏重新绘制替代窗口截图
- 正式运行中另有 2 次首帧 15 秒未就绪，已单独保存并排除，重跑成功。桌面协调前的鼠标/前台干扰短测试也不计入

## 结果

下表是三轮的「每次 paint 回调平均 CPU 调用耗时」取中位数，单位 ms。不是屏幕帧时间，不据此换算 FPS。

| 开关组合 | 首页猛滚 | 动画 toggle |
| :--- | ---: | ---: |
| 全部开启 | 8.310 | 1.633 |
| 只关图块，保留两项缓存优化 | 5.847 | 0.103 |
| 只关普通位图缓存的 native 转换 | 8.776 | 1.641 |
| 只关 SVG 蒙版缓存 | 8.578 | 1.664 |
| 关图块 + 关 native 转换 | 5.964 | 0.158 |
| 关图块 + 关 SVG 蒙版缓存 | 6.040 | 0.169 |

全开与只关图块的各轮结果：

| 轮次 | 首页全开 / 关图块 | 动画全开 / 关图块 |
| :--- | ---: | ---: |
| 1 | 8.314 / 5.847 | 1.608 / 0.104 |
| 2 | 8.192 / 5.742 | 1.633 / 0.100 |
| 3 | 8.310 / 5.934 | 1.640 / 0.103 |

关闭图块后，首页 paint 平均耗时下降约 30%，动画约 94%。这是 CPU 绘制调用耗时的变化，不意味着屏幕 FPS 增加同一比例。按固定 8 秒测量窗口累计，框架流水线加 paint 耗时由首页约 357 ms/秒降至 290 ms/秒，动画约 247 ms/秒降至 40 ms/秒。

首页已绘制修订的 paint CPU P95 从 16.694 ms 降至 12.514 ms；动画从 4.078 ms 降至 0.142 ms。首页发布间隔 P95 从 18.769 ms 降至 12.565 ms，动画发布间隔基本都在 6.25 ms。这些发布间隔依然不是 DXGI/DWM 呈现间隔。

## 归因

全开情况下，每个阶段 8 秒内计数与耗时的三轮中位数：

| 指标 | 首页 | 动画 |
| :--- | ---: | ---: |
| 新建图块数 | 396 | 2161 |
| 局部修补图块次数 | 1316 | 639 |
| 持续变化降级次数 | 61 | 611 |
| 图块构建 CPU 调用耗时 | 316.8 ms | 1383.7 ms |
| 图块修补 CPU 调用耗时 | 1878.9 ms | 248.9 ms |
| 片段比较 CPU 调用耗时 | 1.0 ms | 1.1 ms |
| 特征扫描 CPU 调用耗时 | 2.1 ms | 3.2 ms |
| 普通位图缓存 native 转换调用耗时 | 7.0 ms | 0 ms |

- 动画页的问题主要落在反复构建与修补图块，比较和扫描只占几毫秒，之前怀疑整树扫描是主要回退来源的说法不受本次数据支持
- 首页局部修补尤其昂贵，已修补面积变小并不意味着离屏上下文和提交成本就足够低
- SVG 蒙版生成在保留缓存时只发生少量初始构建，关闭缓存后重复生成；图块关闭时动画 paint 从 0.103 增至 0.169 ms，说明缓存仍有独立收益，但不能从这里重复外推此前每图标 0.25 ms 的合成估计
- native 转换开关只控制普通 BitmapCache 的结果转换，图块自身仍使用原生图。这里没有证据支持将 native 转换视为动画回退的主因；不能据此推断所有图片密集场景也无收益
- GetProcessTimes 的整个进程 CPU 时间也已保留，但轮间波动大，包含 JUCE、驱动与后台线程，不能用它替代已分段的 paint 计时作精确归因
- 构建、修补、位图与 SVG 生成计时存在包含关系，不把它们全部相加当总 CPU 时间

## 实现验证

- Release 全量原生构建与 CTest：30 项通过
- 新增测试覆盖 native 开关的缓存命中与转换语义、原生输入不重复转换、诊断关闭不累计、SVG 缓存关闭输出一致
- TypeScript 类型检查和 `git diff --check` 通过；真实窗口夹具为手动目标，不加入无人值守 CTest
- 默认三个优化开关仍全部开启，新增细分计时默认关闭；本轮没有修改版本号、tag、已发布包或正式 Demo 配置

## 限制与后续

本轮未采集 PresentMon/ETW，未覆盖正式音频宿主、其它窗口尺寸、其它 DPI 和其它 GPU；不能把发布间隔拿去与主人的呈现 FPS 表直接比较。这里足以确认图块在这两个操作负载上的 CPU 绘制回退；0.10.2 据此正式删除图块实现，保留两项缓存优化。
