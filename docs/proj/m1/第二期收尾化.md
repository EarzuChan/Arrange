第一期收尾化已经把 M1 主链路收紧到基本可封存状态。第二期收尾化继续延续：不推翻主链路，也不做革命式大清洗，而是：继续把 final review 中确认的轻微欠债彻底收束干净。

本期核心原则：**宁可少暴露，也不要假暴露；凡是公开 API，必须有 TS API、QuickJS reader、core/native 语义、pipeline 行为、测试覆盖的闭环。**

# 收尾原则

1. 主链路不变。
   - Vue/TS runtime 仍通过 QuickJS native API 直接调用 C++。
   - C++ 仍直接读取 JSValue。
   - 变更仍进入 typed MutationTransaction。
   - LayoutTree 与 SceneFramePipeline 仍是唯一 native UI pipeline。

2. 不接受“半支持”。
   - TS 暴露但 native 不执行，错误。
   - native 有字段但 pipeline 不使用，错误。
   - 未来会支持所以现在先放着，错误。
   - 可以留下中文注释说明“将来添加回来”，但当前公开面必须干净。

3. 不做兼容包袱。
   - M1 尚未对外发布，不需要兼容错误 API。
   - 已经确认是孤儿、半吊子、假支持的公开面，必须删除。

4. prop 必须 schema 化，semantics 留待以后正规化。
   - 直接读取 JS object 不等于允许任意对象横穿 native。
   - PropValue 只能是受控 carrier，不能重新变成“任意数据协议”。
   - testTag / accessibility / inspector 所需 semantics 通道本期不半吊子恢复；以后必须作为独立专题正规添加回来。

# 现存问题

## 1. `pointerInput` 是半支持 API

文件：

- `packages/runtime/src/modifier.ts`
- `native/arrange_quickjs/src/QuickJsModifierReader.cpp`
- `native/arrange_core/include/arrange/core/Modifier.h`
- `native/arrange_core/src/Modifier.cpp`

具体问题：

- TS 公开 `Modifier.pointerInput(handler)`。
- QuickJS reader 只把它读成 `result.input.pointerInput = true`。
- `handler` 没有注册为 callback。
- core 没有 `PointerInput` EventSlot。
- pointer dispatch 当前实际只支持 clickable / scroll 等已落地路径。

这会造成“用户以为 pointerInput 能用，但 handler 永远不会被调用”的假支持。

## 2. FocusRequester 是孤儿 API

文件：

- `packages/runtime/src/state.ts`
- `packages/runtime/src/modifier.ts`
- `native/arrange_quickjs/src/QuickJsModifierReader.cpp`

具体问题：

- `state.ts` 仍导出 `rememberFocusRequester`、`useFocusManager`、`FocusRequester`。
- `Modifier.focusRequester(...)` 已经不在公开 modifier API 中。
- QuickJS reader 明确拒绝 `focusRequester` / `onFocusChanged` / `focusProperties` / `focusGroup`。
- native focus 目前只覆盖 Input 自身的 focus、caret、IME、text session，不存在 JS 请求 focus 的正规链路。

这会造成“用户能 import focus requester，但没有正规挂载路径”的孤儿公开面。

## 3. PropValue / `setProp(value: unknown)` 仍有任意 carrier 气味

文件：

- `packages/runtime/src/native.ts`
- `native/arrange_quickjs/src/QuickJsNativeApi.cpp`
- `native/arrange_quickjs/src/QuickJsValueReader.cpp`
- `native/arrange_core/include/arrange/core/PropValue.h`
- `native/arrange_core/src/PropValue.cpp`

- `native/arrange_core/src/Paint.cpp`
- `native/arrange_juce/src/TextInputLayoutModel.cpp`

具体问题：

- TS 侧 `setProp` 仍接收 `value: unknown`。
- QuickJS 侧 `propValue` 仍递归读取 object。
- core 侧仍通过 `objectProp` / `stringProp` / `numberProp` / `boolProp` / `colorProp` 分散读取 props。
- 当前虽然已经移除宽松跨类型转换，但 prop key、prop shape、合法对象结构尚未统一 schema 化。

这不是旧 JSON 链路复活，但如果继续放任，会形成新的“任意对象 native prop 协议”。

## 4. testTag / semantics 没有正规通道，但本期不做

文件：

- `packages/runtime/src/modifier.ts`
- `native/arrange_core/include/arrange/core/Modifier.h`
- `native/arrange_core/src/LayoutTree.cpp`
- `cpp_tests/arrange_core_smoke.cpp`
- `cpp_tests/arrange_quickjs_app_smoke.cpp`

具体问题：

- 第一阶段已删除 demo 中的 `testTag` 占位使用，这是正确的。
- 但测试、Inspector、accessibility 未来都需要稳定的声明式 metadata 通道。
- 当前没有 `CompiledModifier.semantics` 或等价结构。
- 不能把 `testTag` 再作为普通 layout/paint/input modifier 偷偷塞回去。

semantics 应当是独立、正规、可测试的语义通道，而不是临时调试字段。

本期结论：

- 不恢复 `testTag`。
- 不新建 semantics core 通道。
- 不把 semantics 塞进普通 prop map 冒充完成。
- 只保留中文注释说明：将来会把 semantics / testTag 作为完整正规通道添加回来。

## 5. diagnostics logger 还没有形成最小闭环

文件：

- `native/arrange_juce/include/arrange/juce/ArrangeEditor.h`
- `native/arrange_juce/src/*Diagnostics*`
- `native/arrange_juce/src/RuntimePackageLoader.cpp`
- `native/arrange_juce/src/PackageRuntimeSource.cpp`
- `packages/runtime/src/index.ts`
- `packages/runtime/src/native.ts`

具体问题：

- 文档已经要求开发期诊断表层包含日志，但当前还没有真实 `DiagnosticEvent` 结构体和统一公开 logger API。
- 当前仍存在 `DiagnosticsOverlay` 旧命名；这个畜生在暗示旁路 overlay，而不是事件事实源 / scene / state 的明确职责拆分。
- 模块过程日志、用户可见诊断、toast、错误屏、Copy diagnostics 的事件事实源需要收敛到 `DiagnosticEvent`。

- file sink 初期可同步，但当前文档与实现都必须明确禁止在 audio thread、paint 或高频关键路径依赖同步文件 I/O。

这属于 M1 可显著提升可维护性和用户可诊断性的收尾项。

## 6. Icon 当前是假资源语义

- `native/arrange_juce/src/ImageResourceCache.cpp`

具体问题：

- Demo 写了 `<Icon source="play" ... />`。
- 当前 native painter 没有解析 `play`，而是对所有 `DrawIcon` 硬编码绘制同一个三角形。
- 这会造成 `Icon source` 看起来能用，实际不读取用户资源。

- Image 不提供 tint；位图着色、滤镜或 shader 留待后续专门设计。

这属于“native 有字段、pipeline 不按字段执行”的假支持，必须在本期收尾化清掉。

## 7. clipping / overflow 语义还没有完全落地

文件：

- `docs/arch/11-Modifier.md`
- `docs/arch/12-内建组件.md`
- `docs/arch/18-文本输入与绘制.md`
- `native/arrange_core/src/Layout.cpp`
- `native/arrange_core/src/Paint.cpp`
- `native/arrange_juce/src/JuceDrawOpsPainter.cpp`

具体问题：

- 文档已经确认普通容器默认不裁剪，显式 `m.clip(shape)` 才裁剪，scroll / Lazy viewport 必须自带 viewport clip。
- 当前实现已支持 `m.clip(...)` 生成 `PushClip / PopClip`，这是正确方向。
- 但滚动容器当前可见实现重点是平移内容，必须确认并补齐 viewport clip，不能只平移不裁剪。
- `Text overflow` 与视图 clipping 是两件事；当前 `DrawText` 总是 `reduceClipRegion(...)`，会导致 `overflow: "visible"` 不真实。
- `ellipsis` 当前主要只对单行可靠，多行 overflow 需要至少明确现阶段行为并避免和普通 clipping 混用。

这属于“链路语义不圆满”的局部重造项：不是推翻主链路，但必须在本期把默认容器裁剪、显式 clip、scroll viewport clip、Text overflow 的边界落干净。

- Standalone 与 VST3/AU/AAX 的路径、权限、生命周期、多实例行为不同，当前不得伪装已有通用最佳实践。

本期只做边界约束与窄能力整理：保留显式 native diagnostics log file 配置，不设计和实现通用 storage API；远期 `ArrangeStorage` 已进入想法暂存器。

- 支持 level：`trace` / `debug` / `info` / `warn` / `error`。
- 支持分层 category，至少覆盖：
  - `app`
  - `host.live`
  - `host.dist`
  - `host.hmr`
  - `runtime.script`
  - `runtime.transaction`
  - `pipeline.frame`
  - `pipeline.layout`
  - `pipeline.paint`
  - `input.pointer`
  - `input.key`
  - `input.ime`

  - `resource.image`

  - `diagnostics.setLogLevel(...)`
  - `diagnostics.setCategoryEnabled(...)`
  - `diagnostics.setToastsEnabled(...)`

## 7. clipping / overflow 必须按 Compose 思路落地

要求：

- 普通容器默认不裁剪子内容。
- `m.clip(shape)` 必须是显式裁剪，裁剪后续绘制与子内容，不改变测量尺寸。
- `m.clip(shape)` 必须保留 Modifier 顺序语义，不能把不同链条折叠成同一种绘制结果。
- `verticalScroll` / `horizontalScroll` 必须自带 viewport clip，不能只平移内容。
- Lazy viewport 必须自带 viewport clip。
- scroll viewport clip 不改变测量尺寸，不删除 layout tree 内容，只限制绘制与命中范围。
- 命中测试应按 viewport 裁掉不可见滚动内容后再派发。
- Text `overflow` 只处理 Text 自身文字溢出：
  - `clip`：裁在 Text rect 内。
  - `ellipsis`：有界宽度与行数限制下省略。
  - `visible`：Text 自身不主动裁剪，但仍受祖先 clip、scroll viewport、Lazy viewport、宿主根窗口裁剪。
- `DrawText` 不得无条件 `reduceClipRegion` 导致 `overflow: "visible"` 失真。
- 多行 ellipsis 若本期无法做到完整终局，也必须明确当前支持边界，不得和普通 clipping 混作完成。

验收标准：

- `m.clip(...)` 有顺序语义测试。
- 普通父容器不因默认父 bounds 裁剪子内容。
- vertical / horizontal scroll 内容不会画出 viewport。
- Text `overflow: "visible"` 在无祖先 clip 时可画出 Text rect。
- Text `overflow: "clip"` 被裁在 Text rect。
- Text 单行 `overflow: "ellipsis"` 可靠。
- clipping / overflow 的 dirty repaint 边界无法证明时选择 full fallback，不得漏画。
