本文件记录第五期正规化的现存问题、必须的解决方案，以及后续执行时的工作空间。

第五期不是为了推翻第四期。第四期已经把最危险的旧问题收住：QuickJS event slot 不再假注册，scroll 不再由 native 直接写旧派生 prop，Modifier 不再走多套旧派生 SetProp，Debug / Release demo 已经由主人验收可用。

第五期要处理的是更深一层的质量问题：当前主链路已经可用，但协议边界、internal invalidation、diff 表达、代码规范仍有一些“旧味道”。这些问题不一定马上导致崩溃，但会在后续功能扩展时重新制造双链路、隐式协议、魔法 prop、测试与生产割裂。

第五期目标：在不破坏第四期已稳定链路的前提下，把剩余的“半正规化接口”和“不够硬的职责边界”继续收束。生产链路仍必须只有一条；任何新增或保留的内部通道，都必须有明确职责、明确类型、明确测试，不能靠名字约定和特判凑合。

核心原则：

- 已通过验收的 Debug / Release demo 行为不能回退。
- QuickJS、TS runtime、native core 不能各自定义一套 bridge / value / modifier 编码语义。
- internal invalidation 不能伪装成普通声明 props。
- event slot dirty 必须被结构化表达，不能靠“diff 为 0 时保底标 dirty”这种猜测式处理。
- 测试 reference 只能服务测试，不能重新变成生产语义来源。
- 代码质量必须进入可维护状态，不能让格式混乱、旧命名、半成品接口继续成为后续复制模板。

# 现存问题

## 1. `native/arrange_quickjs/src/QuickJsScriptHost.cpp` 仍保留泛用 JS value serializer，协议边界不够硬

`native/arrange_quickjs/src/QuickJsScriptHost.cpp` 仍有：

- `serializeJsValue(...)`
- `serializeObject(...)`
- `serializeArray(...)`
- `encodeBridgeValue(...)`

第四期已经删除了 QuickJS 解释完整 JS Modifier 实例的 fallback 路径，这是正确的；但 QuickJS 现在仍有一套泛用 JS value -> encoded bridge string 的序列化规则。

这意味着当前至少仍存在两套 value 编码逻辑：

- TS 侧：`packages/runtime/src/bridge.ts` / `packages/runtime/src/renderer.ts`
- QuickJS 侧：`native/arrange_quickjs/src/QuickJsScriptHost.cpp`

风险点包括：

- `undefined` / `null` 的处理是否一致；
- function 是否一致地只用于 callback binding，不进入 command buffer；
- object / array 的 JSON 序列化细节是否一致；
- event slot binding `{eventSlot, callback}` 与 encoded `{eventSlot}` 的边界是否一致；
- `setProp` 与 `setModifier` 在 object commit / command buffer 两条提交形式中是否共享同一 schema。

这不是要求 QuickJS 完全不读 JS object。QuickJS 同进程 object commit 客观存在，必须读取 JS 对象字段。但 QuickJS 不应继续像一个自由 JSON serializer；它只能按标准 `BridgeOp` / `BridgeModifierPayload` schema 读取并编码。

## 2. `packages/runtime/src/bridge.ts` 的 `commitCommandBuffer` 仍是边界不清的半成品接口

`packages/runtime/src/bridge.ts` 中 `NativeCommitTarget` 暴露：

```ts
commitCommandBuffer?: (bytes: Uint8Array) => void
```

但当前生产 Vue mount / patch 主要走：

```ts
commit?: (ops: Array<BridgeOp | NativeCommitCommand>) => void
```

object commit 与 command buffer 并不等价：

- object commit 是 QuickJS 同进程生产路径，可以携带 callback binding；
- command buffer 是 serializable bridge，只能携带无 callback payload；
- command buffer encode 会去掉 callback；
- command buffer 当前更多用于 fixture / test，而不是完整生产路径。

如果这个接口继续以普通生产能力暴露，后续调用方会误以为 `commitCommandBuffer` 与 `commit` 完全等价，从而绕开 event slot callback 注册链路。

## 3. `native/arrange_juce/src/TextInputMutationSink.cpp` 仍通过 magic SetProp 表达 native internal invalidation

`native/arrange_juce/src/TextInputMutationSink.cpp` 的 `invalidateNativeState` 仍构造 `SetProp`：

```cpp
op.key = flag == DirtyFlag::Paint
             ? "__arrangeNativeInputPaintInvalidation"
             : "__arrangeNativeInputStateInvalidation";
```

第四期已经在 `native/arrange_core/src/LayoutTree.cpp` 中把这两个 key 拦截为 internal dirty intent，不再写入普通 `node.props`。这是正确的阶段性修复。

但它仍然有旧味道：native 内部状态失效被伪装成 Bridge `SetProp`，再由 `LayoutTree` 特判识别。

正确方向应该是：

```txt
native text input state changed
-> explicit InputIntent / NativeInvalidation / dirty API
-> LayoutTree / InvalidationGraph
-> SceneFramePipeline
```

而不是：

```txt
native text input state changed
-> fake SetProp("__arrangeNativeInput...")
-> LayoutTree magic key 特判
```

## 4. `packages/runtime/src/app.ts` 仍有 `__arrangeSubtreeReplaced` 内部 prop 通道

`packages/runtime/src/app.ts` 中在 `setElementText(...)` 场景仍会提交：

```ts
{op: "setProp", id, key: "__arrangeSubtreeReplaced", value: true}
```

这不是第四期禁止的 Modifier 派生 prop，但仍属于“内部结构/刷新意图塞进普通 prop”的模式。

问题必须界定清楚：

- 如果 native 没有消费 `__arrangeSubtreeReplaced`，那它就是无意义脏数据和无意义 invalidation。
- 如果 native 消费它，那它就是隐式协议，应改成明确 opcode / intent / dirty API。
- 如果它只是为了触发刷新，那刷新请求不能伪装成普通声明 prop。

第五期必须查明并处理这个通道，不能让它继续作为不明含义的内部 prop 残留。

## 5. `native/arrange_core/src/LayoutTree.cpp` 的 `SetModifier` diff 为 0 时强行标 `EventSlot` dirty，表达不够精确

`native/arrange_core/src/LayoutTree.cpp` 中当前逻辑是：

```cpp
if (diff.dirtyMask == 0) {
    markDirtyAttributed(op.id, DirtyFlag::EventSlot, ...);
    break;
}
```

这个逻辑有现实动机：Modifier 的 layout / paint / transform 没变，但 callback 绑定或 event slot metadata 可能变了。

但这种写法仍不够严格。它把“没有 layout/paint 变化”与“event slot metadata 变化”混在一起，靠保底 dirty 维持正确性。

第五期应该把 `CompiledModifierDiff` 从单一 `dirtyMask` 继续结构化，至少明确：

- layout 是否变化；
- paint 是否变化；
- transform 是否变化；
- hit-test/input 是否变化；
- focus 是否变化；
- scroll event slot 是否变化；
- click event slot 是否变化；
- parent data / zIndex 是否变化。

event slot dirty 必须来自真实字段比较，而不是 `diff.dirtyMask == 0` 的 fallback。

## 6. `native/arrange_core/src/Paint.cpp` 仍通过 `style.type` 字符串分派 paint 行为

第四期引入 `PaintChainOp` 后，padding / background / clip 的顺序语义已经比之前明确，不再靠 `paddingIndex` / `sizeSeen` 一类补丁反推顺序。

但 `native/arrange_core/src/Paint.cpp` 仍通过：

```cpp
style.type == "background"
style.type == "border"
style.type == "alpha"
style.type == "dropShadow"
style.type == "innerShadow"
```

来分派绘制行为。

这不是当前崩溃问题，但仍不是最终干净的 compiled semantics。理想上，Modifier 编译后应该把 paint 行为变成 typed enum / typed op，而不是 Paint 阶段继续读字符串类型。

当前可以接受 `PaintChainOpKind` 作为过渡，但第五期应至少明确是否继续推进到 typed paint op。

## 7. `native/arrange_juce/src/RuntimePackageLoader.cpp` 格式和局部代码规范明显不合格

`native/arrange_juce/src/RuntimePackageLoader.cpp` 中存在明显格式问题，例如：

```cpp
int statusCode = 0;
const auto options = ...
auto stream = ...
  if (!stream) {
...
result.initialTransaction=std::move(*initialTransaction);
result.scriptHost= std::move (scriptHost);
```

这类代码虽然不一定影响运行，但会成为后续复制和维护的坏模板。

第五期必须整理该文件格式，并检查是否存在同类不规范写法：

- 缩进混乱；
- 操作符两边空格不一致；
- `std::move (...)` 这种非规范格式；
- 局部变量和分支排版不清晰；
- error / diagnostic 构造重复。

## 8. `native/arrange_core/src/LayoutTree.cpp` 局部整洁度仍有明显毛刺

`native/arrange_core/src/LayoutTree.cpp` 中 `isEventProp(...)` 后存在多余空行等局部毛刺。

这类问题不是逻辑 bug，但第五期如果要进入更高规格维护，应顺手清理，避免核心文件继续呈现“刚修过、没整理”的状态。

## 9. `packages/runtime/src/test/headlessLayout.ts` 是测试 reference，但仍有双维护风险

第四期已经把 TS 侧 layout reference 从生产入口隔离到：

```txt
packages/runtime/src/test/headlessLayout.ts
```

并通过 `@arrange/runtime/test` 暴露测试工具。这是正确的。

但该文件仍然是一套 TS layout / paint reference。只要后续新增 Modifier 语义，就有风险出现：

- native core 改了一套；
- headless test reference 又改一套；
- 测试开始验证 reference 自己，而不是验证真实 native pipeline。

第五期不一定要删除它，但必须约束它的职责：它只能是轻量 headless test harness，不能重新成为生产语义来源，不能要求每个生产 Modifier 都维护 TS / native 两份完整实现。

## 10. `native/arrange_core/src/LayoutTree.cpp` 的 event prop 判定过宽

`native/arrange_core/src/LayoutTree.cpp` 当前 `isEventProp(...)` 使用：

```cpp
key.rfind("on", 0) == 0 ||
key.rfind("__arrangeEventSlot.", 0) == 0 ||
key.find("EventSlot") != std::string_view::npos
```

这能覆盖当前事件 prop，但判定偏宽：

- 任意 `on...` prop 都被视为 event dirty；
- 任意包含 `EventSlot` 的 prop 都被视为 event dirty；
- 如果未来有普通业务 prop 或 accessibility prop 命中该模式，会被错误归类。

第五期应把事件 prop 识别收束到明确名单或明确 schema，不能让 dirty attribution 靠宽泛字符串猜测。

# 必须的解决方案

## 1. 收束 QuickJS value 编码职责

必须处理 `native/arrange_quickjs/src/QuickJsScriptHost.cpp` 中泛用 serializer 的职责边界。

要求：

- QuickJS 可以读取 object commit 中的标准 `BridgeOp` 字段；
- QuickJS 可以读取标准 event slot binding 的 `callback`；
- QuickJS 不能重新解释 Modifier 语义；
- QuickJS 不能通过自由 JSON serializer 扩展出 TS schema 之外的协议；
- `setModifier` 只能接受标准 array payload，不是标准 payload 时必须明确拒绝或输出空 payload并记录错误口径，不能悄悄 fallback；
- value 编码规则必须与 `packages/runtime/src/bridge.ts` 对齐，并由测试覆盖。

验收：

- 新增/调整测试覆盖 object commit 与 command buffer 对无 callback payload 的等价编码；
- 测试覆盖 function / undefined / event slot binding 的边界；
- QuickJS 不再承担 Modifier fallback serializer 职责。

## 2. 明确 `commitCommandBuffer` 的阶段定位

必须在代码层面处理 `commitCommandBuffer`。

允许两种方向，必须选择其一：

### 方向 A：标为 experimental / test-only

- 类型命名或注释必须明确它不是完整 runtime commit 等价物；
- 不能让生产 `createApp(...).mount(...)` 自动优先走它；
- 测试必须明确它不能携带 callback；
- 文档或类型注释必须说明 object commit 与 command buffer 的差异。

### 方向 B：升级为明确生产二进制桥

- callback/event slot 注册必须有独立真实通道；
- command buffer payload 必须完全 serializable；
- object commit 与 command buffer 对无 callback payload 必须等价；
- native decode 后必须进入同一 `LayoutTree` apply 链路；
- 不能出现二进制路径和 object 路径各自定义 Modifier schema。

第五期默认建议方向 A，除非决定本阶段投入完整 binary bridge。

## 3. 删除 text input native invalidation 的 fake SetProp 通道

必须整改：

- `native/arrange_juce/src/TextInputMutationSink.cpp`
- `native/arrange_core/src/LayoutTree.cpp`

目标：

- `__arrangeNativeInputPaintInvalidation` / `__arrangeNativeInputStateInvalidation` 不应继续作为生产 Bridge prop 出现；
- 如果短期需要兼容测试，测试必须明确证明这些 key 不会进入普通 props，不得扩大使用范围。

验收：

- 生产源码中不再由 `TextInputMutationSink.cpp` 构造这两个 magic prop；
- `LayoutTree` 不再需要通过普通 `SetProp` 分支识别 native input invalidation；
- key / text / ime 输入仍触发正确 frame pipeline；
- 输入、IME 的最终人工验收仍留给主人。
