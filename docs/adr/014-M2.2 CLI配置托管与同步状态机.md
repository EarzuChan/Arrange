# ADR 014：M2.2 CLI 配置托管与同步状态机

日期：2026-09-14

## 背景

M2.2 第三期重写伟大 CLI。早期实现把生成、配置检查和同步执行分散在多个服务中，无法稳定表达文件、结构块、区域和逻辑托管项之间的关系。新版需要让 create、adopt 和 sync 使用同一套无状态定义，并让有副作用的交互修复与常规批量更新分开。

## 决策

1. `ProjectState` 取代 `ProjectContext`，包含 `rootDir`、`project` 和 `local`。
2. File、Cluster、Region、ManagedItem 都是无状态定义，具体结果由传入的 ProjectState 和本次扫描产生。
3. File → Cluster → Region 表达物理关系；ManagedItem → Region 表达逻辑关系，ManagedItem 可以跨文件、跨 Cluster。
4. sync 的 CONFIG 与 SETUP 均采用 `SCAN → RESOLVE → APPLY`。SCAN 无副作用；RESOLVE 每次处理一个阻塞项，产生副作用后重新加载状态并全量扫描；APPLY 只执行确定的常规更新。
5. `extraneous` 的 Resolve 选项为删除、承认现状并更新配置、放弃。无法可靠定位时必须交互定位，不以猜测代替确认。
6. `.arrange/` 作为本机工作目录，首版承载 Apply 事务 journal 和恢复信息，未来可承载可丢弃的缓存；它不替代 project/local 配置。
7. Apply 采用临时文件、内容校验和 journal 恢复信息，不承诺多文件操作系统级绝对原子性。

## 影响

create、adopt、sync、build、dev、package 必须共享 File／Cluster／Region 定义；旧的独立生成器、ConfigChecker／ConfigPerformer 双轨和 `ProjectContext` 引用应在重写中移除。历史 M2.2 实现只作为历史记录，不作为新版事实源。

长期技术事实见 [Arrange CLI 与工程模式](../arch/31-ArrangeCLI与工程模式.md) 和 [Arrange CLI 托管与同步模型](../arch/32-ArrangeCLI托管与同步模型.md)。
