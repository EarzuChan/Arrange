# ADR 014：M2.2 CLI 配置托管与同步状态机

日期：2026-09-14；2026-09-15 按 CONFIG 最终讨论重写；2026-09-16 补充接口取舍。

## 背景

M2.2 第三期重写 CLI。旧实现和早期草案混合了工程事实、物理定位、内容理解与修复动作，导致生成规则重复、托管粒度分裂，扫描结果也无法穷尽。新版选择机械化、标准化的文本托管：明确边界，按配置生成，以最小受管正文整体替换。

## 决策与理由

1. `ProjectState` 统一工程根、共享配置和本机配置；File/Cluster/Region/ManagedItem 保持无状态。各级负责自身并委派子级，避免 create、adopt、sync 分别维护实现。
2. 物理归属与 ManagedItem 的逻辑归属分开，拓扑从本次输入推导。ManagedItem 可以跨文本和 JSON，开关只到 ManagedItem，保证同一语义整体受管。
3. ManagedItem 关闭即退出 CONFIG 检查，创建时仍按需生成裸正文。关闭托管不能变成另一类强制恢复问题。
4. TextCluster 与 TextRegion 统一采用长期 Wrapper。放弃文本结构智能识别和恢复内容反哺配置，使扫描无需理解 CMake/npmrc 正文；一次性 Marker 只负责交互插入定位。
5. Cluster 仅定位和委派，已有 Cluster 不作整块过期比较或更新。TextRegion 才是正文替换单位，由此保留 Cluster 内自定义及未托管内容。
6. CONFIG SCAN 结果正式分为 Fatal、Resolvable、Idle、Applicable 四类。Fatal 先收集、继续独立扫描，再由 RESOLVE 统一阻断；父级阻断的子项当前不进入扫描。
7. Resolve 一次处理一个 Issue，交互后重新加载并全量扫描；不复用旧报告继续修下一项。Apply 只消费最终无阻塞报告，不把开发期复检加入生产流程。
8. CONFIG 管文件，SETUP 管准备状态；完整 sync 顺序执行两套独立、同构的 LSRA。SETUP 的具体矩阵与处理对策留待后续确定。
9. `.arrange/` 保留本机事务与恢复信息的定位，不成为配置来源；使用临时文件和 journal 处理写入失败，不承诺多文件绝对原子性，不设计扫描缓存。
10. 定位、检查与生成共用各级定义，生成只传 State，避免另行传递托管开关。接口与 outer/inner 约定见[母文档](../arch/32-ArrangeCLI托管与同步模型.md#物理定义接口)。

## 影响

实现须替换旧的智能候选、`unwrapped-existing`、`extraneous`、删除对策与反哺配置流程，并更新 optional null、JSON 路径 damaged 和 Wrapper 嵌套的处理。已有草稿不因本 ADR 更新而成为完成状态。

具体行为、完整矩阵和恢复规则唯一记录在[托管与同步母文档](../arch/32-ArrangeCLI托管与同步模型.md)；用户可见命令见 [Arrange CLI 与工程模式](../arch/31-ArrangeCLI与工程模式.md)。
