# ADR 021：字体样式与 SP 改为对齐 em 语义

日期：2026-11-06。状态：已定；字体样式部分 Windows 已施工完成，macOS 待验。

## 背景

M5-EX 要给文字加字体族、字重与字形，需求与两个平台的原型结论见 [M5-EX 需求与待办](../proj/m5：快完成了/02-M5-EX需求与待办.md)。原型中发现一处与字体匹配无关、但必须先解决的问题：

- 文字的 `fontSize` 是 SP，名字对齐 Compose，落到 JUCE 却是 JUCE 高度（字体上下行之和），不是 em。换算系数因字体而异：Lucida Grande 0.849、Helvetica Neue 0.858、Arial 0.895、Avenir Next 0.732、PingFang SC 0.714。
- 中日文回落字体沿用同一个 JUCE 高度，PingFang SC 的系数比拉丁字体小，同一行里中文比拉丁字母小约 16%。
- 一旦开放 `fontFamily`，同一个字号换字体最多差 25%。
- 行高同样受影响：JUCE 一行的高度取该行各字体上下行之和的最大值，含中文的行比纯拉丁行高，行高小于上下行之和时被截掉。

## 决策与理由

1. **SP 在 Compose 基本就是 em 的意思。** 名字和 `16.sp` 的写法不变，Density 的 `spScale` 照旧只缩放 SP；变的是定义：`fontSize` 的数值是字体的 em 大小，对齐 CSS 的 `font-size` 与 Compose 的 `sp`。JUCE 侧用 `FontOptions::withPointHeight`（它的点高度即 CoreText 与 DirectWrite 的字体大小）。已在 macOS 上验证拉丁与回落字体的 em 一致、换族 em 不变，Windows 与 macOS 的原生测试均已覆盖。不另造单位，也不改属性名：名实不符只靠改定义就能消除，改名要动公开 API 与 SFA 编译规则，收益只是名字。

2. **这是破坏性变更，旧数值不做兼容换算。** 旧数值是 JUCE 高度，按 em 看约为 0.85 倍，是不同字体下的不同倍数，没有统一的换算。框架默认字号、Demo 与诊断表层的字号一次按 em 重新取值：默认字号由 14 改为 12，Demo 的字号阶梯改为 29、24、16、14、13、11、10，按各字号在当前默认字体下的视觉大小取整，使现有界面的观感基本不变。使用方升级后要自己重新取值，没有迁移开关。

3. **行高是绝对行距，行盒由 Arrange 自己定。** `lineHeight` 对齐 CSS 的 `line-height: <length>`，与字体的上下行之和无关，可以小于它；未设置取字号的 1.2 倍。每行的行距恒为 `lineHeight`，基线取主字体的半行距加上行，回落字形画在同一条基线上。不沿用 JUCE 的行盒，是因为它让行距随一行里有没有回落字体而变，也无法表达小于上下行之和的行高。行高默认值同时变化：旧默认是 1.2 倍 JUCE 高度，约 1.4 倍 em，新默认 1.2 倍 em，未设置行高的文字在同一视觉字号下会略紧。

细节规则写在 [文本输入与绘制](../arch/18-文本输入与绘制.md#字号与行高)。

## 后续条目：字体样式（M5-EX 施工）

4. **字体样式字段与 Web 无关，只借用 CSS 的取值与匹配规则。** `TextStyle` 增加 `fontFamily`、`fontWeight`、`fontStyle` 与 `fontSynthesis`，三处入口（Text、Input、`drawText`）共用，全部进入排版缓存键与原生 schema；字重取 1 至 1000 的整数，`FontWeight` 常量只是数值别名，样式名不向下传递；字形只有 `normal` 与 `italic`，不做 `oblique` 角度。伪造只给一个开关而不是粗斜体各一个：粗斜体伪造是同一种“字面不够，由 Arrange 补”的行为，分开收益很小。非法值在 JS 与原生两侧都抛错，不静默忽略。

5. **字面由 Arrange 枚举、读字重、按 CSS 匹配，经 `FontOptions(typeface)` 交给 JUCE。** 不用 JUCE 的名字匹配：它没有数值字重，两个平台的匹配与合成互不一致（原型已证实 `SemiBold`、`Medium` 在两个平台落点不同，缺字重时静默落到常规体）。系统字体字重 Windows 读 DirectWrite、macOS 读 CoreText，自带字体两个平台都直接解析字节里的 OS/2 表，覆盖项优先；枚举排除模拟字面、非常规宽度字面与可变字体的命名实例，所以只支持静态字面。`fontFamily` 列表只决定主字体：按序取首个可用的族，列表里后续的族不参与逐字回落，缺字回落交给平台——JUCE 的整形接口只接受一个主字体，逐字多族回落要自写整形，不值得。默认字体为 Windows 的 Segoe UI 与 macOS 的 Helvetica Neue，都是静态字面。

6. **伪造由 Arrange 自己绘制。** 伪斜体是绕本行基线的错切（0.2），伪粗体是字形原样绘制后补一圈轮廓描边（0.04 em），字距不变。JUCE 自带的合成在 macOS 纯色路径上粗体不生效、Windows 与软件渲染路径行为不同，无法统一，所以不用。描边与字形重叠，半透明文字色下重叠处略深，不再为此引入路径布尔运算。伪斜体对一行里所有字形生效（回落字体不随斜体），伪粗体只作用于主字体（回落字体已跟随请求的字重，再描边会过粗）。

7. **自带字体走现有资源获取层，字体注册表是进程级的。** `defineFontFamily` 复用 `acquirePainter` 的请求、缓存、预算、live 与 dist 链路，解码结果是 `FontContent`（字节与 OS/2 读数）而不是图像，因此不新增第二套网络与路径逻辑；不支持 WOFF，因为 JUCE 无法解压。注册表放在进程级而不是编辑器级：JUCE 自己的字体登记就是进程级的，每个编辑器一份只会让登记路径多一层；代价是同一进程里两个 App 重名族会互相替换，登记时带运行时所有者，运行时销毁即撤销自己登记的族。加载前用回落字体排版，到达后重排；`preload: true` 的族到齐前不发布首帧，上限 3 秒，超时与失败都照常出帧——宁可先闪回落字体，也不让界面被一个坏字体卡死。

8. **字体环境代际一变，Text 与 Input 重新测量，含文字命令的绘制层重建。** 注册表任何变化都推进代际，排版服务读取代际并清空缓存，流水线运行前比较代际，变化时只标脏 Text、Input 所在节点（测量）和含文字命令的绘制 Modifier 所在节点（绘制），不整树失效；Canvas 的 `onDraw` 不重录，命令本身没变，只有排版结果换了。绘制层记录构建时的代际，代际不同即重建，因此缓存片段不会沿用旧字体的字形。运行时发现代际推进就请求一次流水线运行，不依赖其它失效。

9. **平台分歧留待 macOS 验证。** macOS 的枚举（CoreText、Apple 刻度映射）、字面取用（`createSystemTypefaceFor` 以 CoreText 样式名取字面）、默认字体与伪造观感依原型结论实现，但 macOS 部分在 Windows 上无法编译验证，验证项列在 [M5-EX 需求与待办](../proj/m5：快完成了/02-M5-EX需求与待办.md#macos-待验)。
