# ADR 016：M2.2 CLI 工程准备与交付整理

日期：2026-10-09。状态：实现及本轮 Mac 验收完成；Windows 真实机器验收待切换开发机。

## 背景

新版 CLI 已有 CONFIG 托管模型，但 SETUP、工程初始化、开发监管和交付整理尚不能组成可实际使用的工程入口。用户批准集中完成成熟 CLI，同时要求架构清晰、Windows/Mac 分层实现；本机为 Mac，Windows 的真实运行验证留待切换开发机。

早期 CLI 与 Demo 脚本的测试记录不能证明新版服务可用。Demo 迁移与旧脚本废除延后，使用临时真实工程验证本轮能力。

## 决策与理由

1. CONFIG 只维护工程文件；SETUP 必须使用真实工具链验证、安装依赖和 configure，使工程可随时 dev/build/package。写回本机配置不等同于准备成功。各阶段采用独立报告和成功记录，避免混用 CONFIG 判定。
2. 新建和接入共用现有托管定义。已有 JUCE 工程明确配置根 target，避免从显示名称或 CMake 正文猜测；命令编排通过显式服务依赖与统一 Executor 调用平台能力。
3. 原生产物以 CMake File API 为主路径，并按平台规范提升为完整 bundle。标准工程无需额外强制导出 JUCE 属性；package 与 dev 共用产物定位，避免两套路径猜测。
4. package 的交付范围首先是可运行整理：完整产品、完整 UI、必要的已知运行依赖和轻量清单。先在 staging 验证，再备份替换和失败回退，防止 clean 或复制失败破坏旧交付。
5. 采用准备记录、CLI 构建成功/失败状态及项目/Framework 版本检查阻断已知失配。手工已有产物可缺少 CLI 构建记录；不引入全仓源码指纹，也不声称能证明任意手工二进制来源。
6. Mac 保留有效签名，对 unsigned/ad-hoc 产物提供可验证的本地签名处理；身份签名失效必须报告，不能静默降级。Developer ID、notarization、installer、系统安装和发布另行设计，避免把本地可运行与公开分发混为一项完成结论。
7. 正式入口统一限制支持平台和终端性质，自动化通过显式装配入口运行。领域交互由上层注入，消除业务服务对终端实现的依赖，使完整流程测试不必修改私有成员。
8. 托管定义各自检查自身，Scanner 沿现有物理数组负责遍历与汇总；支持项在独立注册层集中声明，避免通用机制反向导入具体定义以及重复维护关联。Framework 兼容检查的来源选择与编排集中到 FrameworkService。
9. 保留单文件替换、快照检查和打包暂存回退；删除成功后长期留存的日志、恢复记录中的重复 hash 与初始化双重复制。配置写入定位为逐文件提交和失败恢复记录，不扩大为跨文件原子事务系统。
10. Painter 资源来源跟随实际 Live/Dist 源，由 Framework 注入相应获取能力并共享异步解码、状态与生命周期。完整 Debug 不为资源预先构建 UI 或打包；Live 使用已配置开发服务的资源地址，避免热更新代码与旧包内图片混用。CLI 保持工程编排职责，不维护额外资源图。

具体工程、命令、路径和签名契约以 [CLI 与工程模式](../arch/31-ArrangeCLI与工程模式.md) 为准；CONFIG/SETUP 模型以[托管与同步母文档](../arch/32-ArrangeCLI托管与同步模型.md)为准。本文记录选择与原因，不另定义接口。

## 实施与验收影响

create/adopt、SETUP、dev/build/package 以统一状态、真实工具结果和明确失败出口实现。保留 CONFIG 的精确写入与事务保护，不通过工程创建或环境准备绕过它。

自动化测试应验证范围与路径保护、真实进程生命周期、CMake 模型身份、完整 bundle、构建记录失配和提交故障恢复。Mac 临时真实工程及 GUI/宿主结果单独记录；Windows 的模拟布局与环境测试不能替代 Windows 开发机的工具链、构建和运行验收。

当前实施状态由 [M2.2 第三期工作区](../proj/m2/2/第三期M2.2的工作.md) 维护；本轮 Mac 结果、最终测试数量、实际执行范围与证据位置见[本轮验收](../proj/m2/2/本轮验收.md)。Windows 真实机器验收和 Demo 迁移仍按后续安排处理。此前 ADR 保持历史原文；本篇补充 ADR 013/014 的 CLI 运行与交付边界。
