# ADR 006：第二期正规化统一输入、状态与帧计划

日期：2026-05-11

## 背景

M1 第一期正规化已经把 Arrange 从“事件、mutation、layout、paint 顺手推进”的状态收敛为 Compose-like 的 composition phase 与 render phase。

第二期开始前仍存在更深层问题：

- 输入来源没有完全统一。声明式状态变化、pointer / key / IME、resize、reload / HMR、resource ready 与 diagnostics event 仍可能从不同 controller 进入不同处理路径。
- 输出阶段没有完全统一。部分路径仍能直接请求 render、full repaint、局部 mutation 或 repaint，而不是由统一阶段计划决定。
- dirty 分类与归因不够严格，无法稳定解释哪个输入、哪个状态、哪个节点、哪个阶段为什么失效。
- Bridge、Modifier 与 diagnostics 仍有过渡实现：JS object ops、debug JSON、展开字段、旁路 overlay 绘制不能继续作为生产语义。
- 命名与职责边界需要更接近 Compose-like 思想，但不能机械拆碎既有聚合对象。

## 决策

### 1. 生产输入统一为 InputIntent

所有生产输入必须先进入统一 intent 模型：

```txt
InputIntent
  JsCommit
  AnimationFrame
  Pointer / Wheel
  Key / TextInput / ImeComposition
  Resize
  PackageLoad / Reload / HmrReload
  ResourceReady
  DiagnosticsEvent
```

宿主 adapter、package binder、diagnostics 入口、输入控制器不得直接决定 measure、layout、DrawOps build、repaint 或 dirty 清理。

### 2. 状态变化统一进入 RuntimeStore 或 MutationTransaction

JS / Vue composition 产生的 tree mutation 进入 `MutationTransaction`。

native-first 状态允许存在，例如 scroll、focus、pressed、hover、text editing、diagnostics state，但必须作为 typed runtime state 存在，并产出 typed invalidation。

生产链路固定为：

```txt
Input
-> InputIntent
-> RuntimeStore / MutationTransaction
-> InvalidationGraph
-> FramePlan
-> SceneFramePipeline
-> PublishedFrame
-> PassivePaint
```

### 3. FramePlan 是唯一输出阶段计划

`FramePlanner` 负责根据 pending intent、transaction、runtime state 与 dirty 归因生成 `FramePlan`。

三件套及相关输出阶段只能由 `FramePlan` 驱动：

```txt
drainComposition
applyMutations
measure
layout / place
buildPaint
buildHitTest
buildDiagnostics
publishFrame
passivePaint
```

阶段执行、跳过与 full fallback 都必须有可追踪原因。

### 4. SceneFramePipeline 是显式阶段执行器

`SceneFramePipeline` / `FramePipeline` 可以是聚合对象，不要求机械拆成一堆小类。

但它不得继续是黑盒 `run(...)`。阶段输入、阶段输出、dirty 消费、阶段跳过原因、fallback reason 与 PublishedFrame 产出都必须显式可查。

### 5. paint 只消费 PublishedFrame

JUCE `paint()` 只能：

```txt
read PublishedFrame
draw
```

禁止在 `paint()` 内执行 JS、apply mutation、measure、layout、build DrawOps、设置 diagnostics error、切换 loaded 状态、request repaint 或清 dirty。

### 6. Bridge 与 Modifier 生产语义必须 typed 化

Bridge 生产路径统一为：

```txt
Vue renderer
-> BridgeWriter
-> typed Bridge payload
-> native.commit(...)
-> MutationTransaction queue
```

JS object ops、JSON trace 与 debug mirror 只允许作为开发期诊断或测试辅助，不能成为生产事实源。

Modifier 生产路径统一为：

```txt
JS ModifierDescriptor[]
-> Bridge typed modifier payload
-> C++ ModifierChain / ModifierNode
-> Layout / Paint / HitTest / Input
```

`modifierDebugJson` 与展开字段不得参与生产语义。

### 7. DiagnosticsScene 是独立真视图

诊断界面不进入用户 App tree，不参与用户 layout / zIndex / focus / accessibility，也不共享用户 Vue reactive state。

但错误屏、badge、toast 与 diagnostics state 必须由独立 `DiagnosticsScene` 复用 core layout / paint / DrawOps pipeline 产出，而不是通过旁路 overlay 绘制。

### 8. 命名与职责向 Compose-like 思想对齐

第二期允许保留必要聚合对象，但必须重命名或重约束其职责。

要求：

- host、runtime、composition、frame planner、frame pipeline、scene state、layout tree、layout node、input adapter、input processor、diagnostics scene 的层级要能从命名看出。
- 不为对齐名词而拆碎对象。
- 不把 QuickJS、Vue composition、JUCE host、C++/JS 双世界这些客观差异伪装成 Compose 原生结构。
- 旧 `Surface` / `Render` / `Controller` 泛名不得继续掩盖生产职责。

## 影响

- `docs/arch/` 中的调度、Bridge、Modifier、输入、诊断与测试文档必须按本 ADR 收敛为唯一输入 / 状态 / 失效 / FramePlan / PublishedFrame 模型。
- 旧 ADR 005 仍记录第一期正规化历史；第二期后以本 ADR 与当前 `arch/` 母文档为准。
- 后续代码整改必须先保证主链路可解释，再做局部性能优化。
- deterministic / headless / test clock 测试必须覆盖 intent、dirty、FramePlan、pipeline 与 diagnostics scene；自动化屏幕点击不作为常规正确性证据。

## 不做

- 不机械复刻 Compose Desktop 的 Kotlin、Snapshot、Skia 具体实现。
- 不把合理聚合对象拆成维护地狱式小类。
- 不用 debug JSON、JS object 临时读取、旁路 overlay 绘制或 `paint()` 决策作为生产捷径。
