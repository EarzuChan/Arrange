# 内部包构建与分发契约

本文定义 Arrange 内部包族的构建边界、导出边界与消费边界。它约束 `@arrange/runtime`、`@arrange/vite-plugin`、`@arrange/vue-*` 以及后续其余 Arrange 内部包。

# 目标

Arrange 的内部包必须像正规包一样被构建、导出和消费，而不是靠源码直连、demo 特供配置或隐式魔法维持可运行：意思是，用户要像用正规的包一样用我们的包，而不是还需要引入很多黑魔法，且我们自己的demo，也必须正规化地使用我们的包。

```txt
source tree
-> package build
-> dist / exports
-> user consumption
```

# 包边界

## 源码树

`src/` 是包的实现源码，只属于仓库内部开发与构建流程，不是用户消费边界。

## 发布/消费树

`dist/` 与 `package.json exports` 才是正规消费边界。用户、demo、宿主和插件系统都必须按包名与 exports 解析，不得把源码路径当长期公开 API。

## 包族职责

- `@arrange/vue-*`：Arrange 专用 Vue fork / specialization。
- `@arrange/runtime`：用户 authoring 主入口与运行时主包。
- `@arrange/vite-plugin`：开发与构建工具包，负责构建与开发期接入，不负责替用户制造长期魔法依赖。

# 构建契约

1. 每个内部包都必须有明确的构建输出。
2. 构建产物必须是最终可消费形态，不能要求用户再去理解源码目录结构。
3. 编译期宏、分支宏、构建期特性开关必须在包构建阶段收束，最终产物不应保留未解析宏。
4. 包的公开入口只允许通过 `exports` 进入；额外路径若存在，也只能作为包内部实现细节或过渡期构建产物，不得成为长期消费模型。

对 Arrange Vue 来说，`__DEV__`、`__BROWSER__`、`__COMPAT__`、`__ESM_BUNDLER__`、`__FEATURE_*` 一类宏属于构建契约的一部分，不能交给用户在项目里临时补丁式处理。

# 消费契约

Arrange 的用户项目应像正常使用包一样使用 Arrange：

- `import { createApp } from "@arrange/runtime"`
- `import vue / compiler` 只走 Arrange 约定入口
- `ui-src/` 只作为用户源码项目
- `ui/` 只作为产物包目录

不允许再有以下做法：

- 直接 alias 到内部源码树。
- 在 demo 配置里堆积构建魔法。
- 把 package source 当公开 API。
- 让用户项目依赖仓库内部路径或临时开发开关。

# 验证要求

内部包的正规化必须能通过以下闸门：

- package build 能生成可消费产物。
- bundle 内不残留未解析的内部宏。
- 用户侧只依赖 package exports 即可运行。
- demo 的使用方式与真实用户项目一致。
