# 内部包构建与分发契约

本文定义 Arrange TS 包的构建边界、导出边界与消费边界。它约束外部发布包 `@arrange/framework`，也约束内部实现包 `@arrange/runtime`、`@arrange/vite-plugin`、`@arrange/vue-*` 以及后续其余 Arrange 内部包。

# 目标

Arrange TS 包必须像正规包一样被构建、导出和消费，而不是靠源码直连、demo 特供配置或隐式魔法维持可运行。用户和 demo 都只通过公开包名与 exports 使用 Arrange。

```txt
source TS
-> package exports
-> Arrange toolchain
-> app bundle / host runtime
```

Arrange TS 包不面向纯 JS、CJS、Web bundler 通用生态或无 TypeScript 工具链用户。TS-first 是包发行边界，不是开发阶段权宜之计。

对外发布的 TS 包以源码 TS 为唯一发行物：不提供 `dist`、`.d.ts` 和 CJS 发行物。

# 包边界

Arrange TS 包采用 TS-first 发行。公开入口必须是 `package.json exports` 暴露的 `.ts` 入口。

不得把未导出的仓库路径、包内私有文件或源码目录结构当成公开 API。

`package.json exports` 是唯一正规消费边界。用户、demo、宿主和插件系统都必须按包名与 exports 解析。

不提供 `.d.ts`、`dist/*.js`；类型源就是 exports 暴露的 `.ts` 入口。

# npm 发布边界

Arrange 的 JS 包发布到官方 npm 仓库，发布形态秉持 TS-first：

- 包必须可被 `npm pack` 直接打包与校验。
- 包必须声明明确版本号与公开发布意图。
- 发布文件必须受 `files` / exports 边界控制。
- 发布内容不得绕过 exports 暴露内部源码路径。
- 版本号必须与 native 协议 / 运行时握手规则保持一致或可判定兼容。
- `@arrange/framework` 是唯一外部 npm 包。
- `@arrange/runtime`、`@arrange/vite-plugin` 与 `@arrange/vue-*` 是内部实现包，不作为用户安装入口。

# 包族职责

- `@arrange/framework`：用户 authoring、开发、构建与 CLI 主包。
- `@arrange/runtime`：内部运行时与 authoring API 实现包。
- `@arrange/vite-plugin`：内部开发与构建工具包。
- `@arrange/vue-*`：内部 Arrange Vue compiler / runtime / reactivity 包族。

# 构建契约

1. 每个包都必须有明确的 exports。
2. exports 必须指向 TS-first 入口，不能指向 JS-first 或 d.ts-first 入口。
3. 编译期宏、分支宏、构建期特性开关必须由内部包或 Arrange toolchain 收束，不能交给用户项目临时处理。
4. 包的公开入口只允许通过 `exports` 进入；额外路径若存在，也只能作为包内部实现细节，不得成为消费模型。
5. 内部包构建不负责生产给用户消费的 JS 包；最终 JS 只来自 Arrange toolchain 生成的 app bundle 或宿主运行产物。

对 Arrange Vue 来说，`__DEV__`、`__BROWSER__`、`__COMPAT__`、`__ESM_BUNDLER__`、`__FEATURE_*` 一类宏属于构建契约的一部分，不能交给用户在项目里临时补丁式处理。

# 消费契约

Arrange 的用户项目应像正常使用包一样使用 Arrange：

- `import { createApp } from "@arrange/framework"`
- `arrange dev`
- `arrange build`
- `import vue / compiler` 只走 Arrange 约定入口。
- `ui-src/` 只作为用户源码项目。
- `ui/` 只作为产物包目录。

用户项目必须处在 Arrange TS-first 工具链内；Arrange 不承诺纯 JS、CJS、无 TS 编译能力或任意 Web bundler 的消费体验。

不允许再有以下做法：

- 直接 alias 到内部源码树。
- 在 demo 配置里堆积构建魔法。
- 绕过 exports 把 package source 当公开 API。
- 把内部包 `dist` 当用户消费入口。
- 声明或依赖不存在的 `.d.ts` 来伪装正规发行。
- 让用户项目依赖仓库内部路径或临时开发开关。

# 验证要求

包正规化必须能通过以下闸门：

- exports 指向的 TS-first 入口能被 Arrange toolchain 消费。
- app bundle 或宿主运行产物内不残留未解析的内部宏。
- 用户侧只依赖 package exports 即可运行。
- demo 的使用方式与真实用户项目一致。
- npm pack / install fixture 可以验证 `@arrange/framework` 发布包边界。
