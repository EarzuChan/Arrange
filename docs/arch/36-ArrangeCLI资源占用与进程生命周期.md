# Arrange CLI 资源占用与进程生命周期

本文是 CLI 多进程操作、资源隔离与外部工具生命周期的事实源。目录归属见 [用户目录与源码缓存](35-Arrange用户目录与源码缓存.md)，命令与工程模式见 [CLI 与工程模式](31-ArrangeCLI与工程模式.md)。

## 资源与冲突

所有正式命令经 `ApplicationOperations` 声明资源集合，由 `ProjectOperations` 根据配置推导实际路径，`Operations` 管理占用上下文。读取可以共享，写入与任何同资源读取或写入冲突；等待者不持有部分资源。路径按现有祖先的真实目录解析，Windows 忽略大小写，目录父子范围重叠也视为冲突。

| 资源 | 当前粒度 |
| --- | --- |
| 初始化目标 | 工程根以及计划涉及的复制来源、写入目录，目标独占 |
| 工程配置 | 工程根的配置身份，sync 写，其余命令读 |
| UI 工作区 | 实际 UI 目录，安装、build 和 dev 独占，pack 读取 |
| native 源码 | CONFIG 写、configure/build/pack/dev 读 |
| native 构建树 | 每个平台、架构、flavor 独占；SETUP 占项目构建根，覆盖工具确认后的架构 |
| 交付物 | artifacts 根，打包与运行交付二进制时独占 |
| Live 服务地址 | 约定开发地址，启动 UI dev server 的会话独占 |
| 共享源码 | 请求与内容发布身份分别独占，固定快照可并发读取 |

初始化目标的占用与其它类型的同路径操作冲突。工程配置、源码请求等不同类型不会因路径相似而自动产生无关冲突。用户显式让两个工程引用同一 UI 或交付目录时，实际路径使它们使用同一资源。

当前 sync 持有工程配置写占用覆盖整个命令及交互过程，采用保守粒度，不承诺同一工程的 UI/native sync 并行。build/pack/dev 持有配置读占用，native debug/release 可并行，UI build 使用同一个工作区时串行。独立工程继续并行，固定 Live 地址仍只允许一个 UI dev server。

## 授予与重新规划

工作进程在短暂协调锁内注册整组请求，全部无冲突才授予。冲突时显示持有者命令、客户端 PID 和资源路径，等待可取消，超过十分钟明确失败。较早的冲突写请求会阻止后续读请求插队，避免写者饥饿。外部工具、下载和用户交互不占协调锁。

取得资源后重读配置并检查规划时的快照；变化时释放整组并重新规划。SETUP 在应用动作前验证实际 UI、native 源码和构建根仍属于当前上下文，工具确认修改 buildRoot 等位置时，释放并按新位置重新申请。领域服务不通过临时追加锁升级占用。源码请求只依赖工程占用，不反向申请工程资源，内容发布也不反向申请请求锁。

`sync --scan` 使用只读请求，发现冲突直接报告无法稳定观察，不等待修改者完成；不写工程配置或准备状态。用于稳定扫描的资源协调信息保存在用户级目录，可能按需创建。它不意味着整个文件系统在扫描期间静止，外部编辑仍可能发生。

## 命令生命周期

create/adopt 的纯询问与计划预览不持有资源；应用时整组申请，重新核验计划后写入。接着 sync 是一次新占用，不递归持有初始化锁。

build 的占用从重新检查状态一直覆盖 configure、compile/link、产物核验、receipt 和默认 pack，打包不会在输入保护中途接力失去占用。pack 同时读取 UI/native 构建输入并独占交付根，覆盖复制、暂存校验、提交和回退。

dev 在启动前构建或打包，继续持有 UI 工作区、native 构建树或交付目录的原占用，直至全部受管进程停止。Windows 运行中的 EXE 不会被另一个 CLI 尝试重新链接。端点占用配合实际就绪与端口绑定检查，不能替代 Vite strictPort 或系统 bind 的真实结果。

native receipt 文件名包含平台、架构与 flavor，成功/失败记录原子写入，独立构建树不会覆盖同一份状态。UI receipt 仍属于单一 UI 工作区。没有旧文件名回退。并发命令的任务日志目录身份独立，自动清理跳过仍存活 CLI 的目录。

## 内核锁与工具工作进程

每个命令按需创建一个本机工作进程，不建立后台常驻服务。它持有资源会话并执行该命令的全部外部工具；界面和领域流程留在客户端，输出通过 IPC 回到任务接口。入口在成功、失败及取消后关闭工作进程，工作进程先结束全部工具，再撤销占用。

Windows 使用不共享的文件句柄作为内核锁；macOS 使用 `flock`。绑定通过 Koffi 调用系统 API，没有按心跳过期夺锁。工作进程暂停时内核占用持续存在。锁文件保存在用户级 `operations`，不会随 native clean 或构建树重建被删除。

Windows 工作进程在启动工具前加入带 `KILL_ON_JOB_CLOSE` 的 Job Object，工具及后代自动继承；异常关闭 Job 时系统结束全部成员。工作进程忽略终端 Ctrl+C 广播，取消由客户端 IPC 传入，保证清理期间不提前退出。正常关闭前清理工具后解除 Job。

macOS 外部工具使用受管进程组，客户端 IPC 断开后工作进程停止进程组。两端均在主工具退出后继续清理后代，确认结束才撤销工具登记。启动前先登记尚未确认 PID 的过程，避免崩溃时误认没有遗留工具。

## 异常恢复边界

后续命令只有在工作进程内核锁已释放、客户端已结束、已登记工具 PID 或 macOS 进程组均不存在时才删除残留占用记录。工作进程死亡而客户端仍活着、工具仍存活或崩溃发生在无法确认 PID 的启动窗口时，保留占用并阻止接管；不根据时间或 PID 猜测主动杀死其它进程。未知启动窗口需要确认环境已清理后处理记录，当前没有自动强制解锁命令。

PID 重用会导致保守阻塞，不导致错误接管。不能对手工执行的 CMake、pnpm、编辑器或显式脱离受管进程组的外部程序提供强制隔离；原有文件快照、准备记录和提交核验继续有效。

源码获取锁已经纳入同一资源协议，构建目录 owner 的短暂写入使用同一内核锁原语。CLI 不再依赖 `proper-lockfile` 或心跳锁作为另一套操作路径。底层领域服务是显式程序化工具，直接调用时由调用方负责资源协议；正式命令与应用装配统一经过上述入口。

## 维护资源协议

共享源码使用增加保守的生命周期读占用；用户级源码维护持写占用，直到所有相关受管进程结束才能修改。工程清理、恢复与其实际目录写入冲突。预览不持有长期占用，确认后一次规划全部资源并重读核验；登记用短暂原子更新。维护不通过 force 绕过锁，不按 PID 或时间猜测清理。

首版共享源码生命周期占用整个用户 sources 目录：工程执行与原生验收为目录读请求，用户级维护为目录写请求。请求/发布细锁仍为 source 类型，不能与生命周期锁互相升级。maintenance 在执行前整组声明生命周期和所有目标；storage clean 对忙资源立即报告，不抢删。原生验收开始前声明全部构建树，configure 仅核验已持占用，不中途加锁；CMake/CTest 经同一工作进程执行并在信号后收尾。
