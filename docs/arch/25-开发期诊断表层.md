# 开发期诊断表层

开发期诊断表层是 Arrange 在正式 DevTools 之前提供的最小诊断能力。它帮助开发者看见加载状态、错误、reload、HMR 与必要运行事件，但不属于用户 App。

统一命名：

| 项 | 名称 |
| :--- | :--- |
| 概念名 | 开发期诊断表层 |
| 实现类 | `DiagnosticsScene` |
| 事件事实源 | `DiagnosticEvent` |
| 事件存储与分发 | `DiagnosticEventStore` / `DiagnosticLogger` |
| 状态模型 | `DiagnosticsState` |
| 短提示 | diagnostics toast |
| 强错误状态 | 错误屏 |

生产命名按职责分有：

- `DiagnosticEvent`：一条诊断事实。
- `DiagnosticEventStore`：recent event ring、过滤与 sink 分发。
- `DiagnosticLogger`：面向 native 与 TS 的日志 API 门面。
- `DiagnosticsState`：错误屏、badge、toast 等诊断视图状态快照。
- `DiagnosticsScene`：独立于用户 App tree，但复用 core layout / paint / DrawOps pipeline 的诊断场景。

`DiagnosticsScene` 只负责把诊断状态构造成 DrawOps；它不是日志存储，不是事件事实源，也不是第二套调度中心。

# 边界

诊断表层由 `arrange_juce` / scene host 托管。

它必须满足：

- 不进入用户 App tree。
- 不参与用户 layout。
- 不占用用户 zIndex。
- 不写入用户 Vue reactive state。
- 不污染用户 focus、hover、pointer capture 或 accessibility tree。
- 默认不拦截 badge / toast 区域的鼠标事件。
- 错误屏激活时可以接收 Retry、Copy diagnostics 等诊断输入。
- 复用 core layout / paint / DrawOps pipeline 产出诊断 DrawOps。
- 诊断状态变化必须进入 diagnostics intent / DiagnosticsState / invalidation / FramePlan。

诊断表层不是通用 UI 组件，也不是未来 DevTools 本身。未来 DevTools 可以复用诊断事件和状态，但不能依赖当前 diagnostics scene 的绘制坐标或文案。

# 数据流

所有诊断输出必须共用同一份结构化来源：

```txt
AppResolver / DevServerClient / ScriptHost / NativeTransaction / Input / Scroll / Resource
-> DiagnosticEvent
-> DiagnosticEventStore / DiagnosticLogger
-> DiagnosticsState
-> DiagnosticsScene
-> FramePlan
-> badge / error screen / diagnostics toast / log sink / future DevTools
```

要求：

- 事件来源只描述事实，不直接决定视觉样式。
- `DiagnosticsState` 是诊断表层唯一状态快照。
- paint 只能读取 PublishedFrame，不能在绘制中探测 dev server、文件系统或脚本 runtime。
- `activeSource` 只能由实际加载成功结果更新：live 成功才是 `Live`，dist 成功才是 `Dist`。
- 错误屏、badge、toast、日志可以有不同详略，但事件 id、source、URL/path、errorCode 必须同源。

事件模型：

```cpp
enum class DiagnosticLevel {
    Trace,
    Debug,
    Info,
    Warn,
    Error,
};

enum class DiagnosticCategory {
    App,
    HostLive,
    HostDist,
    HostHmr,
    RuntimeScript,
    RuntimeTransaction,
    PipelineFrame,
    PipelineLayout,
    PipelinePaint,
    InputPointer,
    InputKey,
    InputIme,
    InputScroll,
    ResourcePackage,
    ResourceImage,
    ResourceIcon,
    Diagnostics,
};

struct DiagnosticEvent {
    std::uint64_t id;
    double timestampMs;
    DiagnosticLevel level;
    DiagnosticCategory category;
    std::string code;
    std::string message;
    std::string detail;
    std::string source;
    std::string pathOrUrl;
    bool requestToast = false;
};
```

分类采用从高到低的层级命名；native 可用 enum 表示，TS 暴露稳定字符串：

```txt
app
host.live / host.dist / host.hmr
runtime.script / runtime.transaction
pipeline.frame / pipeline.layout / pipeline.paint
input.pointer / input.key / input.ime / input.scroll
resource.package / resource.image / resource.icon
diagnostics
```

状态模型：

```cpp
struct DiagnosticsState {
    BuildMode buildMode;          // Debug / Release
    AppSource activeSource;       // Live / Dist / None
    bool liveEnabled;
    bool distEnabled;
    std::string liveUrl;
    std::filesystem::path distPath;
    std::optional<DiagnosticError> error;
    std::vector<DiagnosticToast> toasts;
    std::uint64_t lastEventId = 0;
};
```

`DiagnosticsState` 更新属于 runtime state reduction。它不得在 JUCE `paint()` 内发生。

# 事件

基础事件包括：

```txt
AppLoadStarted
AppLoadSucceeded
AppLoadFailed
LiveUnavailable
FallbackToDist
ReloadRequested
ManualReloadRequested
LiveToggled
HmrConnected
HmrDisconnected
HmrReloadReceived
ResourceMissing
ProtocolMismatch
ScriptException
LogSinkFailed
```

事件最少携带：

```txt
event id
level
category
timestamp
build mode
active source
configured live/dist
url/path
short message
detail message
error code
```

事件进入哪些输出渠道由诊断层决定。例如 reload 可以进入 toast 与日志；脚本异常必须进入错误屏与日志。

`DiagnosticEvent` 是唯一事实源：同一个事件可以派生日志行、toast 文案、错误屏摘要、Copy diagnostics 内容和未来 DevTools 行，但不能由这些输出渠道各自维护独立事实。

# 生命周期

加载、reload、错误恢复与 HMR 按事件驱动更新诊断状态：

```txt
load / reload requested
-> emit AppLoadStarted
-> try live / dist
-> emit AppLoadSucceeded | LiveUnavailable | FallbackToDist | AppLoadFailed
-> reduce DiagnosticsState
-> diagnostics invalidation
-> FramePlan
-> build DiagnosticsScene DrawOps
-> publish frame
-> write log sink
```

要求：

- `DiagnosticsState` 更新必须早于 UI 输出。
- badge、错误屏、toast 不能各自维护互相矛盾的状态。
- 进入或退出错误屏、source 切换、root rebuild 后必须由 FramePlan 选择 full repaint。
- 若局部 repaint 边界证据不足，FramePlan 必须选择显式 full repaint 并记录原因。
- 日志写入不能阻塞音频线程，也不能在 paint 内做文件 I/O。

# Editor badge

Editor 内状态 badge 用来显示实际运行来源。

默认文案：

- `Debug live`
- `Debug dist`
- `Release dist`
- `Debug live failed -> dist`
- `Debug no app`

默认行为：

- Debug 默认显示。
- Release 默认隐藏；用户显式开启诊断时可显示。
- badge 不参与用户 layout。
- badge 默认不拦截鼠标事件。
- badge 反映实际 `activeSource`，不是配置意图。

默认位置和样式：

```txt
position: top-right
margin: 8dp
height: 20dp
cornerRadius: 6dp
fontSize: 11sp
padding horizontal: 8dp
background: 0xCC111827
border: 0x664B5563 1dp
text: 0xFFE8EAED
```

状态色：

- live：`0xFF22C55E`。
- dist：`0xFF3B82F6`。
- fallback：`0xFFF59E0B`。
- error / no app：`0xFFEF4444`。

# Standalone 标题栏

Standalone 可同步粗粒度状态：

```txt
Arrange Demo [live]
Arrange Demo [dist]
Arrange Demo [error]
Arrange Demo [no app]
```

插件宿主窗口标题栏不可靠，VST3 / AU / AAX 中仍以 Editor badge、错误屏和日志为准。

标题栏只表达粗粒度 source state，不承载详细错误。

# 错误屏

错误屏是诊断表层的强状态。当用户 App 无法显示时，错误屏替代用户 UI。

内容：

- 标题。
- 错误来源。
- 简短说明。
- 路径或 URL。
- stack / diagnostic summary。
- 当前 source 配置。
- Retry。
- Copy diagnostics。

行为：

- 进入和退出错误屏必须 full repaint。
- Retry 走 [错误屏与重试](07-错误屏与重试.md) 定义的统一加载链路。
- 错误屏输入不得透传给用户 App。
- Debug 展示详细诊断。
- Release 展示克制诊断，但保留复制完整诊断的能力。
- Copy diagnostics 至少包含 build mode、active source、configured source、URL/path、错误摘要、stack 和最近诊断事件。

默认样式：

```txt
background: 0xFF2A1014
title: 18sp bold 0xFFFF6B6B
body: 13sp 0xE6FFFFFF
code/path: 12sp monospace-like 0xFFE5E7EB
button: rounded 6dp, background 0xFF374151
```

# Diagnostics toast

diagnostics toast 用于短暂提示低风险事件，不替代错误屏。

适用事件：

- `Reloaded from live`
- `Live unavailable, loaded dist`
- `Live enabled`
- `Live disabled`
- `HMR connected`
- `HMR disconnected`
- `Copied diagnostics`

不适用事件：

- 无法显示用户 UI 的致命错误。
- 需要用户阅读 stack 的错误。
- 高频事件，例如每帧 repaint、pointer move。

默认行为：

- bottom-right，margin 12dp，maxWidth 360dp。
- 显示 2.5 秒。
- 同类 toast 合并。
- 最多同时显示 3 条。
- 不参与用户 layout。
- 默认不拦截鼠标事件。
- Release 默认隐藏，除非用户显式开启诊断。

# 日志

日志必须由 `DiagnosticEvent` 生成，不允许各模块长期直接散落 `printf`、`std::cout` 或临时文件写入。日志、toast、错误屏和未来 DevTools 必须共用同一份诊断事件事实源。

日志事件至少包含：

```txt
time
level
category
event
message
source
path/url
errorCode
detail
```

级别：

```txt
trace / debug / info / warn / error
```

类别：

```txt
app
host.live / host.dist / host.hmr
runtime.script / runtime.transaction
pipeline.frame / pipeline.layout / pipeline.paint
input.pointer / input.key / input.ime / input.scroll
resource.package / resource.image / resource.icon
diagnostics
```

日志输出渠道：

- debugger log：开发期默认渠道。
- recent event ring：内存环形缓冲，供 Copy diagnostics、错误屏摘要和未来 DevTools 使用。
- file sink：用户显式开启时写入文件。
- console adapter：QuickJS `console.log/warn/error` 应转为 `script` 类别的日志事件。

Debug 默认输出到 debugger log，并记录 `info` 及以上级别到 recent event ring。Release 默认只输出 `warn` / `error`，并避免泄露不必要的敏感路径。文件日志必须在 message/background safe 的位置写入，失败时降级到 debugger log 并产生 `LogSinkFailed`。

file sink 只允许在安全线程、安全频率下使用。开发组和 Arrange App 开发者都不得在 audio thread、paint、pointer move、每帧 layout/paint 等高频关键路径中依赖同步文件 I/O。高频诊断必须进入异步队列或后台写入。

过滤规则：

```txt
level >= configured logLevel
category in configured categories if categories is not empty
```

模块可以记录 `trace` / `debug` 级别的细节事件，例如 transaction batch、FramePlan、layout、paint、input、resource resolve；但用户默认视图应以 `info` / `warn` / `error` 为主，避免把内部过程噪声暴露给普通 Arrange App 开发者。

# Native 与 TS 诊断 API

诊断能力分为 native-only 和 native + TS 双 API。能影响宿主安全、路径、文件、Release 暴露程度的底层开关只留 native；面向开发者操作与可诊断性的能力应同时提供 native 与 TS API。

native + TS 双 API：

```ts
logger.trace(category, message, detail?)
logger.debug(category, message, detail?)
logger.info(category, message, detail?)
logger.warn(category, message, detail?)
logger.error(category, message, detail?)

diagnostics.toast(message, options?)
diagnostics.requestReload(options?)
diagnostics.triggerFakeError(options?)
diagnostics.copyDiagnostics()
diagnostics.copyRecentEvents()
diagnostics.setLogLevel(level)
diagnostics.setCategoryEnabled(category, enabled)
diagnostics.setToastsEnabled(enabled)
```

要求：

- TS `logger.*` 必须进入 native `DiagnosticEvent`，不能只打印到 JS console。
- QuickJS `console.log/warn/error` 应转为 `runtime.script` category。
- `diagnostics.toast(...)` 必须产生 `DiagnosticEvent` 与日志；toast 显示可关闭，但事件与日志不可丢。
- `diagnostics.requestReload(...)` 走现有 reload / package load 统一链路。
- `diagnostics.triggerFakeError(...)` 只能用于诊断目的，走真实错误屏与 FramePlan 链路，不得在 paint 中临时画假错误。
- TS 调试控制 API 是否在 Release 中生效由 native config 决定；Release 默认克制。

native-only 配置：

- app source：live / dist / dev server URL。
- file sink 路径与是否启用。
- recent event ring size。
- Copy diagnostics 在 Release 中是否包含完整路径/stack。
- 环境变量覆盖。
- 诊断快捷键绑定。
- 是否允许 TS 调试控制 API 在当前 build mode 下生效。

可 toggle 功能必须在文档和 API 中明确：

| 功能 | native | TS | 说明 |
| :--- | :--- | :--- | :--- |
| badge 显示 | 是 | 可选 | 默认 DebugOnly |
| diagnostics toast 显示 | 是 | 是 | 只影响显示，不影响事件与日志 |
| log level | 是 | 是 | 过滤 sink 输出，不删除事件事实 |
| log category | 是 | 是 | 过滤 sink 输出，不删除必要错误事件 |
| file sink | 是 | 否 | 路径与文件 I/O 只由 native 控制 |
| request reload | 是 | 是 | 必须走统一 reload 链路 |
| fake diagnostic error | 是 | 是 | 诊断专用，Release 默认可禁用 |
| copy diagnostics | 是 | 是 | Release 详细程度由 native 控制 |
| error screen | 是 | 否 | 致命错误不能被 TS 关闭，只能控制详细程度 |

# Toast 与日志的关系

diagnostics toast 是部分 `DiagnosticEvent` 的短暂可视化输出，不是第二套诊断事实源。

要求：

- toast 只能由诊断事件派生，不能由某个模块绕过 `DiagnosticEvent` 直接绘制。
- 调用 diagnostics toast 同时必产生对应日志事件。toast 显示可以被配置关闭，但调用 toast api 对应产生的日志事件仍将打印，我们也不提供关闭这条日志生成的开关。
- toast 适合低风险、短生命周期事件，例如 reload、fallback、copy diagnostics、HMR connected / disconnected。
- 致命错误必须进入错误屏与日志，不能只发 toast。
- 高频事件，例如 pointer move、每帧 repaint、每次 layout pass，不得默认产生 toast。
- toast 是否显示由 `config.diagnostics.toasts`、环境变量和 build mode 决定；不影响日志是否记录。

diagnostics toast 建议仅用于开发期诊断。Release 中虽不限制你使用，但它仍属 Arrange 的诊断表层功能，不是面向最终插件用户的业务 toast。插件 UI 若需要展示保存成功、授权提示、业务警告等用户 toast，应由开发者在自己的 Arrange App 内实现。

# 用户控制

目标配置：

```cpp
config.diagnostics.badge = arrange::juce::DiagnosticVisibility::DebugOnly;
config.diagnostics.toasts = arrange::juce::DiagnosticVisibility::DebugOnly;
config.diagnostics.errorScreen = true;
config.diagnostics.logLevel = arrange::juce::LogLevel::Info;
config.diagnostics.logCategories = {};
config.diagnostics.logFile = {};
config.diagnostics.copyFullDiagnosticsInRelease = true;
```

可选可见性：

```txt
Hidden
DebugOnly
Always
```

环境变量可作为开发期覆盖：

```txt
ARRANGE_DIAGNOSTICS=0|1
ARRANGE_DIAGNOSTIC_BADGE=0|1
ARRANGE_DIAGNOSTIC_TOASTS=0|1
ARRANGE_LOG_LEVEL=trace|debug|info|warn|error
ARRANGE_LOG_CATEGORIES=app,live,hmr,script,resource
ARRANGE_LOG_FILE=path
```

优先级：

```txt
显式 EditorConfig
-> 环境变量
-> build mode 默认值
```

# 快捷键

默认诊断快捷键：

```txt
F5              手动 reload
Ctrl/Cmd+F5     切换 live enabled 后 reload
F6              Debug 下发送测试 toast
F7              Debug 下触发手动诊断错误页
```

这些快捷键属于 Editor 诊断交互，不进入用户 App key event。用户未来需要改写时，应通过 `EditorConfig.diagnostics.shortcuts` 显式配置。

# 默认策略

Debug：

- badge 显示。
- toast 显示。
- 错误屏显示详细诊断。
- log level 为 `info`。

Release：

- badge 隐藏。
- toast 隐藏。
- 错误屏显示克制诊断。
- Copy diagnostics 可提供完整信息。
- log level 为 `warn`。

测试模式：

- 可强制显示 badge / toast。
- 可导出所有诊断事件 snapshot。
- 截图 smoke 可断言 badge、toast、错误屏存在与文案。

# 长期约束

`DiagnosticsScene` 承接事件记录、日志、badge、toast 与错误屏视图构建。`ArrangeEditor` 只提供宿主入口、平台 action 与 passive paint，不直接维护诊断视觉状态。

诊断表层必须接入统一 invalidation / FramePlan / SceneFramePipeline，同时保持它和用户 App tree 的边界。

# 不做

- 不把 toast 当通用用户 UI 组件。
- 不把诊断状态塞入用户 Vue App。
- 不让 diagnostics scene 影响用户 layout 或 hit-test 语义。
- diagnostics overlay 不反向依赖 DevTools。
- 不在 `paint()` 内生成 diagnostics error、切换 loaded 状态或临时绘制错误屏。
