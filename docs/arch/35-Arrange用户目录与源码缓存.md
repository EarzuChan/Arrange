# Arrange 用户目录与依赖源码缓存

本文定义 Arrange 在设备、用户层面的目录和共享依赖源码生命周期，CLI 与未来框架运行时遵守同一边界。工程配置、命令与构建职责见 [CLI 与工程模式](31-ArrangeCLI与工程模式.md)，原生包消费见 [Native 包消费契约](30-Native包消费与FetchContent契约.md)。

## 两个作用域

Windows 与 macOS 均以当前用户主目录下的 `~/.arrange` 为默认用户级根。用户可用绝对路径环境变量 `ARRANGE_HOME` 显式覆盖；相对路径拒绝使用，不自动回退到其它目录。路径解析与只读检查不创建目录，实际写入时才创建。

用户级目录属于 Arrange 在这台设备、这个用户下的工作空间，不属于某个工程，不应整体视为可删除缓存。工程内 `<project>/.arrange` 保留工程日志、构建凭据等本机工作状态；`arrange.local.yaml` 表达该工程的本机工具与路径选择。工程清理不能顺带删除用户级内容。

```text
~/.arrange/
  builds/                  各工程独立的 native 构建树，CLI 管理
  deps-src/                 共享固定版本源码，CLI 管理
    requests/              来源与 ref 到确切 commit 的本机索引
    entries/               发布完成的源码与身份记录
    locks/                 请求与发布资源的身份路径
    tmp/                   尚未发布的获取内容
  tmp/                     用户级其它临时工作目录，按需使用
  runtime/                 框架运行时用户数据的目录边界，当前未启用写入
  operations/              CLI 资源占用记录和内核锁文件
  projects/                已操作工程的路径登记与资源发现线索
  transactions/            用户级清理和修复的持久记录
```

CLI 不清理框架运行时持久数据，运行时不修改 CLI 发布的源码快照。当前不引入用户配置文件、后台缓存服务或自动空间回收。

## 构建目录

默认 native 构建树位于 `builds/<工程根路径 SHA-256 前 8 位>/<平台架构配置>`。Windows 的工程路径身份忽略大小写，配置目录为 `xd/xr/ad/ar`；macOS 保留路径大小写，配置目录为 `mac-xd/mac-xr/mac-ad/mac-ar`。其中 `x/a` 表示 x64/arm64，`d/r` 表示 debug/release。

同一工程的所有权记录 `owner.json` 保存项目根路径；写入经锁保护并原子发布，身份不匹配或记录损坏时明确拒绝。不同工程、架构、配置与平台不共用生成文件和编译结果。`native.buildRoot` 可覆盖构建根，相对值相对于工程根解析。

CLI 只解析当前用户级目录契约，不探测其它默认目录，不提供旧布局迁移或回退。工程移动到新位置后按新根重新配置。

Windows 长路径限制与 configure 预检见 [CLI 工具链](31-ArrangeCLI与工程模式.md#版本与工具链)。主目录过长时用户明确设置更短的 `ARRANGE_HOME` 或 `native.buildRoot`；两端不采用需要额外权限的目录别名或符号链接缩短路径。

## 共享依赖源码

缓存源码包含 Arrange、JUCE 和 QuickJS-NG；平台、编译器、架构与 debug/release 不进入源码身份。所有编译结果仍在独立构建树中。CLI 准备源码后传入 CMake 标准 `FETCHCONTENT_SOURCE_DIR_ARRANGE/JUCE/QUICKJS_NG`，不将自动生成的缓存路径写进工程 YAML，不改变 CMake 的公开 target 或消费方式。

来源与 ref、可选固定 commit 构成请求身份。下载完成后，以原始仓库来源和实际 commit 的哈希标识内容，同一来源、同一 commit 可由不同 ref 共用。目录采用短哈希，记录保留完整内容身份以检查碰撞。索引不保存仓库凭据，Git 输出在进入任务日志前抹去 URL 用户信息。

默认依赖版本由每个 Arrange 版本的 `cmake/NativeDependencies.json` 声明，CLI 不维护另一份版本表。获取时校验 tag 对应 commit。依赖清单必须存在且包含固定 commit；缺失或无效时明确失败，不解析 CMake 声明作为替代来源。用户显式覆盖仓库或版本时按覆盖值获取，不套用默认 commit。

同一请求首次解析成功后记录实际 commit，日常命中使用这个快照，不联网追踪 tag 移动。已经知道固定 commit 时直接查内容缓存，不因 ref 变化重复下载。缓存命中检查发布记录、源码入口和 detached HEAD，准备时另以本地 Git diff 检查 tracked 源码是否被改动；不会静默覆盖受损缓存。开发源码修改应使用显式本地目录覆盖。

CLI 仅缓存可确认来源的工程：Arrange 仓库与版本均由 CLI 托管时获取 Arrange；已显式提供本地 Arrange 时从该目录读取依赖清单。自定义未托管 CMake 的来源不由 CLI 猜测。`JUCE_DIR`、`ARRANGE_QUICKJS_NG_SOURCE_DIR`、各 `FETCHCONTENT_SOURCE_DIR_*` 显式覆盖优先，不接管、移动或删除用户目录。

## 获取、并发与恢复

缓存命中不 fetch。缺失条目取得跨进程请求锁后再次检查，然后在同一缓存文件系统的临时目录内获取 Git commit 和递归子模块。验证入口与版本后，在内容锁保护下原子发布完整条目，再原子发布请求索引。发布后的快照不切换 commit；新版本建立新条目。

跨进程获取和发布使用 [CLI 资源占用协议](36-ArrangeCLI资源占用与进程生命周期.md)，源码条目锁与工程操作由同一工作进程管理。Git fetch 和递归子模块获取不设置 CLI 总时长上限，允许弱网下长时间下载或静默等待；用户可以取消，真实 Git 网络或版本错误仍明确失败。本地 Git 操作与校验保留执行期限。不同工程或 debug/release 争用同一请求时只由一个持有者获取。进程取消不发布半成品；异常退出后确认进程已结束才恢复占用，持有请求占用后清理该请求遗留的临时目录。

完整缓存存在时源码预检不要求远端可达；需要新源码时仍报告真实网络、版本或 Git 错误。此能力不等同于整个工程离线运行，npm 安装与 Framework 兼容性检查各自遵守既有契约。

当前不自动淘汰条目，也不复用旧工程 `_deps` 作为缓存来源。已有 CMake 构建树可能引用发布条目的路径，用户手动删除缓存后应重新运行 native SETUP。缓存目录下的符号链接或越界路径在检查、写入与递归清理前拒绝，不允许清理逃逸至其它目录。

## 工程登记与维护

`projects/<路径身份>.json` 保存工程规范化绝对路径、首次与最近操作时间及构建根、验收构建树发现线索；不复制 YAML、源码版本或准备状态。实际操作前登记已确认工程，失败仍保留；纯扫描、help 不登记。create/adopt 写入计划确认后登记，sync/build/pack/dev/clean 在取得资源并重读确认工程后登记。框架验收源码根使用 verification 登记类别，以依赖清单检查存在性，不要求 Arrange 工程 YAML。最近时间只用于展示与排序，不决定淘汰。移动产生新路径登记，不引入工程 UUID；不存在、不可访问、路径被占用分别报告。owner 与源码发布记录仍是归属事实源，登记不能单独授权删除。

清理以归属、引用和占用判断，不自动按时间淘汰。不可读或缺少引用记录时保守阻止源码清理；runtime、外部源码、未知目录不清理。configure 启动前持久保存可能引用，失败也保留。用户级 `transactions` 保存维护记录，实际移出前记录，实际删除后只能继续清理。修复使用记录中的确切 commit，在暂存目录校验后替换，影响的准备凭据失效。

构建树的 `source-references.json` 保存可能使用的绝对源码目录。configure 开始前原子保存新旧引用并集，完整验证后收缩；失败或取消不丢旧引用。默认构建根和登记发现的外部根均扫描；owner 哈希不符、记录损坏、系统目录不可达或引用缺失时保守阻止源码维护。无法跟踪手工 CMake 或未登记的外部消费者，其资源由用户负责。失联登记仅在所属受管构建资源处理完后移除。

源码缓存采用当前 schema 2，记录净化后的来源与确切 commit，URL 凭据不进入记录或身份。repair 不重新追踪 tag，先校验新快照再替换旧条目；已知引用构建的准备凭据在替换前失效。旧格式、损坏身份或缺少来源不能自动修复和猜测清理；CLI 不迁移旧数据。磁盘占用是文件逻辑字节合计，不冒充文件系统实际分配量；不可读时标为不完整。

登记同时保存所在文件系统的挂载根与设备身份，用于区分磁盘不可达与工程失联；同一挂载点被其它设备替换时标为无法检查。仅实际操作重新确认后更新该事实，不按路径缺失猜测卸载设备上的工程已删除。


## 存储检查事实与清理判定

`storage inspect` 分别展示记录、内容、归属、所属工程、准备状态与引用检查；具体原因和阻断路径随结果输出。状态是结构化事实，中文文案只负责显示，清理和修复不得反向解析文案。工程登记当前格式为 schema 2，依赖源码发布记录当前格式为 schema 2；读取先检查版本头，不支持其它版本，不读取旧业务字段、不迁移。工程 YAML 当前没有独立格式版本字段，产品版本不用于判断格式兼容；其语法与结构按当前工程定义校验。

| 检查结果 | 判定依据 |
|---|---|
| 正常 | 当前格式记录与对应身份或内容校验通过 |
| 丢失 | 设备可检查，已登记或被索引的目录、记录或必需内容不存在；明确丢失对象 |
| 身份失效 | 原工程路径存在，但不再是登记工程 |
| 损坏 | JSON/YAML 语法、当前结构、身份哈希或内容一致性校验失败 |
| 版本不兼容 | 显式格式版本不是当前唯一支持版本；不猜测旧结构 |
| 无法访问或验证 | 设备、权限、占用或工具错误阻止可靠检查，不能当作丢失或已损坏 |
| 无法确认 | 无可识别归属或事实不足，不能授权删除 |
| 未准备或已过期 | 构建配置、准备输入、模型与当前工程或本机选择不匹配 |
| 未完成 | 依赖获取暂存或验收准备尚未完成；有持久事务时提示恢复入口 |

构建归属与依赖引用分别判断。owner 有效且设备可检查、所属工程丢失或身份失效时，构建目录属于可清理孤儿；缺少引用记录不会撤销已证明的归属。归属未知、工程不可访问或归属版本不支持时拒绝自动清理。准备过期不自动授权用户级删除，仍使用工程 clean。

依赖源码只有发布身份和内容有效、全部登记与构建引用可检查且无引用时才可清理。记录缺失、版本不支持、内容损坏或引用不完整时说明阻断原因；当前有效记录能确定来源和 commit、引用完整时，允许 repair 修复已丢失或损坏的源码内容。请求索引能发现已丢失的条目，不能只遍历现有目录后宣称库存完整。

用户目录唯一依赖源码路径为 `deps-src`，条目 ID 为 `deps-src:<键>`；旧路径不探测、不迁移，旧 ID 不作别名。获取暂存内容在确认归属与占用后清理；有未完成用户事务时先恢复。runtime 与未受管外部内容不进入候选。

`storage clean --scan` 同时展示候选和排除原因。库存确实为空才报告“存储为空”；存在资源而无候选时报告“没有可安全清理的候选”，不能误称没有内容。磁盘统计不完整时继续标注“至少”，大小显示规则见 [CLI 输出](31-ArrangeCLI与工程模式.md#输出)。
