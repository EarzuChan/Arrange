看得气抖冷，车轱辘话一大堆。简要概述：目前有基础的诊断系统，包括错误屏、Toast、Badge、Debug标题栏；目前还没有并入“系统组件化链路”，而还是一个粗糙的内部并用硬渲，不够有约束和统一化，然后更后的真DevTools没搞呢还。

# 目标

Arrange 还没有正式 DevTools，但 M1 起必须有一组稳定、可约束的开发期诊断表层：

- Debug 状态指示器：Editor 内 badge、Standalone 标题栏。
- 错误屏幕。
- 日志输出。
- 必要的 overlay toast。

这些能力不是正式 DevTools，也不是用户 UI 组件。它们是 Arrange runtime / editor 的诊断层，为未来 Inspector / DevTools 打基础。

本文件约束四件事：

- 实现原理：诊断数据怎样从加载、脚本、Bridge、输入、滚动、资源等链路进入统一模型。
- 样式：badge、标题栏、错误屏、toast 的默认视觉。
- 行为：什么时候显示、隐藏、拦截输入、触发 repaint 或写日志。
- 用户控制：`EditorConfig.diagnostics`、环境变量、快捷键与默认值。

# 分层

```txt
用户 App tree
-> Arrange render tree
-> Arrange diagnostics overlay layer
-> JUCE Graphics / host window
```

诊断表层由 `ArrangeEditor` / `arrange_juce` 托管：

- 不进入用户 App tree。
- 不参与用户 layout。
- 不占用用户 zIndex。
- 不触发用户 pointer / keyboard 事件，除非明确是错误屏按钮或诊断交互。
- 不把诊断状态写进用户 Vue reactive state。

# 与未来 DevTools 的关系

当前诊断表层只负责“可见、可复制、可定位”的最小能力。未来 DevTools / Inspector 可以复用同一份诊断模型，但不能反过来让 M1 诊断层依赖完整 DevTools。

```txt
DiagnosticsModel
  -> badge
  -> error screen
  -> toast
  -> log sink
  -> future DevTools / Inspector
```

原则：

- 诊断数据先结构化，再分别渲染到 badge、错误屏、toast、日志。
- 不在 paint 代码里临时拼业务状态。
- JSON trace 只能作为诊断镜像，不作为生产协议来源。

# 与正式 DevTools 的未来接缝

M1 诊断表层只提供最小 overlay，不提供正式 DevTools 面板。但实现必须为未来 DevTools 留出稳定接缝：

```txt
DiagnosticEvent stream
DiagnosticsState snapshot
RenderTree / Dirty / Layout / Paint snapshots
Bridge protocol trace
Input / Scroll state snapshots
Log sink
```

未来 DevTools 可以：

- 订阅事件流。
- 拉取状态快照。
- 读取结构化日志。
- 触发受控 reload / copy diagnostics。

未来 DevTools 不可以：

- 直接依赖当前 badge/toast 的绘制坐标。
- 解析错误屏文案作为协议。
- 通过用户 App tree 插入调试节点。
- 要求 M1 overlay 反过来依赖 DevTools 是否存在。

# DiagnosticsModel

## 实现落点

M1 可以先把实现收在 `arrange_juce` 内部，但必须按未来可抽出的形态写：

```txt
AppResolver / DevServerClient / ScriptHost / Bridge / Input / Scroll / Resource
  -> DiagnosticEvent
  -> DiagnosticsState reducer
  -> badge renderer
  -> error screen renderer
  -> toast renderer
  -> log sink
```

约束：

- 事件来源只描述事实，不直接决定 UI 样式。
- `DiagnosticsState` 是单一诊断状态快照；paint 只能读取快照，不在绘制中临时探测 live server、文件系统或脚本 runtime。
- `activeSource` 只能由实际加载成功结果更新：live 成功才是 `Live`，dist 成功才是 `Dist`，不能把“配置了 live”误显示成“当前运行 live”。
- 错误屏使用同一份 `DiagnosticError`，不能另起一套只服务错误页的字符串模型。
- 日志、toast、badge、错误屏的文案可以有不同详略，但事件 id、source、URL/path、errorCode 必须来自同一事件。
- 未来真正 DevTools 接入时，只应订阅或查询 `DiagnosticsState` / `DiagnosticEvent`，不能反向依赖当前 overlay renderer。

核心模型：

```cpp
struct DiagnosticsState {
    BuildMode buildMode;          // Debug / Release
    AppSource activeSource;       // Live / Dist / None
    bool liveEnabled;
    bool distEnabled;
    std::string liveUrl;
    std::filesystem::path distPath;
    std::optional<DiagnosticError> error;
    std::vector<DiagnosticToast> toasts;
};
```

## 生命周期

加载、reload、错误恢复和 HMR 必须按事件驱动更新诊断状态：

```txt
load/reload requested
-> emit AppLoadStarted
-> try live/dist
-> emit AppLoadSucceeded | LiveUnavailable | FallbackToDist | AppLoadFailed
-> reduce DiagnosticsState
-> schedule repaint / full repaint
-> render badge/error/toast
-> write log sink
```

约束：

- `DiagnosticsState` 更新必须发生在 UI 输出之前，不能 badge 用一套状态、错误屏用另一套状态。
- 进入或退出错误屏、source 切换、root rebuild 后必须 full repaint。
- toast / badge 的 repaint 可以是局部 repaint，但若局部 bounds 不可靠，M1 必须 full repaint。
- 日志写入不能阻塞音频线程，也不能在 paint 内做文件 I/O。
- 文件日志必须在 message/background safe 的位置追加；失败时降级到 debugger log 并发出 `LogSinkFailed` 诊断事件。

## 与用户 App 的边界

诊断表层属于 Arrange Editor，不属于用户 App：

- 用户不能通过 `Box` / `Text` / `zIndex` 覆盖或布局诊断元素。
- 诊断元素不能污染用户 focus、hover、pointer capture、accessibility tree。
- 诊断状态不能写入用户 Vue reactive state。
- 用户 App 的错误边界只能处理用户组件内可恢复错误；无法显示用户 UI 的错误仍进入 Arrange 错误屏。
- 诊断快捷键默认由 Editor 先处理，除非用户显式改写 `EditorConfig.diagnostics.shortcuts`。

诊断事件：

```txt
AppLoadStarted
AppLoadSucceeded
AppLoadFailed
LiveUnavailable
FallbackToDist
ReloadRequested
ManualReloadRequested
LiveToggled
HmrConnected
HmrDisconnected
HmrReloadReceived
ResourceMissing
ProtocolMismatch
ScriptException
```

事件最少携带：

```txt
event id
level
category
timestamp
build mode
active source
configured live/dist
url/path
short message
detail message
error code
```

这些事件同时进入：

- 状态 badge。
- 错误屏。
- overlay toast。
- 日志 sink。

不同输出渠道允许过滤事件，例如 `ReloadRequested` 可以只进入日志和 toast，`ScriptException` 必须进入错误屏与日志。

# Debug 状态指示器

## Editor badge

Editor 内统一绘制状态 badge。默认位置：

```txt
top-right
margin: 8dp
height: 20dp
cornerRadius: 6dp
```

默认文案：

- `Debug live`
- `Debug dist`
- `Release dist`
- `Debug live failed -> dist`
- `Debug no app`

默认样式：

```txt
fontSize: 11sp
padding horizontal: 8dp
background: 0xCC111827
border: 0x664B5563 1dp
text: 0xFFE8EAED
```

状态色：

- live：绿色点 `0xFF22C55E`。
- dist：蓝色点 `0xFF3B82F6`。
- fallback：黄色点 `0xFFF59E0B`。
- error / no app：红色点 `0xFFEF4444`。

行为：

- badge 不参与用户 layout。
- badge 默认不拦截鼠标事件。
- badge 在 Debug 默认显示。
- Release 默认隐藏；如果用户显式开启诊断，也可显示 `Release dist`。
- badge 内容反映“实际 active source”，不是用户配置意图。
- badge 文案不得从临时字符串拼接推断；必须来自 `DiagnosticsState.buildMode`、`DiagnosticsState.activeSource` 与最近 source 事件。
- badge 点击默认无行为；若未来开启交互，也必须明确进入诊断交互模式，不能误触用户 App。

## Standalone 标题栏

Standalone 尽量同步标题：

```txt
Arrange Demo [live]
Arrange Demo [dist]
Arrange Demo [error]
```

宿主插件窗口标题栏不作为可靠输出渠道，因此 VST3 / AU / AAX 中仍以 Editor badge 为准。

标题栏只表达 coarse source state，不承载详细错误。详细错误必须在错误屏、日志或 Copy diagnostics 中出现。

更新时机：

- load success 后更新 `[live]` / `[dist]`。
- error 后更新 `[error]`。
- no source 后更新 `[no app]`。
- reload started 时可短暂保持上一次状态，不显示尚未成功的新状态。

Standalone 标题栏是辅助通道，不是唯一证据。截图验收以 Editor badge / 错误屏为准。

# 错误屏幕

错误屏是诊断表层的强状态。当用户 App 无法显示时，错误屏替代用户 UI。

内容：

- 标题。
- 错误来源。
- 简短说明。
- 路径或 URL。
- 关键 stack / diagnostic summary。
- 当前 source 配置：live enabled、live URL、dist path。
- 操作提示。
- Retry。
- Copy diagnostics。

行为：

- 进入错误屏必须 full repaint。
- 退出错误屏必须 full repaint。
- Retry 走统一 `live -> dist -> error` 加载链路。
- Retry 不复用上一次失败分支；每次都重新解析当前配置与环境，因此支持 live 半路启动、半路关闭、完全无 live 与完全 live。
- 错误屏上的普通点击不应误触发用户 App pointer 事件。
- 错误屏不触碰音频线程。
- Debug 展示详细诊断；Release 保持克制，但必须可复制完整诊断。
- Copy diagnostics 复制结构化文本包，至少包含 build mode、active source、configured source、URL/path、错误摘要、stack、最近诊断事件。

样式：

```txt
background: 0xFF2A1014
title: 18sp bold 0xFFFF6B6B
body: 13sp 0xE6FFFFFF
code/path: 12sp monospace-like 0xFFE5E7EB
button: rounded 6dp, background 0xFF374151
```

# Overlay toast

toast 用于短暂提示，不替代错误屏。

适用事件：

- `Reloaded from live`
- `Live unavailable, loaded dist`
- `Live enabled`
- `Live disabled`
- `HMR connected`
- `HMR disconnected`
- `Copied diagnostics`

不适用事件：

- 无法显示用户 UI 的致命错误。
- 需要用户阅读 stack 的错误。
- 高频事件，例如每帧 repaint、每次 pointer move。

默认位置：

```txt
bottom-right
margin: 12dp
maxWidth: 360dp
```

默认行为：

- 显示 2.5 秒。
- 同类 toast 合并。
- 最多同时显示 3 条。
- 不参与用户 layout。
- 默认不拦截鼠标事件。
- Release 默认只显示用户显式开启的诊断 toast。
- 错误屏激活时，toast 仍可绘制，用于验证诊断 overlay 链路；错误屏本身仍独占用户 App 输入。
- toast 不用于展示 stack trace；需要堆栈的事件进入错误屏或日志。
- toast 队列由诊断层持有，不能进入用户 App tree。

样式：

```txt
background: 0xEE111827
border: 0x334B5563 1dp
cornerRadius: 8dp
title: 12sp 0xFFE8EAED
body: 11sp 0xFFB8BDC7
```

# 日志输出

日志必须结构化，至少包含：

```txt
time
level
category
event
message
source
path/url
errorCode
```

级别：

- `trace`
- `debug`
- `info`
- `warn`
- `error`

类别：

- `app`
- `live`
- `hmr`
- `dist`
- `bridge`
- `script`
- `layout`
- `paint`
- `input`
- `scroll`
- `resource`
- `host`

Debug 默认输出到：

- IDE / debugger log。
- x64dbg / Visual Studio 可见的 debug output。
- 可选文件 log。

Release 默认只输出 `warn` / `error`，且不得泄露用户私有路径以外的敏感内容。完整 debug log 需要用户显式开启。

日志事件与 overlay 事件共源：

- 一个 `DiagnosticEvent` 可以同时产生日志、toast、badge 状态变化和错误屏状态变化。
- 日志 sink 不得自行重新探测 dev server、dist path 或 script state。
- 日志格式可以是文本行，但字段必须结构化生成，便于未来 DevTools ingest。

建议文本行格式：

```txt
2026-05-08T22:10:33.123+08:00 info app AppLoadSucceeded source=live url=http://127.0.0.1:9178
```

# 用户控制

目标配置：

```cpp
config.diagnostics.badge = arrange::juce::DiagnosticVisibility::DebugOnly;
config.diagnostics.toasts = arrange::juce::DiagnosticVisibility::DebugOnly;
config.diagnostics.errorScreen = true;
config.diagnostics.logLevel = arrange::juce::LogLevel::Info;
config.diagnostics.logFile = {};
config.diagnostics.copyFullDiagnosticsInRelease = true;
```

语义：

- `badge` 控制 Editor 内状态 badge。
- `toasts` 控制 overlay toast。
- `errorScreen` 控制 Arrange 是否显示错误屏；M1 不建议关闭，关闭只允许高级嵌入方把错误转给自己的容器。
- `logLevel` 控制最低输出级别。
- `logFile` 为空时不写文件。
- `copyFullDiagnosticsInRelease` 控制 Release 错误屏复制诊断时是否包含完整 stack/path/event history。

可选值：

```txt
Hidden
DebugOnly
Always
```

环境变量可作为开发期覆盖：

```txt
ARRANGE_DIAGNOSTICS=0|1
ARRANGE_DIAGNOSTIC_BADGE=0|1
ARRANGE_DIAGNOSTIC_TOASTS=0|1
ARRANGE_LOG_LEVEL=trace|debug|info|warn|error
ARRANGE_LOG_FILE=path
```

优先级：

```txt
显式 EditorConfig
-> 环境变量
-> build mode 默认值
```

显式 `EditorConfig` 永远优先，因为它代表宿主/插件作者的发布意图。环境变量只作为开发期临时覆盖，不能改变 Release 包的安全默认策略。

运行时快捷键：

```txt
F5              手动 reload，走 live -> dist -> error
Ctrl/Cmd+F5     切换 live enabled 后 reload
F6              Debug 下发送一条新的诊断 toast，文案包含当前时间并自然消失
F7              Debug 下触发“手动诊断错误页”；恢复仍走点击 retry 或 F5 reload
```

快捷键属于开发期诊断交互，不进入用户 App key event。若用户未来需要覆盖快捷键，必须在 `EditorConfig.diagnostics` 中显式声明，而不是让用户 App 抢占。

M1 默认只定义上述快捷键。其它诊断交互，例如打开 DevTools、展开 overlay、锁定 toast、切换 badge，应等正式 DevTools API 设计后再加入。

# 默认策略

Debug：

- badge：显示。
- toast：显示。
- error screen：显示详细诊断。
- log level：`info`。

Release：

- badge：隐藏。
- toast：隐藏。
- error screen：显示克制诊断，但支持复制完整信息。
- log level：`warn`。

测试模式：

- badge / toast 可强制显示。
- 所有诊断事件可导出 snapshot。
- 截图 smoke 可断言 badge/toast/error screen 的存在与文案。

# 绘制与事件原则

- 诊断 overlay 最后绘制，位于用户内容之上。
- badge / toast 默认 click-through。
- 错误屏是独占界面，可接收 Retry / Copy 等输入。
- overlay 不改变用户 content bounds。
- overlay 不触发用户 hover / focus / pointerInput。
- overlay 的 repaint 单独标记；但 error screen 进入/退出必须 full repaint。
- source 切换、root rebuild、error screen 进出、window resize 后若局部 repaint 证据不足，M1 必须优先 full repaint，不能留下残影。
- badge / toast 尺寸由诊断表层自己测量，不参与 Arrange 用户布局，不允许通过 `Box` / `Text` 等用户组件伪装实现。

# 长期工程约束

诊断表层由 `DiagnosticsOverlay` 承接事件记录、日志、badge、toast 与错误屏绘制。`ArrangeEditor` 只提供运行状态快照、调度 repaint 与处理 Retry 等宿主事件。

`DiagnosticsOverlay` 仍属于 `arrange_juce` 的 editor overlay，不是用户 App 组件，不参与用户 App layout、zIndex、focus、hover、pointer 和 reactive state；也不能发展成第二套生产 UI 系统。后续接入统一 overlay / invalidation 管线时，必须保持这条边界。

# 不做

- M1 不做完整 DevTools dock / remote inspector。
- M1 不做节点选择器、属性编辑器、时间线。
- M1 不把 toast 当通用 UI 组件。
- M1 不把诊断状态塞入用户 Vue App。
- M1 不让诊断 overlay 影响 layout 或 hit-test 语义。
